# GoExample SLO and Alerts

This is the first executable service-level objective definition for the HTTP server. It is intentionally scoped to the metrics emitted by `Framework/observability.Metrics`; it does not claim that an external Prometheus, Alertmanager, dashboard, or paging route is deployed. The repository configuration baseline is `support/deploy/prometheus/prometheus.yml`; deployment and secret-mount instructions are in `support/deploy/prometheus/README.md`, and rule behavior tests live in `support/deploy/prometheus/tests/goexample-slo.test.yml`.

## Objectives

| SLI | Objective | Measurement | Error budget |
| --- | ---: | --- | ---: |
| Availability | 99.9% monthly | Responses whose status is not `5xx` divided by all HTTP responses | 0.1% |
| Latency | 95% under 250ms | `goexample_http_request_duration_seconds` p95, excluding `5xx` | 5% of requests |
| Saturation | Accepted HTTP connections below 90% of configured capacity | `goexample_http_server_connections` / `goexample_http_server_connection_capacity`, plus request admission, goroutine and heap signals | 10% connection headroom |

The availability definition deliberately excludes server failures only. Client errors remain visible in the metrics and logs, but do not consume the server availability budget. A route-specific SLO should be added only after its traffic volume and user impact are known.

## Rules

Load `support/deploy/prometheus/rules/goexample-slo.yml` into Prometheus with `rule_files`. The file provides five-minute, 30-minute, one-hour, six-hour and three-day windows, availability error ratios, a latency histogram SLI, and multi-window burn-rate alerts:

- critical availability: 5m and 1h burn rate above 14.4x;
- warning availability: 30m and 6h burn rate above 6x;
- warning latency: p95 above 250ms for 10 minutes.
- warning HTTP connection saturation: accepted connections above 90% of the configured server capacity for 10 minutes.
- warning trace export: at least one final OTLP batch failure in the five-minute rate for 5 minutes.
- warning trace attempts: failed OTLP HTTP attempts remain above 0.01/s (roughly more than three failures per five minutes) for 5 minutes, including transient failures recovered by retry.
- warning trace queue: at least one capacity drop in the five-minute rate for 5 minutes.
- warning trace saturation: processor utilization above 80% for 5 minutes.
- warning queue dead letters: reliable deliveries continuously exhaust retry or explicitly reject processing for 5 minutes.
- warning queue settlement: acknowledgement or dead-letter callbacks continuously fail, time out, or panic for 5 minutes.
- warning queue lease extension: configured lease-extension callbacks continuously fail, time out, or panic for 5 minutes.
- warning authentication abuse: the configured login limiter continuously rejects requests for 5 minutes.
- warning audit delivery: configured security audit sink writes continuously fail for 5 minutes.

The alert rules aggregate route-template labels before calculating service ratios, so dynamic IDs are not used as metric labels. Connection events use only the fixed `new`, `active`, `idle`, `hijacked`, `closed`, and `_OTHER` states; addresses and connection identifiers are never labels. Queue delivery events use only `acknowledged`, `retried`, `dead_lettered`, and `settlement_failed`; lease events use only `extended` and `failure`. Broker names, destinations, message IDs, intervals, attempts, and errors are never labels. Admission and draining rejection rates are recorded separately without labels. A zero-capacity connection metric or zero-traffic request interval produces `NaN` rather than a false outage; operators must still require a minimum request volume before treating a low-traffic ratio as statistically meaningful.

## Operating procedure

1. Confirm the alert is not caused by a scrape, deployment, or edge outage by checking `goexample_process_uptime_seconds`, `goexample_http_server_connections`, `goexample_http_server_connection_capacity`, `goexample_http_requests_in_flight`, `goexample_http_admission_rejections_total`, `goexample_http_draining_rejections_total`, and the application logs. High connections with low in-flight requests usually indicate idle/slow clients; compare the fixed connection-state event rates before changing capacity. A rising admission counter means the API limit is being exhausted; a rising draining counter is expected during rollout and should be correlated with readiness and deployment events.
2. Use the `traceparent` response value and the `trace_id`/`span_id` JSON log fields to correlate an affected request. Check `goexample_otel_trace_exporter_enabled`, then compare the fixed `success` and `failure` outcomes in `goexample_otel_trace_export_attempts_total`, `goexample_otel_trace_export_batches_total`, and `goexample_otel_trace_export_spans_total`. Attempt failures show transient transport/status failures even when retry recovers the final batch; final batch failure means the bounded retry window was exhausted. Compare `goexample_otel_trace_processor_pending_spans` with `goexample_otel_trace_processor_capacity_spans`, use `goexample_otel_trace_processor_high_watermark_spans` to assess prior pressure, and check `goexample_otel_trace_queue_dropped_spans_total` for confirmed loss. For queue alerts, compare fixed delivery and lease events: retries without dead letters indicate recovery, dead letters require inspecting the adapter-owned DLQ through its access-controlled tooling, and settlement or lease-extension failures require checking broker availability/credentials and the configured interval/timeout/AckWait before restarting the fail-closed worker. Never place message content, destination, acknowledgement handles, or raw broker errors in labels or incident notes. For authentication limiter or audit sink alerts, follow `docs/security/server-audit-events.md`; compare only fixed audit sink outcomes and never copy credentials or raw sink errors into incident notes.
3. Check the route, status, latency bucket, goroutine, heap, and GC metrics before changing limits or rolling back.
4. Record the time range, affected route, customer impact, and mitigation. Close the incident only after the burn rate returns below the alert threshold and a follow-up action is filed.

## Evidence boundary

The repository tests the metric names, fixed label set, standard server capacity/state observation, observer-panic isolation, official OpenTelemetry server/use-case/outbound spans, trace propagation, rule presence, and the OTLP/HTTP protobuf wire contract against a local fake collector. It verifies that a slow collector does not block an HTTP request, provider shutdown flushes queued spans, and one batch recovers from a 503 within its bounded retry window while preserving one failed and one successful HTTP-attempt counter. A separate continuous-503 test verifies the final batch failure, followed by a later successful batch. A deterministic stalled-exporter burst test also verifies that ending application spans remains nonblocking, pending/capacity/high-water reach 5/5/5, all 96 excess spans increment the queue-drop counter, and pending returns to zero after recovery. Redis, `database/sql`, and broker-neutral queue callbacks have low-sensitivity local instrumentation contracts; reliable-delivery tests cover bounded cloned retries, explicit non-retryable handling, acknowledgement, dead-lettering, settlement and lease-extension error/timeout/panic redaction, cancellation, and fixed events through fake callbacks. SQL uses a standard-library fake driver. The fixed Core NATS contract has no durable acknowledgement semantics, while a single-node file-backed JetStream contract verifies server-acknowledged publish, `NumDelivered >= 2` during an omitted acknowledgement, confirmed WorkerGroup acknowledgement, permanent-failure DLQ delivery, and drained source pending state. The same real-server contract then uses an 800-millisecond `AckWait`, 100-millisecond extension interval, and 1.5-second handler to prove `InProgress` prevents redelivery until confirmed acknowledgement, with zero extension failures and drained pending state. A separate abrupt process-restart contract proves three messages, the durable consumer, and the same unacknowledged stream sequence survive the file-store restart before acknowledgement, DLQ, and pending state converge. The structured report deliberately records that `NumDelivered` was 1 before and 1 after restart, so that metadata is not treated as a durable cumulative retry counter. A three-node contract then configures three-replica source/DLQ streams and durable consumers, connects a dedicated business session to the actual source stream leader, and retains the same connection, JetStream/stream/consumer handles, and adapter through three leader stops. After the first failure, all replicas become current before the first successor is stopped with sequence 5 outstanding. That node remains offline while sequence 7 is fetched and the current leader is stopped: Core connectivity to the sole survivor remains, JetStream rejects a publish within three seconds, and restarting the sequence-7 node restores quorum, same-sequence redelivery, lease preflight, publish, acknowledgement, and pending convergence. The last offline node then restarts and all four resources return to three current replicas. A schema-v5 phase leaves sequence 9 unacknowledged, barrier-releases the current leader and another replica into concurrent stop calls with at most 250 milliseconds of start skew, verifies sole-survivor Core connectivity and bounded no-quorum rejection, then restores same-session sequence-9 redelivery, lease preflight, sequence-10 acknowledgement, and all replicas. Static JetStream worker paths calculate a cooperative worst-case handler/retry/backoff/settlement budget, reject a short server-reported lease, update to a sufficient lease, and pass fresh `ConsumerInfo` preflight before WorkerGroup startup; restart and failover reports bind the 8.51-second requirement to the 9-second `AckWait`. Extension-enabled workers instead preflight the interval, bounded callback/final-settlement window, and safety margin. These contracts do not validate target-broker telemetry, target-latency safety margins, network-partition tolerance, infrastructure-level simultaneous failure, disk-corruption recovery, production broker identity/authorization, atomic DLQ/source settlement, or exactly-once. A pinned, source-built `promtool` 3.5.0 first validates the complete Prometheus configuration with `check config --lint=all --lint-fatal`, including its referenced rule file, 30-second scrape/evaluation intervals, 10-second scrape timeout, `/metrics` target, and file-backed Bearer authorization. Validation creates an explicit non-secret credential fixture only while the command runs and removes it in `finally`; `secrets/` is ignored. Standalone lint still validates all 48 rules, while ten behavior scenarios with fixed rule-group order cover all 13 alert rules and lock their triggering thresholds, pending durations, fixed severity labels, annotations, and runbook links. Schema-v3 evidence retains the complete Go dependency checksum set, binary hash, config/rule/test inputs, five outputs, timestamps, and five exit codes behind tamper checks. The repository does not yet provision or validate a real OpenTelemetry Collector and trace backend, provision a Prometheus/Alertmanager pair, connect the outbound HTTP, SQL, or queue clients to a production use case, validate target telemetry, notification delivery, a target broker or controlled paging drill, or retain a successful remote JetStream artifact. Those are required before declaring the observability objective production-complete.

A schema-v6 phase now exercises a local route partition while all three NATS processes remain alive. Three TCP proxies separate actual cluster listeners from advertised routes; the contract closes every active route with sequence 11 outstanding, directly probes all Core endpoints, keeps the original business connection on its server, and requires a bounded JetStream publish failure. The source leader is deliberately placed on another server, and route recovery must still report exactly 11 messages before same-session sequence-11 redelivery, lease preflight, sequence-12 acknowledgement, pending convergence, and three current replicas. The report, manifest, and verifier bind the route counts, server identities, no-late-commit check, and unchanged aggregate server-start count. This is loopback fault-injection evidence only; the unvalidated network-partition boundary above now specifically means target-broker, cross-host, cross-zone, network-device, and authenticated production behavior.

A separate local JetStream snapshot contract archives checked stream bytes with durable consumer state, deletes the original stream, and restores a three-message checkpoint while excluding one later write. It requires the outstanding sequence and pending counts to survive, then completes acknowledgement, dead-lettering, and pending convergence. Its strict evidence path recomputes the archive byte count and SHA-256, requires deliberate tamper rejection, checks server snapshot/restore markers, and bounds restore to 15 seconds. This is single-node logical snapshot evidence only, not disk-corruption, cross-host backup, target capacity, production broker authorization, PITR, RPO, or RTO evidence.

The base real single-node JetStream delivery and dynamic-lease contract also has a dedicated strict evidence path. Its schema-v1 inner report records four source messages, omitted-ack redelivery, confirmed acknowledgement, DLQ publication and acknowledgement, the exact static 8.51-second requirement and 9-second AckWait, the exact dynamic 700-millisecond requirement and 800-millisecond AckWait, the 1.5-second handler and 100-millisecond extension interval, successful extension count, zero extension failures, no post-settlement redelivery, and drained pending state. The schema-v1 outer verifier binds the fixed Go command, pinned image, copied server binary, runtime/source/scope hashes, raw output, server log, inner report, and exact successful nine-artifact checksum set; failed runs remain bounded and cannot claim semantic completion. This is local disposable single-node evidence only, not target broker telemetry, authorization, latency, capacity, cross-host recovery, atomic settlement, ordering, exactly-once, RPO, or RTO evidence.
