## 2. 复评发现

1. `Framework/health/checker.go` 在 goroutine 中直接调用注册的健康检查回调。回调属于扩展点，若因可选依赖或业务代码 panic，会使进程级 goroutine 未恢复并终止整个服务，而不是把该检查标记为失败。
2. 该风险可以在仓库内确定性复现，且不依赖真实 Redis、SQL、NATS、网络或硬件；因此属于本轮可诚实推进的可靠性优化。
3. `scripts/lib/evidence-manifest-contract.mjs` 未绑定 `Framework/health/checker.go`、`checker_test.go` 与 `benchmark_test.go`。健康实现和回归测试可能在清单之外发生漂移，削弱 evidence manifest 的完整性。
4. V88 的 SDK 默认 HTTP 总超时、V87 redirect wire response、V86 context/body 所有权、V85 JetStream、V84 auth、V83 HTTP client、V82 Redis/SQL 等边界已通过现有门禁，本轮不重复修改或计分。
5. 当前主机没有 Docker/Podman/nerdctl，WSL 没有 Linux 发行版；真实 PostgreSQL recovery、生产 Redis Sentinel/NATS、目标 edge/DNS/证书、容量、远端 provenance 与组织审批仍不能由本地替身代替。

## 4. V89-01 实施约束与非目标

1. `Check` 的公开类型、`Register`、`Readiness`、报告 JSON 结构和状态字符串保持不变；只在内部调用边界恢复 panic。
2. panic 不向响应、日志、span、metric 或报告泄露 panic 值、URL、凭据、后端错误或业务数据；对外只表现为该检查 `failed`。
3. 每个回调仍由独立 goroutine 并发执行并共享既有 timeout；`recover` 不新增重试、无限 goroutine、锁、网络往返或后台状态。
4. 正常返回 nil/error、超时、取消、draining、缓存、注册修订号和报告复制语义必须保持。
5. evidence manifest 只增加三个仓库内文件的确定性哈希；受影响的审计、授权、OIDC、SDK 和总 manifest 必须由原生脚本重建，禁止手工篡改哈希。
6. 本地 panic 测试不等于真实生产依赖、目标集群、硬件、容量或故障演练证据；不修改、构建、测试或计分 `MSFront`。

## 6. 性能、内存与并发评估

`callCheck` 在每个健康检查 goroutine 内执行一个 defer/recover。正常回调只增加一次内部调用层，缓存命中仍不执行回调；没有新增 timer、retry、channel、锁、网络 I/O 或报告复制。panic 路径从“进程崩溃”变为一次失败结果，代价是受既有 timeout 和 refresh 生命周期管理的单个失败检查。

本地 benchmark、测试和 `httptest` 只能说明控制流、缓存和资源边界；不能外推生产 p95/p99、CPU、RSS、连接池、目标容量、跨主机恢复、真实 DNS/TLS/HTTP/2/3 或硬件表现。

## 7. 安全、可靠性与可观测性评估

- 健康扩展点 panic 被失败关闭，避免可选依赖或第三方检查导致整个进程退出；报告不暴露 panic 值。
- readiness 仍遵守 draining、caller cancellation、缓存 TTL、revision invalidation 和统一 timeout；没有改变 HTTP 状态或公开 schema。
- evidence manifest 对实现、测试和 benchmark 建立哈希绑定；契约变更后所有受影响本地报告均由脚本重建，旧哈希会被拒绝。
- 真实生产 edge、身份、密钥、共享状态、消息恢复、容量、远端制品和组织审批继续保持 `not_recorded`，不以本地模拟替代。
