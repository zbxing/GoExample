# GoExample 待优化 V11（非 MSFront）

生成日期：2026-08-20  
范围：根工作区、Go `Framework`、`Proj/Example`、协议与网络、观测、测试、CI、容器、部署和生产证据；**明确排除 MSFront**  
评估基线：`docs/评估/项目架构与性能评估.md` V11  
当前全项目评分：**9.0/10**（精确值 **8.960/10**）
目标评分：**10.0/10**  
原则：只按实现、自动测试、失败门禁、目标环境记录或恢复演练提分；静态接口、workflow、YAML 和 loopback 不能冒充生产能力。

## 1. 结论

8.960 不是代码质量低分。Go 服务的本地工程、协议基线、安全门禁和测试覆盖已经较强，剩余扣分主要来自两类问题：

1. 仍能由仓库自身修复的服务器语义缺口，例如 Framework 仍暴露 Fiber 类型、outbound/database instrumentation 缺失、API 生命周期和故障矩阵不完整。
2. 必须依赖真实系统和目标环境的闭环，例如外部共享状态、OTel collector、生产 edge、Linux 容量拐点、正式身份、数据库恢复、编排演练和签名发布。

本轮先完成第一类中风险最高、可重复验证的项目。第二类只定义接口和验收标准，不以替身或文档提高评分。

## 2. 扫描发现

### 优点

- Go workspace、Framework 与 Example composition root 边界清楚，首个 application use case 已脱离 HTTP 框架。
- 请求体、请求头、连接、业务并发、read/write/idle/request/shutdown 均有显式预算和负向配置测试。
- 已有真实 TCP TLS/HTTP1.1、标准 HTTP/2 对照、慢请求头/体、慢读写超时、draining、shutdown 和代理信任边界。
- JWT 必需 claims、audience、最大年龄、角色边界、Bearer challenge、secret 域隔离和生产 fail-fast 较完整。
- 结构化日志、低基数指标、官方 OTel server/use case span、W3C Trace Context、Request ID 输入治理、SLO rules、race/vet/build 与供应链 workflow 已建立。
- OpenAPI 运行路由对照、统一 envelope、JSON media type、验证错误和受保护操作 401 契约均有门禁。
- 幂等 key 已绑定 method/target/principal/media type/body SHA-256 指纹；keep-alive、idle 回收、TCP 半关闭和 shutdown 连接归零均有真实 socket 契约。

### 需要完善

- **外部共享状态缺失：**production external 模式会 fail-fast，但仓库没有 Redis/等价 `Storage`、分布式 `Locker`、跨实例 limiter/idempotency/revocation 实现。
- **标准生态锁定：**Example 生产 query 与 composition root 已不再导入 Fiber，但 `httpapi.Options` 的高级 `RouteRegistrar`、Storage、validator 和 server 仍暴露 Fiber 类型；只有一个真实 Framework 消费者。
- **取消语义限制：**客户端断连不能及时取消 Fiber application context，昂贵下游只能依赖主动 deadline 或停机取消。
- **协议部署缺口：**Fiber listener 没有已验证 HTTP/2/3；loopback edge 不能替代 Nginx/Envoy/Ingress/cloud LB 的 header、buffering、timeout、disconnect 和 drain 契约。
- **观测未闭环：**官方 OTel SDK、server/use case span 和可选有界 OTLP/HTTP exporter 已实现，但没有真实 collector、outbound/database instrumentation、dashboard、Alertmanager、drop/retry 指标或告警演练。
- **容量证据不足：**已有 benchmark 入口但没有可核验 Linux artifact、benchstat 趋势、真实 I/O workload、容量拐点、FD/网络/队列和长稳结果。
- **身份仍为演示实现：**Go auth 是单用户 HS256 示例，没有 OIDC/JWKS、MFA、refresh rotation、设备会话、集中撤销和 secret manager。
- **部署和恢复未闭环：**没有 Kubernetes/等价多副本演练、PDB/HPA/rollback、依赖故障矩阵、RPO/RTO、签名、provenance 和部署验签。
- **API/Framework 治理不足：**breaking-change gate 与首批运行时弃用契约已建立，但仍缺 SDK、消费者矩阵、真实迁移演练、Framework semver/changelog/兼容矩阵、第二消费者和正式 threat model。

## 4. 本轮实施设计

### V11-00 幂等请求指纹与冲突治理

状态：**已完成。** 顺序回放/冲突、并发竞争、共享 storage 命名空间和 race 均已验证。

问题：只按客户端 key 缓存响应会把不同载荷错误地视为同一操作。key 猜测或调用方复用还可能造成跨 principal 的旧响应回放。

实施：

- 指纹绑定 HTTP method、route path、已认证 subject（无认证时为 anonymous）、Content-Type 和原始 body。
- 使用 SHA-256 固定长度摘要，不在存储、错误或日志中记录原始 token/body。
- 指纹与响应使用相同 route namespace、同一 locker 和相同 TTL；共享 store 注入时指纹也写入共享命名空间。
- 相同 key 与相同指纹继续回放，设置 `X-Idempotency-Replayed: true`。
- 相同 key 与不同指纹返回 `409 Conflict`、统一禁缓存 envelope，不执行 handler，不覆盖原响应。
- 保持未携带 key 的请求、登录路由和安全方法原行为不变。

验收：顺序和并发冲突测试通过；共享 store key/TTL/deadline/lock namespace 可观察；race 通过。

### V11-01 keep-alive、半关闭与连接收敛

状态：**已完成。** 三项真实 TCP 契约连续重复运行并通过 race。

实施：

- 在同一真实 TCP 连接连续发送两个 HTTP/1.1 请求，证明连接复用与响应边界正确。
- 设置短 `IdleTimeout`，证明空闲 keep-alive 连接在上限内关闭且不会再次执行 handler。
- 客户端发送完整请求后调用 `TCPConn.CloseWrite()`，证明服务端仍返回完整响应并关闭连接。
- 使用计数 listener 跟踪已接受连接，在 shutdown 后断言 active connection 归零，避免仅以 goroutine 数量推测 FD 收敛。

验收：普通模式重复运行和 race 均稳定；Windows 与 Linux 不依赖固定端口或进程级 FD API。

### V11-03 OpenTelemetry SDK 与有界导出

状态：**部分完成。** 本地 SDK、server/use case span、OTLP/HTTP wire contract、慢 collector 非阻塞和 shutdown flush 已验证；真实 collector、outbound/database instrumentation、drop/retry 指标、dashboard、Alertmanager 和告警演练仍未完成。

实施：

- 使用官方 OpenTelemetry Go SDK 创建 `SERVER` span，严格接收 W3C `traceparent`/`tracestate`，并保留现有 trace/log 关联接口。
- server span 只记录 method、route template 和 status；不记录 raw URL、body、token、用户输入或任意错误文本。
- Example 的 `project.get` application use case 创建真实 child span，业务包仍不依赖 Fiber 或 `net/http`。
- exporter 默认关闭；启用 `otlp` 时使用 OTLP/HTTP protobuf、ParentBased ratio sampler 和有界非阻塞 `BatchSpanProcessor`，queue、batch、schedule delay 与 export timeout 均可校验配置。
- composition root 在所有退出路径以固定 timeout shutdown/flush provider；启动日志只记录 exporter 模式，不泄漏 endpoint。
- `httptest` collector 验证 base path 自动追加 `/v1/traces`、protobuf 请求、慢 collector 不阻塞业务请求以及 shutdown flush。

### V11-08 健康接口弃用契约

状态：**部分完成。** Breaking-change gate、首批 operation 弃用声明和运行时迁移信号已完成；SDK、消费者矩阵和真实迁移演练仍未完成。

实施：

- `/api/health`、`/api/health/ready`、`/api/health/startup` 明确映射到 `/livez`、`/readyz`、`/startupz`。
- 兼容路由在 200 与 503 响应均返回 RFC 9745 `Deprecation`、RFC 8594 `Sunset` 和 RFC 8288 `successor-version` `Link`；标准探针不携带弃用头。
- CORS 显式暴露三类响应头，浏览器消费者可读取迁移信号。
- OpenAPI 将三个 operation 标记为 `deprecated: true`，所有已声明响应状态均引用带弃用头的 response component，并链接 184 天迁移文档。
- Go 行为测试、OpenAPI 契约测试与根 Node 守卫同时锁定运行时、文档和评分，避免只声明弃用但没有可执行迁移路径。

### V11-07 Context-only application query

状态：**部分完成。** Example 的生产 project route 与 composition root 已不导入 Fiber；Framework 高级注册器、Storage、validator、默认 handlers 和 server 仍是 Fiber 专用，且尚无第二个真实消费者。

实施：

- Framework 新增窄范围 `ApplicationQuery`：只表达当前真实存在的无请求体 GET use case，handler 仅接收 `context.Context` 并返回结构化数据或错误。
- Fiber adapter 在 Framework 内完成路由注册、统一成功 envelope 与错误边界；trace、request deadline、admission、draining 和默认中间件保持有效。
- `ApplicationQueries` 与高级 `RegisterRoutes` 不能同时配置；空路径、相对路径、空白、query/fragment、nil handler 和重复路径均在启动期失败。
- Example `projectapi.Queries` 和 `cmd/server` 不再导入 Fiber，`project.get` span 仍是 HTTP server span 的真实 child。
- Go AST 架构测试扫描 `internal/projectapi` 与 `cmd/server` 的非测试源码，阻止 Fiber import 回流；行为测试覆盖成功 envelope、错误脱敏、默认路由共存和非法配置。
