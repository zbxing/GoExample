# GoExample 待优化 V11（非 MSFront）

生成日期：2026-08-21
范围：根工作区、Go `Framework`、`Proj/Example`、协议与网络、观测、测试、CI、容器、部署和生产证据；**明确排除 MSFront**  
评估基线：`docs/评估/项目架构与性能评估.md` V11  
当前全项目评分：**9.1/10**（精确值 **9.143/10**）
目标评分：**10.0/10**  
原则：只按实现、自动测试、失败门禁、目标环境记录或恢复演练提分；静态接口、workflow、YAML 和 loopback 不能冒充生产能力。

## 1. 结论

9.143 不是代码质量低分。Go 服务的本地工程、协议基线、安全门禁和测试覆盖已经较强，剩余扣分主要来自两类问题：

1. 仍能由仓库自身修复的服务器语义缺口，例如 Framework 仍暴露 Fiber 类型、关系数据库/队列 instrumentation 缺失、outbound client 尚无真实业务消费者、API 生命周期和故障矩阵不完整。
2. 必须依赖真实系统和目标环境的闭环，例如外部共享状态、OTel collector、生产 edge、Linux 容量拐点、正式身份、数据库恢复、编排演练和签名发布。

本轮先完成第一类中风险最高、可重复验证的项目。第二类只定义接口和验收标准，不以替身或文档提高评分。

## 2. 扫描发现

### 优点

- Go workspace、Framework 与 Example composition root 边界清楚，首个 application use case 已脱离 HTTP 框架。
- 请求体、请求头、连接、业务并发、read/write/idle/request/shutdown 均有显式预算和负向配置测试。
- 已有真实 TCP TLS/HTTP1.1、标准 HTTP/2 对照、慢请求头/体、慢读写超时、draining、shutdown 和代理信任边界。
- JWT 必需 claims、audience、最大年龄、角色边界、Bearer challenge、secret 域隔离和生产 fail-fast 较完整。
- Go 登录、Bearer 拒绝、application query/command 角色拒绝和 metrics/pprof 授权具备低敏 `security_audit`、固定基数计数、持续登录限流告警和 11 种行为路径隐私断言。
- 结构化日志、低基数指标、官方 OTel server/use case span、W3C Trace Context、Request ID 输入治理、SLO rules、race/vet/build 与供应链 workflow 已建立。
- OpenAPI 运行路由对照、统一 envelope、JSON media type、验证错误和受保护操作 401 契约均有门禁。
- 幂等 key 已绑定 method/target/principal/media type/body SHA-256 指纹；keep-alive、idle 回收、TCP 半关闭和 shutdown 连接归零均有真实 socket 契约。

### 需要完善

- **外部共享状态尚缺目标环境闭环：**仓库已有 Redis `Storage`、分布式 `Locker`、原子 limiter 和跨 app idempotency；仍无目标 Redis TLS/ACL、Sentinel/Cluster、failover、eviction、容量、延迟、告警及 session/revocation 证据。
- **标准生态锁定：**Example 生产 query、typed URI/query/header authorized query、typed authenticated/authorized JSON command 与 composition root 已不再导入 Fiber，但 PUT/PATCH/DELETE、定制 middleware 仍需高级 `RouteRegistrar`，Storage、validator 和 server 也继续暴露 Fiber 类型；只有一个真实 Framework 消费者。
- **取消语义限制：**客户端断连不能及时取消 Fiber application context，昂贵下游只能依赖主动 deadline 或停机取消。
- **协议部署缺口：**Fiber listener 没有已验证 HTTP/2/3；loopback edge 不能替代 Nginx/Envoy/Ingress/cloud LB 的 header、buffering、timeout、disconnect 和 drain 契约。
- **观测未闭环：**官方 OTel SDK、server/use case/outbound/Redis database span、有界 OTLP/HTTP exporter、逐次 attempt/最终导出结果/queue-drop/processor saturation 指标和本地 retry/burst outage 契约已实现，但没有真实 collector、生产业务出站调用链、关系数据库/队列 instrumentation、dashboard、Alertmanager 或告警演练。
- **容量证据不足：**已有 benchmark 入口但没有可核验 Linux artifact、benchstat 趋势、真实 I/O workload、容量拐点、FD/网络/队列和长稳结果。
- **身份仍为演示实现：**Go auth 是单用户 HS256 示例；typed query/command 已有声明式 any-of 角色门禁，但仍缺租户/资源级策略。本地审计尚无不可篡改 sink、留存/删除、SIEM/paging 和具名责任人，也没有 OIDC/JWKS、MFA、refresh rotation、设备会话、集中撤销和 secret manager。
- **部署和恢复未闭环：**已形成 Redis、OTel、HTTP 生命周期和出站请求四组本地有界故障矩阵与 artifact，但没有 Kubernetes/等价多副本演练、PDB/HPA/rollback、真实依赖故障切换、RPO/RTO、签名、provenance 和部署验签。
- **API/Framework 治理仍未闭环：**OpenAPI breaking gate、运行时弃用契约、Framework SemVer/版本文件/changelog/公共 API snapshot、target-branch gate 与服务器威胁模型已建立，但仍缺 SDK、消费者矩阵、真实迁移演练、第二消费者和正式 release tag。

## 4. 本轮实施设计

### V11-00 幂等请求指纹与冲突治理

状态：**已完成。** 顺序回放/冲突、并发竞争、共享 storage 命名空间和 race 均已验证。

问题：只按客户端 key 缓存响应会把不同载荷错误地视为同一操作。key 猜测或调用方复用还可能造成跨 principal 的旧响应回放。

实施：

- 指纹绑定 HTTP method、route path、已认证 subject（无认证时为 anonymous）、Content-Type 和原始 body。
- 使用 SHA-256 固定长度摘要，不在存储、错误或日志中记录原始 token/body。
- 指纹与响应使用相同 route namespace、同一 locker 和相同 TTL；共享 store 注入时指纹也写入共享命名空间。
- 相同 key 与相同指纹继续回放，设置 `X-Idempotency-Replayed: true`。
- 相同 key 与不同指纹返回 `409 Conflict`、统一禁缓存 envelope，不执行 handler，不覆盖原响应。
- 保持未携带 key 的请求、登录路由和安全方法原行为不变。

验收：顺序和并发冲突测试通过；共享 store key/TTL/deadline/lock namespace 可观察；race 通过。

### V11-01 keep-alive、半关闭与连接收敛

状态：**已完成。** 三项真实 TCP 契约连续重复运行并通过 race。

实施：

- 在同一真实 TCP 连接连续发送两个 HTTP/1.1 请求，证明连接复用与响应边界正确。
- 设置短 `IdleTimeout`，证明空闲 keep-alive 连接在上限内关闭且不会再次执行 handler。
- 客户端发送完整请求后调用 `TCPConn.CloseWrite()`，证明服务端仍返回完整响应并关闭连接。
- 使用计数 listener 跟踪已接受连接，在 shutdown 后断言 active connection 归零，避免仅以 goroutine 数量推测 FD 收敛。

验收：普通模式重复运行和 race 均稳定；Windows 与 Linux 不依赖固定端口或进程级 FD API。

### V11-03 OpenTelemetry SDK 与有界导出

状态：**部分完成。** 本地 SDK、server/use case/HTTP client/Redis client span、OTLP/HTTP wire contract、总预算内有界 retry、逐次 attempt 结果、慢 collector 非阻塞、shutdown flush、出口停滞时有界 burst 丢弃、最终导出结果、queue-drop 与 processor saturation 指标已验证；真实 collector、生产业务出站消费者、关系数据库/队列 instrumentation、dashboard、Alertmanager 和告警演练仍未完成。

实施：

- 使用官方 OpenTelemetry Go SDK 创建 `SERVER` span，严格接收 W3C `traceparent`/`tracestate`，并保留现有 trace/log 关联接口。
- server span 只记录 method、route template 和 status；不记录 raw URL、body、token、用户输入或任意错误文本。
- Example 的 `project.get` application use case 创建真实 child span，业务包仍不依赖 Fiber 或 `net/http`。
- exporter 默认关闭；启用 `otlp` 时使用 OTLP/HTTP protobuf、ParentBased ratio sampler 和有界非阻塞 `BatchSpanProcessor`，queue、batch、schedule delay 与 export timeout 均可校验配置。
- composition root 在所有退出路径以固定 timeout shutdown/flush provider；启动日志只记录 exporter 模式，不泄漏 endpoint。
- `httptest` collector 验证 base path 自动追加 `/v1/traces`、protobuf 请求、慢 collector 不阻塞业务请求以及 shutdown flush。
- 官方 BatchSpanProcessor 前的非阻塞容量门只负责接纳/丢弃和计数，batch、timeout、ForceFlush、Shutdown 与 exporter retry 仍由 SDK 处理；exporter 完成后按 batch 大小回收容量，底层 channel 与有效容量一致，避免二次静默丢弃。
- 受控阻塞 exporter 在首个 batch 停滞后接收 100 个新 span；span 结束在 250ms 内完成，96 个超量 span 全部进入无标签 queue-drop counter，恢复后严格只导出正在处理的 1 个与容量为 4 的 queue；Prometheus 对五分钟持续丢弃告警。
- 容量门原子维护 processor pending/capacity/process-lifetime high-water gauge；同一测试锁定停滞时 5/5/5 和恢复后 pending 为 0，Prometheus 在利用率持续超过 80% 时预警，早于实际丢弃。
- HTTP `/metrics` 与 tracer provider 共用同一 `Metrics` 实例；OTLP enabled gauge 及最终 batch/span `success/failure` counter 只使用固定标签，不记录 endpoint、错误文本或凭据。
- collector 在 100ms export budget 下持续返回 503 时 `ForceFlush` 失败并累计 failure，恢复 200 后新 span 刷新成功并累计 success；Prometheus 规则对五分钟最终失败率持续大于零告警。
- 修复官方 exporter 默认 5 秒首次退避大于项目默认 3 秒总 export timeout、实际无法发起第二次请求的问题；每次 HTTP attempt timeout、初始/最大退避和最大 retry elapsed 都从总预算派生，connect/TLS/response header/连接池/header bytes 有限，shutdown 关闭 idle connections。
- `goexample_otel_trace_export_attempts_total{outcome="success|failure"}` 记录每次 HTTP 尝试且不含 endpoint、响应体、错误文本或动态标签；最终 exporter/shutdown 错误在离开 observability 边界前折叠为固定文本。同一 batch 首次 503、第二次 200 的测试锁定 attempt failure=1、success=1、最终 batch success=1；持续 503 测试使用敏感响应体并证明总预算内最终失败、错误/metrics 均不泄漏。Prometheus 对持续 attempt failure 单独告警。
- 独立 `httpclient` 使用标准库 `net/http`，为总请求、connect、TLS handshake、response header、expect-continue、idle connection、连接池和响应头字节提供有限预算，并启用 HTTP/2 与 TLS 1.2 下限；私有 CA/mTLS 配置会克隆隔离，也可注入自定义代理选择器。
- 每次出站传输创建 `CLIENT` span 并传播 W3C Trace Context；只记录规范化 method、status 和有界错误类别，非标准 method 统一为 `_OTHER`，不记录 raw URL/query、body、credentials、header 或任意 transport 错误文本。
- `httptest` 行为测试验证父子 span、远端传播、503 状态、敏感字段不入 span、原请求 header 不被改写、span 覆盖响应体读取生命周期、响应头上限、总 timeout 与调用方 cancel；修复并行负载下的标准库 timeout 取消分类后连续 50 轮定向测试稳定。
- `RedisConfig.TracerProvider` 由 Example composition root 注入同一 provider；自定义 go-redis Hook 为 connect、固定命令和 pipeline 创建 `CLIENT` span，未知命令折叠为 `_OTHER`，结果只取 `success/not_found/timeout/canceled/failure`，pipeline batch size 上限为 1000。
- Redis span 不记录 URL/host、key/prefix、value、命令参数、owner token、caller 路径、事件或 raw error；`NOSCRIPT` 回退按非错误缺失处理。行为测试覆盖 parent-child、Set/Get miss、Lua、锁/解锁、pipeline、后端停止和所有敏感字段负向扫描。

### V11-08 健康接口弃用契约

状态：**部分完成。** Breaking-change gate、首批 operation 弃用声明和运行时迁移信号已完成；SDK、消费者矩阵和真实迁移演练仍未完成。

实施：

- `/api/health`、`/api/health/ready`、`/api/health/startup` 明确映射到 `/livez`、`/readyz`、`/startupz`。
- 兼容路由在 200 与 503 响应均返回 RFC 9745 `Deprecation`、RFC 8594 `Sunset` 和 RFC 8288 `successor-version` `Link`；标准探针不携带弃用头。
- CORS 显式暴露三类响应头，浏览器消费者可读取迁移信号。
- OpenAPI 将三个 operation 标记为 `deprecated: true`，所有已声明响应状态均引用带弃用头的 response component，并链接 184 天迁移文档。
- Go 行为测试、OpenAPI 契约测试与根 Node 守卫同时锁定运行时、文档和评分，避免只声明弃用但没有可执行迁移路径。

### V11-07 Transport-neutral application query/command

状态：**部分完成。** Example 的无请求体 query、typed URI/query/header authorized query、authenticated/authorized JSON command 与 composition root 均不导入 Fiber；Framework 已建立 0.1.x 版本、兼容策略、changelog、91 符号公共 API snapshot 与 target-branch gate。PUT/PATCH/DELETE、定制 middleware、高级注册器、Storage、validator、默认 handlers 和 server 仍是 Fiber 专用，尚无正式 release tag、迁移演练或第二个真实消费者。

实施：

- Framework 新增窄范围 `ApplicationQuery`：只表达当前真实存在的无请求体 GET use case，handler 仅接收 `context.Context` 并返回结构化数据或错误。
- Framework 新增泛型 `NewQuery[Request, Response]`、`NewAuthenticatedQuery[Request, Response]` 与 `NewAuthorizedQuery[Request, Response]`：URI/query/header 输入绑定到 typed request，受保护 handler 只接收 subject、username、role IDs 组成的最小 `ApplicationPrincipal`，JWT/token/Fiber claims 不越过 adapter；authorized query 以大小写敏感的精确 role ID 执行 any-of 门禁。
- required roles 在构造时防御性复制，空列表、重复、非法 ID 和超过 32 项的声明在注册前失败；角色不足在请求参数绑定和 handler 前返回固定禁缓存 403，缺失/无效 Bearer 仍为 401。
- Framework 新增泛型 `NewJSONCommand[Request, Response]`、`NewAuthenticatedJSONCommand[Request, Response]` 与 `NewAuthorizedJSONCommand[Request, Response]`：project handler 只接收 `context.Context`、编译期确定的 request 和可选最小 principal，返回编译期确定的 response；Fiber/JWT 类型及 bind 生命周期不越过 adapter。
- 受保护 command 固定先执行 Bearer、any-of role，再执行 JSON media type、幂等、body bind 和 handler；401/403 不接触幂等状态，正确 subject 进入请求指纹，同 key 正确请求仍可执行和回放。
- Fiber adapter 在 Framework 内完成隔离的 URI/query/header 来源绑定、统一校验、JSON media type、幂等指纹/回放/冲突、统一成功 envelope 与错误边界；trace、request deadline、admission、draining 和默认中间件保持有效。
- typed query 每个导出字段必须且只能声明一个 `uri`、`query` 或 `header` tag，URI tags 与路径参数一一对应；query/header 无法覆盖 URI。动态 GET 只允许命名参数，静态/动态重叠、重复参数、默认路由覆盖及非规范路径均在注册前失败；legacy query 和 command 继续只允许静态规范路径。
- `ApplicationQueries`/`ApplicationCommands` 与高级 `RegisterRoutes` 不能同时配置；nil handler 和同 method 大小写重复路径也在启动期失败。
- application query/command 与已启用的 Framework 默认 GET/POST 路由按大小写不敏感语义冲突时，在注册任何 application route 前启动失败，避免 Fiber 按注册顺序静默命中错误 handler。
- Example `projectapi.Queries`、`projectapi.Commands` 和 `cmd/server` 不导入 Fiber；`GET /project` 的 `project.get`、要求 `demo` role 的 `GET /project/preview/:audience` 的 `project.preview` 与同样要求 `demo` role 的 `POST /project/describe` 的 `project.describe` 都是对应 HTTP server span 的真实 child；describe 只在认证启用时注册并把已验证 subject 作为 `requestedBy` 传入 use case，角色拒绝不会创建 application span。

- 两个独立 Redis client、两个 Fiber app 的并发行为测试证明 quota=1 严格一个 200/一个 429；同 key/body handler 只执行一次且另一请求 replay；同 key/不同 body 一个 200/一个 409；另覆盖有限 TTL、后端停止、锁等待上界和旧 owner 安全。
