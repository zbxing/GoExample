## 2. 全面复评发现

1. `fromJetStreamMessage` 对单个 header 仍先创建通用 map；当该 header 是 JetStream 控制元数据时，应用层最终不会看到任何 header，存在可消除的 map 分配。
2. 单个普通应用 header 仍走通用循环和预分配分支；单值、已通过 NATS header 形状约束的常见消息可以使用等价的单头 fast path，保持 body defensive clone、控制 header 过滤和多值拒绝。
3. `Headers()` 可能返回 `nil`、控制 header、单值应用 header、多值应用 header 或大 header 集合；所有路径必须保留现有错误 sentinel、字段顺序、header 名称字节、body clone、DLQ/ack/lease 语义。
4. `Metrics.Render`、trace carrier、幂等 fingerprint、MIME/ETag 和 JetStream 空 header 等 V94-V100 优化已闭合，不重复实施或重复计分。
5. V101-02/V101-03 仍是目标环境与授权窗口事项；本轮不伪造生产 RPS、p95/p99、RSS、GC、HA、RPO/RTO、exactly-once 或跨主机 provenance。

## 4. V101-01 实施约束与非目标

1. 仅对 `len(headers)==1` 的输入使用分支：控制 header 直接返回 cloned body 与 `nil` application headers；普通单 header 仅在值数量为 1 时返回一个新的 application map。
2. 空 header、非空多 header、大 header 集合继续使用并通过原有路径；控制 header 过滤仍大小写不敏感，多值应用 header 仍返回 `ErrInvalidMessage`。
3. 不改变 `queueclient.Message` 的 body clone、publish confirmation、ack/DLQ settlement、lease extension、consumer preflight、trace extraction、错误 sentinel 或公开 API。
4. benchmark 仅证明本机相对分配和耗时差异，不外推生产吞吐、延迟、容量或 HA。
