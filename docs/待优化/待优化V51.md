## 2. 全面复评发现

### 2.1 架构、协议与交付

- Framework、Solutions/Services、两套 SDK、独立 consumer、OpenAPI、部署恢复和 evidence 工具保持既有所有权与依赖方向。
- 入站 HTTP/Fiber、请求生命周期、身份授权、会话、审计、Redis、NATS、SQL、发布、恢复和 transport 测量的仓库内合同已闭环；目标 edge、正式身份与生产部署差距仍依赖外部环境。
- `httpclient` 已有有限连接/timeout/body、W3C tracing、安全方法 retry 与 client 级 breaker；retry 位于 breaker 内侧且所有 attempt 共用一个逻辑 span。

### 2.2 出站背压缺口

`RetryConfig` 对无响应 transport error 与固定 408/425/429/502/503/504 使用有限指数退避，但当前 `retryTransport` 完全忽略 `Retry-After`。下游即使明确要求等待 2 秒，客户端默认首轮仍可能在约 50ms 后再次请求，增加过载窗口内的同步重试压力。

服务端 header 也不能无限信任：极大秒数或远期日期不得扩大本地 `MaxBackoff` 和 request/client deadline。停止自动重试时，最终 response body 必须保留给调用方，不能被当作中间响应提前关闭。

### 2.3 V51-01 可执行边界

V51-01 解析有效十进制 `delay-seconds` 与 HTTP-date，实际等待取本地指数退避和服务端延迟的较大值。有效值超过 `MaxBackoff` 或剩余 deadline 时不启动下一 attempt，原 response/error 与 body 所有权保持不变；非法值回退原本的本地退避。

该能力不扩大安全方法、可重试状态、attempt 数量、最大退避或总 deadline，也不新增 header telemetry、全局 retry budget、adaptive concurrency、跨实例协调或写请求自动重放。

## 5. 性能与资源边界

成功响应、不可重试状态、写方法、无重试配置和不可重放 body 不进入新解析路径。新增工作只发生在本来就准备重试的失败响应上；其目标是减少下游明确过载时的过早 attempt，而不是宣称降低成功请求 CPU、分配或延迟。

等待仍由原 context 和 timer 管理，不创建后台 goroutine 或跨请求状态。任何生产吞吐、p99、恢复时间、最佳退避或容量提升都必须由真实依赖和目标环境测量，本轮不外推。
