## 3. V31-01 实施设计

### 3.1 原子发布协议

- 新建 `scripts/lib/atomic-output.mjs`，只使用 Node 标准 `fs`、`path` 与 `crypto` 原语。
- 临时文件与目标位于同一目录，名称包含进程 ID 和加密随机后缀，并以 `wx` 独占创建，避免跨文件系统 rename 和并发写者复用临时路径。
- 顺序固定为 `open -> write -> fsync(file) -> close -> rename`；canonical 路径在 rename 前保持旧版本，rename 后一次切换到完整新版本。
- `evidence-manifest.mjs` 保留既有 `.temp/*.json`、无符号链接目录链和单硬链接输出检查，只替换最终发布动作，不改变 schema、inventory、哈希或 verifier。

### 3.2 失败、并发与平台边界

- 写入、文件同步、关闭或 rename 任一步失败时抛回原始错误，并尽力关闭 descriptor、删除临时文件；不得先截断或删除旧 canonical 文件。
- 清理失败不能覆盖主失败；成功路径不残留临时文件。
- Windows 当前 Node 文件系统探针必须证明同目录 rename 可替换既有文件；真实文件系统测试同时锁定旧文件被完整新内容替换。
- 文件 `fsync` 只约束已写临时文件；未对父目录执行可移植同步，因此不把操作系统崩溃或突然断电后的目录项持久性列为已证明能力。

### 3.3 防回归与证据

- 在现有 Node 主测试中注入文件操作，断言成功调用顺序、descriptor 参数、同目录临时路径与禁止提前清理。
- 注入 write 与 rename 失败，断言旧目标未被触碰、descriptor 已关闭、临时文件已清理且原始错误保留。
- 使用真实文件系统覆盖“已有目标替换”和“无临时文件残留”，兼顾当前 Windows 环境。
- V31 文档与新 helper 加入 evidence input contract，输入由 282 增至 284；共享 input contract 变化后重建并独立验证七组领域 evidence。

## 6. 修复前证据

```text
aggregate evidence publication (before V31)
  JSON.stringify(manifest)
  writeFileSync(outputPath, source, 'utf8')
  existing canonical file: truncated before the new payload is complete
  concurrent verifier: may observe empty, partial, or complete new JSON
  failed/interrupted writer: may destroy the last valid canonical manifest

required after V31
  temporary path: same directory + unpredictable + exclusive create
  publish order: write -> fsync(file) -> close -> atomic rename
  reader visibility: complete old manifest OR complete new manifest
  pre-rename failure: old canonical manifest preserved
```

一次聚合 manifest 生成仍为 `O(input bytes + artifact bytes + manifest bytes)`；现有输入和制品散列继续使用固定 1 MiB buffer。V31 只增加一个 manifest-sized 临时文件、一次文件同步和一次同目录 rename，不增加服务请求分配、延迟、RPS 或容量结论。
