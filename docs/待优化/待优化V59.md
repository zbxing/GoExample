## 2. 本轮复评发现

### 2.1 可执行缺口

`httpclient.retryTransport` 在确定继续 retry 后直接关闭中间 response body。Go 的 HTTP/1.x transport 通常要求 body 读到 EOF 并关闭才能复用持久连接；小型 429/503 等错误正文因此可能让下一 attempt 新建 TCP/TLS 连接，在依赖故障窗口放大连接池、端口和握手压力。

### 2.2 必须共同修复的边界

- 只对已经决定丢弃并继续 retry 的中间 response 处理；最终 response/body 所有权绝不改变。
- 只排空非负且不超过 32 KiB 的已知 `Content-Length`；读取最多为声明长度加 1 字节。
- 未知、压缩后未知、超过预算或不守约响应仍立即 Close，不无界读取。
- 复用原 request context/client deadline，不新增 goroutine、配置、公开 API、span/metric label 或正文记录。
- 不扩大安全方法、transient status、attempt、Retry-After、jitter、backoff、breaker 或 deadline。
- 用真实 HTTP/1.1 connection state 证明小型 503 retry 复用同一连接，并用伪 body 固定所有预算和所有权分支。

### 2.3 性能与诚实边界

新工作只发生在原本已经决定继续 retry 的失败路径。小型正文会在 backoff 前被流式读取，最坏额外读取量为 32 KiB+1；成功路径、最终响应和大型/未知失败响应没有新增读取。目标是保留连接复用机会，不宣称生产 p99、吞吐、CPU、RSS、TLS 成本或容量已经改善。
