## 2. 全面复评发现

1. Redis 基础 API、refresh-session、browser-session、authorization-request 已拒绝 `nil context`，但 `ReadBrowserSession` 在读取到已过期记录后，会用 `context.Background()` 执行清理删除。

3. 缺口完全位于仓库内，可用 miniredis、Redis tracing recorder 和一次 EVALSHA 计数确定性验证；不依赖真实 Redis HA、TLS/ACL、硬件、目标网络或生产容量。

## 4. V93-01 实施约束与非目标

1. 不新增公开 API、配置、schema、operation、API version 或 release tag；只改变过期清理对 caller context 的归属。
2. 读取到过期记录后，若 `completedRedisContextError(ctx) == nil`，沿用原有原子删除脚本；若调用方已取消或 deadline 已到，跳过 best-effort 删除并直接返回 `ErrBrowserSessionExpired`。
3. 不创建后台 goroutine，不改变正常 context 的 Redis 命令、Lua、TTL、索引、错误脱敏和 tracing 语义。
4. 不把取消后的清理失败升级为新的公开错误；后续读取/库存脚本仍会按既有规则清理失效索引。
5. 不修改、构建、测试或计分 `MSFront`。

## 6. 架构、性能、内存与并发评估

browser-session Redis adapter 继续用 Lua 一次性读取 payload、索引和元数据。V93 只把过期后的 best-effort 删除从无条件后台 context 改为 caller-owned context，并在 caller 已完成时跳过该 mutation。正常路径不增加命令、连接、锁、goroutine 或分配；取消路径减少一次删除尝试和一个潜在 tracing span。

该修复改善取消与共享状态写入的生命周期一致性，不宣称提升生产吞吐、p95/p99、RSS、GC、HA 或容量。真实 Redis HA/TLS/ACL、跨主机恢复和目标容量仍需外部证据。

## 7. 安全、可靠性、数据与消息评估

- 取消请求不再脱离调用方继续删除 session，降低请求竞态下误删或审计顺序漂移风险。
- 正常过期清理仍使用原有原子 Lua 脚本；跳过清理时不会恢复、延长或返回过期 session。
- refresh-session、authorization-request、SQL transaction/outbox、JetStream settlement、OIDC/JWKS、审计链和 Prometheus 合同不变。
- 正式 Redis/PostgreSQL/NATS HA、PITR、RPO/RTO、KMS/SIEM、IdP/MFA、目标容量和远端 provenance 仍为 `not_recorded`。
