## 2. 全面复评发现

### 2.1 架构、协议与交付

- Framework、Solutions/Services、两套 SDK、独立 consumer、OpenAPI、部署恢复和 evidence 工具保持既有所有权与依赖方向。
- 入站 HTTP/Fiber、请求生命周期、身份授权、会话、审计、Redis、NATS、SQL、发布、恢复和 transport 测量的仓库内合同已闭环；目标 edge、正式身份与生产部署差距仍依赖外部环境。
- `httpclient` 已有有限连接/timeout/body、W3C tracing、安全方法 retry、client 级 breaker 和 V51 `Retry-After`；retry 位于 breaker 内侧且所有 attempt 共享一个逻辑 span。

### 2.2 出站重试去同步缺口

V51 计算出的 local backoff 与有效 `Retry-After` 都是确定值。相同配置的多个请求或副本同时遇到 transport failure、429 或 503 时，会在同一时间边界再次访问依赖；V51 已防止过早重试，但没有分散同步恢复波峰。

直接采用常见向下 jitter 会让等待短于服务端提示或既有本地退避；无界向上 jitter 又可能突破 `MaxBackoff` 和原 request deadline。停止自动重试时，最终 response body 必须继续由调用方拥有，不能在 jitter/deadline 判断前被关闭。

### 2.3 V52-01 可执行边界

V52-01 在 V51 有效等待 `delay` 上增加 `[0, min(delay/2, MaxBackoff-delay)]` 的随机纳秒增量。最终等待不会短于服务端提示或本地指数退避，最多增加 50%，且绝不超过 `MaxBackoff`。jitter 后的等待不能放入原 deadline 时，不启动下一 attempt，原 response/error 与 body 所有权保持不变。

随机源使用标准库 `math/rand/v2` 顶层并发安全函数，只服务于非安全 timer 调度。该能力不扩大安全方法、可重试状态、attempt 数量、最大退避、总 deadline、公共 API 或 telemetry，也不实现跨实例协调、全局 retry budget 或 adaptive concurrency。

## 5. 性能与资源边界

成功响应、不可重试状态、写方法、无重试配置和不可重放 body 不进入 jitter 路径。新增工作只发生在本来就准备重试的失败结果上，每次下一 attempt 前最多进行一次标准库整数采样；不新增后台 goroutine、队列、timer 池或跨请求状态。

该变化的目标是分散同步失败重试，不是宣称降低成功请求 CPU、分配或延迟。生产吞吐、p99、恢复时间、最佳 jitter 比例和容量提升必须由真实依赖与目标环境测量，本轮不外推。
