## 2. 本轮复评发现

### 2.1 可执行缺口

`natsjetstream.Adapter.ReceiveDelivery` 固定调用 `Consumer.Next(FetchMaxWait(...))`，只实现 pull consumer 路径。当前 preflight 已读取新鲜 `ConsumerInfo`，却没有检查区分 push/pull mode 的 `Config.DeliverSubject`。nats.go v1.53.1 的通用创建/更新入口仍可能把带 delivery subject 的配置包装为 `Consumer`，因此 Go 接口类型本身不能证明服务端 consumer 支持 pull。

结果是：其余持久性、DeliverAll、ReplayInstant、MaxDeliver、payload、subject、request expiration、pause 与 AckWait/BackOff 条件均合法的 push consumer 仍可通过启动门禁，直到 worker 发出 pull 请求才失败或无法按适配器合同交付。

### 2.2 必须共同修复的边界

- 通用与 adapter-bound preflight 均以同一次新鲜 `ConsumerInfo.Config.DeliverSubject` 为准。
- `DeliverSubject != ""` 返回固定 `ErrConsumerNotPull` 与正 required lease，支持 `errors.Is`，不暴露 identity、stream、filter/delivery subject、queue group、URL、配置值或 backend 原文。
- `DeliverSubject == ""` 继续既有 pause、持久性、DeliverAll、ReplayInstant、MaxDeliver、payload、subject、request expiration 与 AckWait/BackOff 校验。
- adapter 不订阅 push subject，不增加控制面写入、第二次 `Info`、公共配置、后台轮询、goroutine 或消息热路径工作。
- 单元测试锁定 push/pull、required lease、单次 `Info`、错误优先级与隐私。
- 真实 file-backed JetStream 必须证明 push consumer 被拒绝；显式删除并重建 pull consumer 后通过并完成原 delivery 合同。
- delivery evidence 升级 schema 11；目标生产 consumer mode 治理、broker 与容量继续 `not_recorded`。

### 2.3 性能与恢复边界

V64 把服务端已经明确的协议模式错配提前为启动失败，避免启动 worker 后才暴露 pull 不兼容。合法 pull consumer 只增加启动期一次 O(1) 空字符串比较；不新增网络往返、分配要求、锁、goroutine、timer、buffer、retry 或稳态 telemetry，不能据此宣称合法路径吞吐、p95/p99、CPU/RSS 或生产恢复时间改善。
