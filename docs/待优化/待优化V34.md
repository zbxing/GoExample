## 3. V34-01 实施设计

### 3.1 暂存与格式化协议

1. 新增独立可测试的 `scripts/lib/sdk-generation.mjs`，接收生成源码、staging root 与 formatter 回调。
2. helper 先创建 staging root，再以 `mkdtempSync()` 创建每次调用唯一的子目录；未格式化源码只写入其中的 `client.gen.go`。
3. formatter 仅接收 staged client 路径；成功返回后读取完整 UTF-8 字节。
4. `finally` 删除本次唯一目录；若 formatter/读取失败，canonical client 与 `VERSION` 尚未触碰。
5. cleanup 失败不得被静默吞掉；若已有主错误则保留主错误，避免清理异常掩盖根因。

### 3.2 发布、失败与并发边界

- `publishGeneratedGoSDKSync()` 在发布前快照已有 client 与 `VERSION` 精确字节。
- 两个目标分别通过 `writeFileAtomicallySync()` 发布；单文件 reader 只观察完整旧版或完整新版。
- 任一步同步发布失败时，按相反顺序尽力恢复发布前快照；若回滚也失败，使用 `AggregateError` 同时保留原始发布错误和恢复错误。
- 原目标不存在时，回滚删除本次新建目标；常规仓库路径的 client 与 `VERSION` 均应已存在。
- staging 唯一路径消除 check/check 和 check/generate 的临时文件碰撞，但两个 canonical rename 不是事务；并发 reader、进程终止、系统崩溃、断电、父目录未 fsync 和网络文件系统仍不在声明范围内。

### 3.3 CLI 接入与兼容

- `go-sdk.mjs` 保留 CLI 参数、项目选择、远端契约解析、生成模板和 `gofmt` 搜索顺序。
- check/generate 先调用共享 staging helper，获得完整格式化源码；不再声明或创建 `.temp/sdk-check/<project>`。
- check 直接以格式化字符串比较现有 canonical client，并继续核对 `VERSION`。
- generate 调用双文件发布 helper；控制台输出、相对路径、operation 数量和退出语义保持兼容。
- 两个 workspace 项目生成后字节必须与提交前完全一致，避免将发布时序修复混入代码生成漂移。

### 3.4 测试与证据

- 新增 5 项 helper 行为测试：格式化成功与 cleanup、formatter 失败保留 canonical 文件、连续调用使用不同 staging 目录、完整双文件发布、第二步失败恢复旧 client/version。
- 静态守卫锁定 helper import、staging 调用、共享原子 publisher、移除 canonical `gofmt` 和固定 sdk-check 路径，并保留 V26 至 V33 历史评分和边界断言。
- `docs/待优化/待优化V34.md`、`scripts/lib/sdk-generation.mjs`、`__test__/node/sdk-generation.test.mjs` 加入 evidence input contract，输入由 286 增至 289。
- Node 主阶段目标由 174 增至 179；release 阶段保持 1，API compatibility 预期保持 356 symbols。
