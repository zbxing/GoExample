## 2. 本轮复评发现

### 2.1 可执行缺口

`natsjetstream.Adapter.ReceiveDelivery` 在每次 pull 前后检查调用方 context，但向 nats.go `Consumer.Next` 只传 `FetchMaxWait`。一次空队列 pull 已经在途时，父 context 取消不能直接终止 SDK Fetch；worker 停机可能等待完整 `FetchMaxWait`，其配置上限为 30 秒，SDK 本地兜底还可额外保留约一秒。

nats.go v1.53.1 提供官方 `FetchContext`，但明确禁止和 `FetchMaxWait` 同时使用。adapter 应为每次 pull 创建继承父 context 且以自身 `FetchMaxWait` 为 deadline 的子 context，只传 `FetchContext`，从而同时保留 bounded pull 与在途取消传播。

### 2.2 必须共同修复的边界

- 每次 pull 使用 `context.WithTimeout(parent, adapter.fetchMaxWait)`，只传一个 `jetstream.FetchContext` option，返回后立即 cancel。
- 父 `context.Canceled`/`context.DeadlineExceeded` 优先返回；内部单次 deadline、`jetstream.ErrNoMessages` 与 `nats.ErrTimeout` 继续下一轮。
- 其他 consumer/SDK/backend 错误继续折叠为固定低敏 `ErrReceive`，不暴露 consumer、stream、subject、URL、credential 或 backend 原文。
- 正常消息、invalid-message quarantine、ack、lease extension、DLQ、重投和全部 preflight 行为保持不变。
- 不新增 adapter-owned goroutine、锁、共享状态、后台轮询、控制面写入或公共配置。
- 单元测试固定 option 使用、父取消优先级、内部 deadline 轮询、消息与错误兼容；benchmark 记录快速消息路径的短生命周期 context/timer 成本。
- 真实 file-backed NATS 先证明空 pull 已进入 server waiting，再取消父 context，并在远短于长 fetch 上限的阈值内返回 `context.Canceled`。
- delivery evidence 升级 schema 14；目标生产 shutdown SLO、broker waiting 治理与容量继续 `not_recorded`。

### 2.3 性能与恢复边界

V67 每次 pull 新增一个 O(1) child context/deadline，并在请求返回后立即释放；不新增网络往返、payload/header copy、adapter goroutine 或锁。它降低空队列停机的最坏等待尾部，但会增加一个短生命周期 context/timer，必须记录 benchmark，不能宣称零开销或吞吐提升。

nats.go 会从 context deadline 派生略短的服务端 expires，以保留 10%、最多一秒的客户端收尾缓冲。这仍满足 `FetchMaxWait` 的最大等待语义；既有 `MaxRequestExpires >= FetchMaxWait` preflight 保持保守。真实生产 shutdown、CPU/RSS、吞吐、p95/p99 与 waiting request 清理由目标环境验证，本地结果不得外推。
