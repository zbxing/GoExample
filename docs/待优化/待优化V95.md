V94-01 已完成，剩余 V94-02/V94-03 只依赖真实 edge、DNS、证书、HTTP/2/3、正式 IdP/MFA、生产 Redis/PostgreSQL/NATS、KMS/SIEM、跨主机恢复、目标容量、远端制品和组织审批。全面复评发现一项新的仓库内可验证优化：DLQ 去重 ID 生成仍有可移除的临时哈希/编码分配。因此本轮执行分支 B：覆盖架构与性能评估、生成 V95，并立即实施 V95-01。

评分沿用 20 个非前端维度，权重直接合计 100%，综合分为 `sum(维度分 x 权重)`。V94 基线为 `9.924300/10`；V95-01 完成为 `9.924925/10`。

## 2. 全面复评发现

1. `Framework/queueclient/natsjetstream.deadLetterID` 原实现通过 `sha256.New`、多次 `Write`、`digest.Sum`、`hex.EncodeToString` 和字符串拼接生成稳定 ID。
2. 当前 DLQ 元数据已经在调用方完成非空 stream、sequence 等校验；ID 的字节合同是 `stream + NUL + consumer + NUL + decimal sequence` 的 SHA-256，再加固定前缀。
3. 该路径每次调用基线约为 `240 B/op、4 allocs/op`，属于仓库内可确定复现的重试/DLQ 热路径，不依赖真实 broker 或硬件。
4. V95-02/V95-03 仍是不可替代外部事项，不能由本地 fixture、loopback、miniredis 或文档声明关闭。

## 4. V95-01 实施约束与非目标

1. 不新增公开 API、配置、schema、operation、API version 或 release tag；只改变内部 ID 生成的中间存储与编码方式。
2. 常见元数据使用 256 字节栈缓冲构造完全相同的哈希输入；超出缓冲时允许 append 回退，不新增长度限制。
3. 摘要使用标准 SHA-256，十六进制输出仍为 64 个小写 ASCII 字节，最终 ID 仍以 `goexample-dlq-` 开头。
4. 不改变 DLQ 消息复制、控制 header 过滤、发布确认、source ack、幂等语义、错误 sentinel、超时或并发上限。
5. 不把本地 benchmark 宣称为生产吞吐、p95/p99、RSS、GC、HA 或容量证据；不修改、构建、测试或计分 `MSFront`。

## 6. 架构、性能、内存与并发评估

DLQ 流程仍由 `deadLetter`/`quarantineInvalidMessage` 先复制 body/header，再发布并在确认后 source ack。V95 仅将 ID 哈希输入移到栈缓冲，最终返回值保留一次结果分配；常见路径从历史 `240 B/op、4 allocs/op` 降至约 `80 B/op、1 allocs/op`。当前 Windows/amd64、Intel i5-10400、Go 1.27.1 下五轮结果均一致。超长元数据回退到动态 append，保持无限制的既有行为。发布调用、ack 顺序、重试与并发语义不变。

## 7. 安全、可靠性、数据与消息评估

ID 仍由 broker stream、consumer 与 sequence 的固定组合生成，不引入可预测的外部状态或新密钥；十六进制编码和前缀保持可审计。DLQ 控制 header 过滤、发布确认后 ack、幂等消息 ID 与错误折叠逻辑不变。真实 HA、恢复、RPO/RTO、KMS/SIEM、正式身份和 exactly-once 仍为 `not_recorded`。
