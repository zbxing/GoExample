## 2. 复评发现

`Framework/auth` 已对 OIDC discovery 的认证方法做 fail-closed 协商，但 discovery 和 token response 仍直接使用 `encoding/json.Unmarshal`。Go 默认允许 JSON object 重复 key，后值覆盖前值；这会使 `issuer`、endpoint、认证方法或 token 字段在代理/上游异常时产生歧义。该缺口可在仓库内由有界 HTTP fixture、负向测试和固定 evidence 完整闭环，不依赖真实硬件或外部基础设施。

不选择 `client_secret_post`、JWT/mTLS、动态注册、生产 IdP/MFA/KMS/SIEM、容量、跨主机恢复或组织演练，因为这些需要仓库外的密钥、目标系统、批准值或不可变生产证据。

## 4. V70-01 实施要求

1. 在 `Framework/auth/oidc_client.go` 增加内部 bounded JSON scanner；递归处理 object/array，使用解码后的 key 比较并拒绝大小写折叠重复项，避免 `encoding/json` 字段匹配造成覆盖。
2. scanner 必须拒绝 malformed JSON、多个顶层值和错误结构；scanner 错误只映射到既有 `ErrOIDCProviderUnavailable` 或 `ErrOIDCTokenExchange`，不泄露 provider body、字段名、client ID 或 secret。
3. 保持 discovery/token body 64 KiB 上限、timeout、禁止 redirect、既有字段校验、未知字段兼容、token/callback 绑定和公开 API 不变。
4. 在现有固定 OIDC evidence 测试中加入 discovery/token duplicate key 负向矩阵，至少覆盖 exact、`issuer` 等转义 key、大小写折叠 key、嵌套 object 和多个顶层值。
5. 更新 `Framework/README.md`、`Framework/CHANGELOG.md`、`Framework/COMPATIBILITY.md`、`docs/security/server-threat-model.md`、Node static guards 与 aggregate evidence 输入；OIDC browser evidence schema 3 保持不变并重新生成 checksum-bound artifact。

## 6. 性能与非目标

scanner 只运行在一次 discovery 和一次 token response 的有界 JSON 上，不进入普通 API、SQL、queue、Redis 或 telemetry 热路径；不新增 goroutine、timer、锁、网络往返或后台状态。该优化证明仓库内 OIDC 解析确定性和 fail-closed 语义，不证明真实 IdP、代理、DNS、CA、生产吞吐、长稳、跨主机恢复或 exactly-once。

本轮不实现其它 token endpoint 认证方法、不新增公开 metadata 字段、不修改业务 operation/配置/部署拓扑、不修改、构建、运行或计分 `MSFront`。
