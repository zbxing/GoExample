## 2. 复评发现

Redis browser-session 整 subject 撤销已经由单次 Lua 完成，但 `deleteBrowserSessionsForSubjectScript` 在无基数上限的情况下执行 `ZRANGE 0 -1`；metadata 中的 session-ID 只验证长度，且没有核对 public-ID 的反向 `owner:token` mapping。异常状态可能扩大同步 Lua 工作量，或让篡改后的 metadata 删除错误 ID mapping。

该缺口位于 `Framework/sharedstate`，无需真实硬件、生产 Redis 或外部批准即可关闭。现有两段循环允许先验证全部成员再统一删除；第一段保存已验证 session-ID 后，可用反向 mapping `GET` 替代第二段重复 metadata `GET`，不增加正常路径每个 session 的读取次数。

## 4. V74-01 实施约束

1. 在 `ZREMRANGEBYSCORE` 和 `ZRANGE` 前校验 subject/maximum，并通过 `ZCARD` 拒绝超过 `maxBrowserSessionInventory` 的索引。
2. token、owner、subject 和 session-ID 在派生 Redis key 前必须通过 64 字符小写 SHA-256 hex 校验。
3. 每个 `metadata:<token> = owner:sessionID` 必须对应 `id:<sessionID> = owner:token`；任一缺失或不一致时返回固定 invalid，且不删除 active session。
4. 第一段校验时保存 session-ID，第二段仅使用已验证数据删除 payload、ID/metadata mapping 和 global/subject zset，不重复读取 metadata。
5. 保持单次 Lua、O(N) 且 `N <= 10000`；不新增 goroutine、锁、后台状态、公开 API、配置键或 schema。
6. 本地测试只证明 adapter 的有界性、原子性和 fail-closed 行为，不证明生产 Redis latency、throughput、HA、TLS/ACL、capacity、eviction 或 recovery。

## 6. 本轮已实施优化

V74-01 已完成。`deleteBrowserSessionsForSubjectScript` 现在先验证 subject 与 maximum，并在任何 expiry cleanup 或 `ZRANGE` 前用 `ZCARD` 拒绝超过 10,000 个成员的 subject 索引。第一段循环严格验证 token、metadata owner、session-ID 和 `id:<sessionID> -> owner:token` 反向映射，将已验证 session-ID 缓存在 Lua table；只有全部成员通过后，第二段才删除 payload、双向映射与索引。

新增并通过：

- `TestRedisBrowserSessionRevokeAllUsesOneBoundedAtomicScriptCommand`
- `TestRedisBrowserSessionRevokeAllValidatesEveryMappingBeforeDelete`
- `TestRedisBrowserSessionRevokeAllRejectsOversizedIndexBeforeCleanup`

成功路径预热后仅产生一个 `redis.evalsha` span；malformed session-ID、metadata 缺失、反向映射缺失/不一致和跨 subject 指向均 fail closed，且两个有效 payload 与 subject 索引保持不变。超过 10,000 个成员的索引会在过期成员清理前被拒绝。公开 API、OpenAPI、SDK、配置和持久化 schema 均未改变。

本轮 `yarn vuln:server` 已执行，但受网络策略限制，无法访问 `https://vuln.go.dev/index/modules.json.gz`，因此没有取得 V74 的新漏洞扫描结论，也不记为通过。历史漏洞结果不替代本轮扫描。
