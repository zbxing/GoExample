## 4. V109-01 实施约束与验收

- 对 `len(headers) > 1 && len(headers) <= len(jetStreamControlHeaders)` 的输入先扫描控制名；全部为控制 header 时直接 defensive clone body 并返回 `nil` application headers。
- 控制 header 的 value cardinality 继续按既有过滤合同处理；混合应用 header 仍执行原有单值校验，多值应用 header 仍返回 `ErrInvalidMessage`。
- 不改变公开 API、消息协议、trace extraction、publish confirmation、ack/DLQ settlement、lease extension、consumer preflight、错误 sentinel 或 application header 字节。
- 必须通过定向 natsjetstream 测试、benchmark、`go test -race ./Framework/...`、`yarn test:server`、`yarn vet:server`、Node 守卫、API/项目/SDK 契约、evidence manifest/verify、`gofmt`、`git diff --check`、Graphify update 和 MSFront 差异检查。
- benchmark 只作为仓库内相对分配证据，不声明生产吞吐、尾延迟、HA、RPO/RTO 或 exactly-once。

## 5. 性能、安全与一致性评估

小批量全控制 header 现在只保留 body clone 分配；普通/混合 header 仍复制到独立 map，避免 broker buffer 或调用方数据被修改。该分支不增加 goroutine、锁、网络往返或无界状态。

控制 header 识别仍大小写不敏感，应用 header 不会误判为控制字段；多值应用 header 仍 fail closed。DLQ、ack、lease、retry 和 worker settlement 顺序完全不变。

本轮 Windows/amd64 单次 benchmark：`control-batch` 为 137.5 ns/op、8 B/op、1 alloc/op，legacy 为 179.8 ns/op、56 B/op、2 allocs/op；该结果只用于本地相对分配/耗时对照，不能外推生产 RPS、p95/p99、RSS、GC、网络容量、HA、RPO/RTO 或 exactly-once。
