## 2. 复评发现

1. `OIDCClient` 和 `JWKSVerifier` 允许注入任意标准 `*http.Client`，身份模块不能依赖调用方一定使用 V83 已加固的 `httpclient.New` transport 链。
2. OIDC discovery/token exchange 在 `Do`、body read 和 parse 的结果边界没有拒绝 caller cancellation 或已经到达的 deadline；忽略 context 的 transport/body 可使迟到有效响应被接受。
3. JWKS cached-key 验证路径没有 completed-context 检查，已取消请求仍可能完成 RSA/JWT 验证并返回 claims。
4. JWKS refresh 使用不可取消的 `sync.Mutex.Lock`。短 deadline 调用方可能在另一刷新后面等待到自身预算之外，再使用新 cache 或继续刷新。
5. JWKS refresh 在共享 key map/`refreshedAt` 发布前没有完成态检查，过预算有效响应仍可修改后续请求使用的认证状态。
6. 这些缺口可用私有 helper、context-aware refresh gate、自定义 RoundTripper/body 和确定性并发测试完整闭环，不依赖真实 IdP、网络或设备。

## 4. V84-01 实施约束与非目标

1. 不新增公开 API、配置、环境变量、schema、网络往返、后台 goroutine 或跨请求 timer。
2. helper 同时检查 `ctx.Err()` 与已经到达的 deadline；live 快路径保持 `0 allocs/op`。
3. OIDC discovery/token 和 JWKS refresh 在 transport、body read、parse/validation 后都必须经过 caller completion boundary；已取得的迟到 body exactly-once close。
4. cached JWKS verification 必须在解析前后拒绝 completed context；拒绝结果继续是 `ErrInvalidToken`，不暴露 context 原文。
5. refresh gate 维持 single-flight；等待者按自己的 context 退出，取消者不能把另一调用方的新 cache 当作自身成功。
6. 只有在调用方仍有效时才发布 JWKS keys 与 refresh time；不回滚其它 live 调用方已经合法发布的 cache。
7. 保持 HTTPS/loopback、redirect、HTTP/body limits、OIDC/JWT/RSA/ACR/AMR、refresh interval、unknown-key throttle 和 token 字段语义。
8. 不声称取消能撤销 IdP 已接收的请求，不声称本地 transport/httptest 等同正式 IdP、真实网络、生产容量或生产可用性。
9. 不修改、构建、测试或计分 `MSFront`。
