# GoExample 待优化清单（V12）

评估日期：2026-08-24  
范围：根工作区、Framework、Proj/Example、Go 服务、协议、测试、CI、供应链、观测和部署；明确排除 `MSFront`。  
当前精确综合评分：**9.451/10**；目标：**10.0/10**。

## 1. 本轮结论

V11 的受保护 typed query 和 JSON command 已完成。认证、角色授权、媒体类型、幂等、body bind/validation 和 application handler 的顺序已经固定，拒绝请求不会污染幂等状态、绑定请求体或创建 application span。Example `preview` 与 `describe` 只使用最小 principal，并由 OpenAPI、审计、AST 和行为测试锁定。

本轮新增 `Framework/httpapi.NewHTTPHandler`。它将已组装的 Fiber app 暴露为标准库 `net/http.Handler`，因此标准库 middleware、Nginx/Envoy 边界或其他 HTTP 组合层可以在 Framework 外侧接入。随后新增 `ApplicationCommand.WithMethod`，默认 POST 不变，PUT/PATCH/DELETE 共享认证、授权、media type、幂等、bind/validation 和错误边界，同路径跨 method 可并存，非法 method 启动期失败。

V12-04 的仓库内基础继续推进：新增 transport-neutral `SecurityAuditRecord` 与可注入 `SecurityAuditSink`，使用默认 100ms context 预算；sink 成功、返回错误、超时和 panic 均有行为测试，失败不会改变 HTTP 结果，错误原文和凭据不会进入日志或指标。`goexample_security_audit_sink_writes_total` 只公开固定 `success/failure`，持续失败有本地 Prometheus 规则和 runbook。仓库内 `HashChainAuditSink` 进一步用有界 NDJSON、严格低敏字段、单调序号和前序 SHA-256 链接提供可验证的 tamper-evident 适配器，并覆盖篡改、非法记录、取消和并发写入；新增 `EncryptedAuditWriter` 以 AES-256-GCM、随机 nonce、显式 key ID 和 keyring 验证覆盖落盘保密与轮换读取，重复 nonce、未知 key、格式错误和密文篡改均失败；任意 writer 仍不会因此自动获得持久性、访问控制、不可变性或生产密钥托管。

V12-09 的仓库内部分继续推进：新增与 OpenAPI `1.0.0` 同版本、覆盖 19 个 operation 的 Go SDK，仓库内结构化生成器会拒绝不支持的 contract shape，并以重新生成、`gofmt` 和逐字节比较阻断漂移。独立 `support/consumer/HealthProbe` 可执行模块通过真实 Framework `net/http.Handler` adapter 验证旧 readiness 别名的弃用头与 successor link，再证明迁移后只访问 `/readyz`；消费者/版本/责任边界已形成矩阵。该证据不代表 SDK 已发布 tag，也不代表外部生产消费者完成部署迁移。

V12-06 的仓库内数据库基础继续推进：新增不绑定 driver 的 `Framework/sqlclient`，统一有限 operation/transaction timeout、`database/sql` pool/lifetime/idle 上限、显式 health check、query/scan/lock helper、事务 commit/rollback 所有权和幂等关闭。固定 PostgreSQL `CLIENT` span 只记录 system、operation 与结果类别，不记录 DSN、SQL、参数、行值或原始 driver error；标准库假 driver 行为测试覆盖成功、`sql.ErrNoRows`、超时、取消、rows 清理以及 callback/consumer panic。Framework API snapshot 现为 112 个符号。该证据不代表真实 PostgreSQL driver/业务消费者、队列 instrumentation、故障恢复、备份/PITR 或目标数据量测试完成。

V12-06 的仓库内队列基础继续推进：新增 broker-neutral `Framework/queueclient`，为 Kafka、NATS、RabbitMQ、AWS SQS 和 GCP Pub/Sub 固定 system 提供有限 publish/process timeout、message/header 上限、输入克隆和 W3C Trace Context 注入/提取。固定 `PRODUCER`/`CONSUMER` span 不记录 destination、body、header、message ID 或原始 backend error；行为测试覆盖远端 parent、仅 Trace Context 而非 baggage、超时、取消、失败、panic、header 注入后再次执行上限检查以及调用方输入不被改写，三类运行时校验错误可用 `errors.Is` 稳定分类。Framework API snapshot 在该阶段更新为 127 个符号。该证据不代表生产 publisher/consumer、ack/retry/DLQ、顺序/去重/exactly-once 或故障恢复完成。

本轮继续收口 V12-05 的标准 server 生命周期：新增 `server.RunHTTP`，直接拥有标准 `http.Handler` listener，并固定 accepted connection/read-header/read/write/idle/header 上限、监听前失败、draining 传播延迟、共享 shutdown deadline 和超时强制关闭。可选 `ApplicationShutdown` 与标准 `http.Server.Shutdown` 并发共享同一预算，hook 即使无视 context 也不能阻塞 server 返回；Example 默认组合改为 `NewHTTPHandler + RunHTTP`，注入 `app.ShutdownWithContext` 以取消 Framework application work，旧 Fiber `server.Run` 保持兼容。真实 TCP、连接容量、慢 header、阻塞 handler、阻塞 hook、配置与监听失败测试均已通过，API snapshot 更新为 238 个符号。Fiber adaptor 仍不传播 `http.Request.Context()` 取消，且没有目标 TLS/HTTP2/3 edge 证据，因此只将标准生态与可替换性保守升至 9.0，精确综合评分升至 9.292。

随后继续补齐 V12-05 的标准 server 连接观测：新增最小 `HTTPConnectionObserver`，只接收配置容量和固定 `net/http` 状态，observer panic 被隔离且不改变请求、监听或停机结果。`observability.Metrics` 实现容量与当前打开连接 gauge，以及 `new/active/idle/hijacked/closed/_OTHER` 固定事件 counter；重复关闭不会让 gauge 变负，非法容量折叠为零，地址、连接 ID 和错误文本均不成为标签。Example 默认注入同一 Metrics；Prometheus 记录连接利用率并对持续 10 分钟超过 90% 告警，runbook 区分高连接/低请求的慢或空闲客户端。真实 listener、panic、固定标签、Node 守卫和 API snapshot（241 个符号）均已同步。该证据不代表目标 Prometheus/APM、edge 或 paging 已部署，标准生态与可替换性保守升至 9.1，精确综合评分升至 9.297。

V12-06 的事务冲突边界继续推进：`Framework/sqlclient.RetryTransaction` 显式重试错误链中实现 `SQLState() string` 的 `40001`/`40P01`，默认 3 次、硬上限 10 次，有限指数抖动退避与所有 attempt 共享同一 transaction timeout；非重试错误、尝试耗尽、总 deadline 和不安全 rollback 都会停止。假 driver 测试覆盖 callback 与 commit 阶段冲突、rollback/commit 次数、错误包装和 span 隐私，并将测试数据库标识改为原子递增，消除 Windows 时间戳碰撞。Framework API snapshot 在该阶段为 128 个符号。callback 必须可安全重放，该证据不代表真实 PostgreSQL 锁竞争、driver SQLSTATE 映射或生产副作用具备 exactly-once。

V12-08 的仓库内编排基础继续推进：新增结构化 Kubernetes `List` 模板和严格渲染器，固定 3 副本、零不可用滚动更新、startup/readiness/liveness、资源 request/limit、nonroot/read-only/seccomp、hostname/zone topology spread、PDB、HPA、tokenless ServiceAccount、ClusterIP Service 和仅入站 NetworkPolicy。模板不提交 Secret 或伪造镜像摘要；渲染只接受真实 `@sha256` 镜像引用与精确 HTTPS Origin，并只写 `.temp/deployment`。行为测试覆盖成功渲染、占位符清除、可变 tag、HTTP Origin 和弱化 PDB 拒绝。

V12-08 的发布供应链基础继续推进：新增精确 Go 1.25.13 的 CGO-free Linux/amd64 服务 release 生成器，固定 `-trimpath`、关闭自动 VCS 嵌入，并输出受限 ELF、结构化 manifest 和仅含一个 subject 的 SHA256SUMS；行为测试实际篡改 binary、checksum 与 manifest，校验器均失败。默认分支新增独立 provenance job，在 clean source 上构建并校验后使用固定 commit 的 GitHub attestation action 生成 Sigstore/SLSA build provenance，再以 `gh attestation verify` 复核；成功或失败均归档 bundle、URL、原始验证输出、状态和 evidence manifest。Windows 工具链引导同时修复 PowerShell 解压参数，并只接受 `go.work` 精确 patch 版本、复用已校验官方归档。本机已生成并验证本地 release，但本地 checksum 不是签名，且没有远端成功 run，因此 `signedRelease` 仍为 `not_recorded`。

V12-06 的真实 PostgreSQL 测试入口继续推进：Framework 测试依赖固定 pgx v5.7.6；opt-in 行为测试在真实 PostgreSQL 上确定性制造 serializable 并发更新，要求真实 `40001` 触发第二次 callback 并得到最终值 2；两个并发 `RetryTransaction` 再分别锁住不同行并交叉请求，要求真实 `40P01` victim 自动重试、两个事务最终提交、总 callback 次数为 3 且两行结果一致；第三个测试持有 `FOR UPDATE` 行锁，要求 caller deadline 有界失败、释放后重新加锁成功。独立 CI job 使用固定 digest 的 PostgreSQL 16，并在成功或失败时归档原始输出、退出码、runner/commit 元数据和 SHA-256。本机没有 `POSTGRES_TEST_URL`，测试已明确 skip；当前也没有远端 job artifact，因此不宣称真实测试已在本轮执行成功。

V12-06 的乐观并发边界继续推进：`Client.ExecVersioned` 与 `Tx.ExecVersioned` 要求 caller-owned UPDATE 恰好影响一行；调用方负责在谓词中比较预期版本并在同一语句推进版本，零行统一返回固定 `ErrOptimisticConflict`，多行、nil result 或无法读取 `RowsAffected` 均失败。假 driver 行为测试覆盖零/一/多行、影响行数错误、事务回滚及 span 隐私；opt-in 真实 PostgreSQL 测试让两个 writer 使用相同版本并发更新，要求恰好一个成功、一个冲突且持久化版本只增加一次。固定 runner 会自动执行该测试，但本机未设置 `POSTGRES_TEST_URL` 且无远端成功 artifact；数据库层也不冒充 HTTP `ETag`/`If-Match` 映射已经完成。

V12-06 的 HTTP 乐观并发边界继续推进：新增 unauthenticated/authenticated/authorized 三种 versioned JSON command adapter；认证与授权先于强 `If-Match`，缺失、弱标签、通配符、列表和非法 token 分别形成固定 428/400，应用映射的持久化冲突形成固定 412，成功响应验证并保留新的强 `ETag`。`If-Match` 只对 versioned command 进入幂等指纹，同 key/同版本回放保留 ETag/禁缓存头，同 key/不同版本返回指纹冲突；普通 command 指纹不变。读侧再新增 unauthenticated/authenticated/authorized 三种 versioned query：handler 返回受限未加引号 tag，Framework 输出强 `ETag`，GET 对强/弱/list/通配符 `If-None-Match` 做弱比较，命中时返回保留 tag 的空体 304；认证/授权仍先于绑定与 handler，非法响应 tag 固定脱敏为 500。Go 行为测试锁定顺序、body/idempotency 不污染、非法响应 tag、回放、条件读取和错误脱敏；真实 PostgreSQL opt-in 测试进一步组合初始 GET、HTTP PATCH、`ExecVersioned`、新 ETag、过期版本 412、条件 GET 304 及最终数据不被覆盖。Framework API snapshot 现为 172 个符号。当前公共 OpenAPI 仍为 19 个 operation，没有新增虚构 Example mutation，生产业务接入与远端成功 artifact 仍未完成。

V12-06 的仓库内 PostgreSQL 恢复基础继续推进：`yarn postgres:recovery:contract` 在 Linux Docker 中启动固定 digest 的 PostgreSQL 16，执行真实 SQLSTATE/锁测试后建立 1000 行确定性恢复点，生成 custom-format 逻辑备份，再向源库追加一行并恢复到隔离数据库。独立报告器要求恢复库行数与 SHA-256 摘要精确匹配恢复点、排除备份后的写入，并复核备份大小/哈希、LSN 和两分钟总预算；正负向 Node 测试拒绝行数/摘要漂移、恢复点污染、超时和备份篡改。CI 始终归档 backup/raw/report/status/container log/SHA256SUMS/manifest，只有远端 Linux 双状态成功且制品齐全时 `postgresRecovery` 才可记录完成。该单节点逻辑恢复不等于物理备份、WAL/PITR、复制/failover、目标数据量、RPO/RTO 或操作响应。

V12-03 的 OIDC/JWKS 资源服务器基础继续推进：Framework 新增通用 `auth.TokenVerifier` 和 RS256 `JWKSVerifier`，把 Bearer 验证与 demo 密码登录/HS256 签发解耦。verifier 固定 issuer/audience，要求 `exp`/`nbf`/`iat`/`jti` 及既有低敏身份/角色 claims，限制 RSA 2048-8192 位、token 16 KiB、JWKS 1 MiB/100 keys、HTTP/刷新/token age 预算；启动同步拉取、过期缓存刷新失败关闭、未知 `kid` 5 秒节流和并发刷新合并均有行为测试。Example 的 demo/OIDC 模式互斥，生产 HTTPS 配置、监听前失败退出、固定 `auth_mode` 日志和真实 composition route 已验证；OIDC 模式不会注册本地 `/auth/login`。Framework API snapshot 现为 138 个符号。该本地能力不代表 Authorization Code + PKCE、state/nonce、refresh rotation/reuse detection、MFA、集中 revoke、KMS/Vault 或目标 IdP 已部署。

V12-03 的仓库内会话治理基础继续推进：新增 transport-neutral `auth.SessionManager` 与可注入 `auth.SessionStore`，以 `SessionConfig` 固定 refresh TTL、absolute TTL 和最大 family 数量；无 Store 时 `Start`/`Rotate` 只返回一次原始 token，内部仅保存 SHA-256 hash。新增 `sharedstate.Redis` 实现，使用 namespace-scoped hash-only 索引和 Lua 原子 create/rotation/reuse/revoke，跨 client 的 rotation 线性化，user/family revoke 与 active-family 查询共享同一状态，Redis 错误 fail closed，不回退到本地状态。rotation 保留旧 hash，重放会返回固定 reuse 错误并撤销整个 family；每个 family 的历史 hash 另有固定上限，避免长寿命 family 无限增长。Go 正负向、并发、过期、输入、跨实例、集中撤销、family limit、后端停止和 Node 静态守卫均已通过；Framework API snapshot 现为 205 个符号。该仓库内 Redis/miniredis 证据不代表生产 Redis HA、Sentinel/Cluster、TLS/ACL、容量/RPO/RTO、Authorization Code + PKCE、state/nonce、MFA、KMS/Vault、目标 IdP 或生产会话平台已完成。
本轮继续完成 V12-03 的仓库内授权请求契约：新增 `auth.AuthorizationRequestManager`，仅接受 HTTPS authorization/redirect endpoint，生成随机 `state`、`nonce` 与 S256 PKCE `code_verifier`/`code_challenge`，固定 `response_type=code`，并以最多 15 分钟 TTL、最多 10000 个 pending state、最多 32 个 scope 和 8 KiB authorization code 限制资源消耗。callback `Complete` 会一次性删除 state，过期、重复、格式错误和超限输入 fail closed；`ValidateAuthorizationNonce` 使用 constant-time 比较。Go 行为测试、Node 静态守卫、API snapshot 和 evidence inputs 已同步。该组件只构造和消费仓库内进程状态，不执行 discovery、token exchange、MFA 或持久化跨副本 state，因此不能作为目标 IdP、完整登录流程或生产 OIDC 部署证据。
随后补齐 V12-03 的仓库内 ID token claims 契约：`JWKSVerifier.VerifyIDToken` 复用 RS256/JWKS、issuer/audience、签名 key rotation、token size 和最大 age 边界，额外要求非空 `sub`/`nonce`、与授权请求 nonce 的 constant-time 匹配；多 audience 必须提供匹配 `azp`，可选 `auth_time` 也必须在有界时间窗口内。Go 正负向测试、API snapshot（205 个符号）、Node 静态守卫、README/CHANGELOG 和 evidence 边界均已同步。该方法只验证已由调用方取得的 ID token，不执行 token exchange、discovery、MFA、profile 映射或生产 IdP 部署。

本轮继续完成 V12-03 的仓库内 discovery/token exchange 契约：新增 `auth.NewOIDCClient`，在构造时获取 `/.well-known/openid-configuration`，要求精确 issuer、JSON 响应、`code`/`S256` 能力和无凭据/无 query/fragment 的 authorization、token、JWKS endpoint；discovery 与 exchange 均禁止重定向，metadata/token 响应分别限制为 64 KiB，HTTP timeout 不超过 10 秒。`ExchangeCode` 只接受 `AuthorizationCode` 的 bounded code/verifier/nonce，提交固定 authorization_code、redirect URI、client ID 和 PKCE verifier，并验证 Bearer、access token、ID token、expires_in、refresh token 与 scope 边界；调用方仍必须用 `AuthorizationCode.Nonce` 调用 `VerifyIDToken`。Go 正负向测试、API snapshot（214 个符号）、Node 静态守卫、README/CHANGELOG 和 evidence inputs 已同步。loopback HTTP 仅用于测试，生产仍需目标 IdP、HTTPS/CA/egress、MFA、持久 state、KMS/Vault、跨副本撤销和浏览器回调证据。

- HTTP 生命周期有真实 TCP 读写超时、keep-alive、半关闭、drain、shutdown 和连接容量契约。
- OTel、Redis/SQL/queue instrumentation 和 outbound `net/http` client 只记录低敏固定字段，并有边界测试。
- Node 守卫、OpenAPI 兼容比较器、威胁模型、manifest verifier 和恢复 runbook 形成可重复门禁。

### 缺点

- 自定义 middleware、高级 registrar、Storage 和 validator 仍是 Fiber 专用；typed command 的 PUT/PATCH/DELETE 与 query 的 GET/HEAD 已完成，但更广泛的标准方法仍需高级 registrar。
- `RunHTTP` 已让标准 server 拥有默认 listener 生命周期和固定连接观测，`NewHTTPHandler` 也已传播标准请求取消与真实 TCP 断连；原生 Fiber listener 仍依赖 deadline，HTTP/2/3、目标 edge、Prometheus/APM 和 paging 仍缺运行证据。
- 仍只有 Example 一个真实 Framework 服务消费者；Go SDK、仓库内消费者矩阵和本地迁移演练已完成，但没有 SDK release tag、外部消费者或生产迁移记录。
- Go 已有外部 OIDC/JWKS access-token 验证、本地 refresh family/reuse/revoke 基础、Authorization Code + PKCE、hash-keyed 跨副本一次性 state/nonce、有界 discovery/token exchange、可选 ACR/AMR/fresh-auth_time assurance、state-cookie 浏览器 callback、hash-only opaque session/CSRF/logout、每用户限量与仓库内集中撤销、显式设备名称 metadata，以及 Example subject-owned tenant/resource/attribute 策略；仍没有目标 IdP 的实际 MFA enrollment/challenge 与 claim mapping、设备管理 UI/指纹、生产集中撤销证据或生产 policy engine/关系数据/策略分发证明。
- 审计已有可注入、有界且失败隔离的本地 sink 契约，但没有实际不可篡改存储、留存/删除策略、访问控制、SIEM/paging 投递和具名处置责任人。
- SQL/queue adapter、固定 Nginx edge、固定 Redis Sentinel、Linux 容量报告与短时 soak 已有仓库内契约及 CI 入口，但 Redis、collector、目标 PostgreSQL/broker/edge、编排和 Linux benchmark 都没有成功目标环境制品；容量矩阵也尚未覆盖认证失败、依赖延迟、TLS edge、目标 payload、拐点或目标长稳。
