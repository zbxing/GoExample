## 2. 优化原则

1. 先测量、再决定框架。不同框架官方 benchmark 不能作为迁移依据。
2. 隔离业务与 transport，但不创建包含所有框架最小公分母的“万能路由抽象”。
3. 先定义协议、状态和故障语义，再选择 Redis、OpenTelemetry、Kubernetes 等实现。
4. 每项提分必须具备可重复命令、失败门禁和目标环境证据。
5. 10 分代表目标生产环境的持续证明，不代表仓库中配置文件数量。

## 4. P0 实施项

### V9-01 框架选择 ADR 与跨框架 benchmark

状态：**部分完成**。ADR、相同 application service、真实 TCP Fiber/`net/http` 基线、应用侧 TLS/HTTP/1.1 契约、根命令和固定 Linux artifact workflow 已完成；workflow 已覆盖 throughput、p50/p95/p99、错误率、alloc、CPU profile、heap profile 和进程 CPU/RSS。校验失败、认证、模拟 I/O、edge、GC/连接数，以及实际 Linux 原始结果与统计结论仍待补齐。

目标：回答“Fiber 在本项目真实工作负载中是否值得其生态和协议成本”。

实施内容：

- 新增 ADR，记录当前选择、候选框架、业务流量模型、约束、决策阈值和复评日期。
- 至少实现 Fiber 与 Chi/`net/http` 两个 adapter；根据目标场景再加入 Gin、Echo、Hertz。
- 所有候选使用相同 use case、JSON schema、认证判断、日志策略和模拟 I/O。
- 在固定 Linux runner 上通过真实 TCP socket 测试，不使用 `app.Test`/`httptest` 结果代替网络结果。
- 场景至少包含：纯 JSON、校验失败、带认证请求、数据库/RPC 延迟、keep-alive、TLS 或真实 edge、不同并发度。
- 输出 throughput、p50/p95/p99、错误率、CPU、RSS、alloc/op、GC、连接数和取消后的残留任务。
- 使用 benchstat 或等价统计方法，多轮运行并记录硬件、内核、Go 版本、框架版本和完整命令。

建议决策门槛：

- 门槛必须在运行测试前写入 ADR，避免看完结果后移动标准。
- 若 Fiber 在目标流量下没有稳定、显著且业务可感知的 CPU/尾延迟收益，优先 Chi/`net/http`、Gin 或 Echo 的标准生态。
- 若选择 Hertz，必须单独证明其协议/网络扩展价值，而不能只比较 hello-world QPS。

验收标准：

- benchmark 可由一条根命令重复执行，并在非目标平台明确跳过。
- CI 对性能只使用抗抖动的趋势/阈值，不以单轮噪声阻断发布。
- ADR 给出“保留 Fiber”“迁移”或“延后决策”之一，且能追溯到原始数据。
- profile 显示瓶颈确实位于 HTTP/序列化热路径，而不是数据库或日志。

### V9-02 Transport 与 application 边界

状态：**首个业务用例已完成，整体项目边界未完成**。`/api/v1/project` 已经通过 typed application service 和 Fiber adapter 验证，后续仍需迁移其它业务操作并补齐 pooled buffer、异步和授权 principal 的系统性审计。

目标：使业务用例不依赖 `fiber.Ctx`，降低框架锁定和 pooled context 误用风险。

实施内容：

- 为 Example 的业务操作定义 typed command/query、result 和领域错误。
- application use case 只接收 `context.Context` 与 typed input；不得接收 Fiber/Gin/Echo/Hertz context。
- Fiber adapter 负责 path/query/header/cookie 解析、输入复制、调用 use case 和错误到 HTTP 的映射。
- 保留路由器本身的框架特性，不设计一个试图屏蔽所有框架能力的通用 router interface。
- 审计 goroutine、callback、cache 和日志字段，禁止在 handler 返回后保留 Fiber pooled 值的引用。
- 将 auth claim 传递改为显式 application principal 或受控 context value，并提供 typed accessor。

验收标准：

- `Proj/Example` 的核心 use case package 不 import `github.com/gofiber/fiber`。
- 同一 use case 可被 Fiber adapter 和 benchmark baseline adapter 调用。
- 新增架构守卫，阻止 Fiber import 进入约定的 application/domain package。
- Fiber handler 返回后修改/复用 request buffer 不会改变已传给异步或下游代码的数据。
- 现有 OpenAPI、授权、错误 envelope 和 E2E 全部保持通过。

### V9-03 断连取消与协议部署契约

状态：**部分完成**。真实 TCP 已验证主动 deadline、server shutdown、客户端断连、应用侧 TLS/HTTP/1.1、请求头读取超时（不完整请求返回 408）、transport 连接并发耗尽返回 503、最小流式响应、API admission 背压，以及 loopback HTTP/2 edge-to-Fiber/HTTP/1.1 upstream 边界；deadline/shutdown 可取消协作式下游，客户端断连不会及时传播。ADR 0002 已将该限制记为框架迁移条件；目标 edge、HTTP/3、传输级慢响应背压和可控断连补偿仍未完成。

目标：明确 Fiber/fasthttp、edge proxy 和下游 context 的真实生命周期。

实施内容：

- 使用真实 listener/socket 构造客户端发送后断开、取消上传、慢读响应和 server shutdown 场景。
- 记录主动 request deadline、客户端断连、edge timeout、server shutdown 分别如何传递到 DB/RPC。
- 若 fasthttp 无法提供所需断连取消语义，选择可控补偿方案或把该项作为迁移标准。
- 明确 HTTP/2/h2c/HTTP/3 是应用能力还是 edge 能力，记录 TLS 终止、header、buffering、idle timeout 和 drain 配置。
- 为部署契约增加协议握手、取消传播和超时一致性测试。

验收标准：

- 下游阻塞任务在 deadline/shutdown 后的终止时间有明确上限且测试稳定。
- 客户端断连语义有可复现实验；若不支持，文档明确风险与适用边界，不能标记为已解决。
- HTTP/2 生产路径至少在 edge-to-client 或 app listener 一侧有自动握手测试。
- 代理与应用 timeout 满足外层预算大于内层预算，避免无序 502/504 和残留工作。

### V9-04 共享 limiter、idempotency 与 session 状态

状态：**部分完成**。已实现 Framework `Storage`/`Locker` 注入、用途/路由 key namespace、TTL/context 契约替身测试、production external 模式 fail-fast 和显式内存降级开关。仍无 Redis/等价实现；Fiber limiter 的 Storage 接口是读改写模型，当前没有跨实例原子计数证明；session/revocation 尚未接入。

目标：使多实例扩容不改变配额、幂等和撤销语义。

实施内容：

- 先定义 store 接口的原子操作、TTL、key scope、时钟、容量、故障模式和数据分类。
- limiter 使用原子计数/窗口算法，明确用户/IP/租户维度和可信代理边界。
- idempotency 原子声明 key，绑定 method/path/principal/body hash，区分 in-progress、completed、failed 状态。
- session/revocation 支持集中撤销和短 TTL 缓存，不依赖单节点内存。
- 提供 Redis 或等价共享实现及内存测试实现；禁止把内存实现误用于多实例 production。
- 明确共享设施不可用时 fail-open/fail-closed 策略、timeout 和指标。

验收标准：

- 两个服务实例并发接收同一 key 时只能执行一次受保护副作用。
- 跨实例 rate limit 不可通过轮询节点绕过。
- Redis 超时、重连、主从切换和 key eviction 有故障测试。
- production 多实例配置在共享 store 缺失时启动失败，或有经过批准的显式降级策略。

### V9-05 OpenTelemetry 与 SLO 闭环

状态：**部分完成**。W3C trace context、服务端 span 标识、trace/log 关联、低基数 metrics 约束和可执行 SLO/alert rules 已有本地代码测试与 Node 静态守卫；OTel SDK/exporter、collector、Prometheus/Alertmanager `promtool` 校验、dashboard 和受控告警演练仍未完成。

目标：让性能、错误和依赖故障可定位、可告警、可关联。

实施内容：

- 接入 W3C Trace Context、OTel server span、outbound HTTP/RPC、database 和关键 use case span。（当前完成 W3C header/context/server span 标识，OTel SDK 仍待接入。）
- 对 Fiber 使用维护状态明确的 instrumentation；若需自研，必须覆盖 route template、status、panic 和 context propagation。
- OTLP exporter 使用有界 queue、timeout、batch、sampling 和失败指标，不能阻塞请求主路径。
- 日志加入 trace/span ID；metrics 使用低基数 service/route/status 属性。
- 定义 availability、latency、error、saturation SLI 和可执行 SLO。
- 提供 recording rules、dashboard、burn-rate alerts 和告警演练。（当前已提供 recording rules 和 burn-rate alert 定义，dashboard、Prometheus/Alertmanager 运行验证及演练待完成。）

验收标准：

- 一次 MSFront -> Go -> database/outbound 请求能在 trace 中串联，日志可按 trace ID 查询。
- exporter 不可用不会拖垮 API，丢弃/重试有指标且内存有上限。
- metric 与 trace 属性通过基数测试，不包含用户 ID、原始 URL 或敏感 token。
- SLO 告警能由受控故障触发并通过 runbook 完成处置。

## 8. 框架决策后的分支

### 分支 A：保留 Fiber

- ADR 必须记录真实收益和已接受的 fasthttp 限制。
- Fiber adapter、pooled value 复制规则、断连取消边界和 OTel instrumentation 归 Framework 所有。
- edge 承担的 HTTP/2/3、TLS 和 buffering 必须成为可测试部署契约。

### 分支 B：迁移到标准 `net/http` 生态

- 根据功能密度选择 Chi、Gin、Echo 或直接 `net/http`，不要只按 benchmark 排名。
- 先迁移 adapter，保持 use case、OpenAPI、错误 envelope 和 E2E 不变。
- 在新旧 transport 上运行同一契约与性能套件，逐步切换，保留明确回退路径。

### 分支 C：评估 Hertz

- 只在高并发、网络层或多协议扩展是核心需求时进入该分支。
- 同样要求 application 边界隔离、context/取消测试、OTel 和共享状态，不因高性能定位免除生产门禁。

## 9. 重新评分规则

- 完成代码但没有自动测试：最多记为“已实现，未验证”。
- 本地测试通过但无目标平台证据：不能拿满部署、性能或恢复分。
- benchmark 只覆盖 hello-world：不能提高运行时性能综合分。
- 只有 Kubernetes YAML、OTel 配置或 Redis 接口：不能提高相应维度到 10 分。
- 生产或等价预发布环境持续运行、门禁失败可复现、演练结果可归档后，才重新计算分数。

达到 10 分至少需要：框架选择有数据、业务与 transport 解耦、协议与断连语义闭环、多实例状态一致、OpenTelemetry/SLO 可运行、正式身份、数据库恢复、目标平台容量、可信发布和第二项目兼容性全部有持续证据。
