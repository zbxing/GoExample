## 2. 本轮复评发现

### 2.1 可执行缺口

`nats.go v1.53.1` 的 `ConsumerConfig` 允许空 filter、一个 `FilterSubject` 或多个 `FilterSubjects`。`Adapter` 自身只绑定一个 literal `Subject`，现有 package preflight 却不知道该值。满足持久性、redelivery、payload 与 lease 要求的宽 filter、错误 filter 或多 filter consumer 仍会通过，随后可能把另一业务 subject 的消息交给当前 handler 并确认或投递到错误 DLQ。

### 2.2 必须共同修复的边界

- 新增 adapter-bound preflight，只检查 adapter 实际持有的 consumer，并复用一次新鲜 `ConsumerInfo`。
- 只接受一个与 adapter literal subject 完全相等的 filter；空、通配、错误、多值或双字段配置全部 fail closed。
- 失败返回固定 `ErrConsumerSubjectMismatch`，支持 `errors.Is`，不暴露 subject、filter、identity、配置值或 backend error。
- 保留既有 package `PreflightConsumer` 签名与行为，避免破坏兼容；文档明确它不证明 adapter subject isolation。
- 单元 fake 与真实 file-backed JetStream 共同验证从宽 filter 拒绝到 exact filter 通过，并证明异 subject 不进入 adapter。
- delivery evidence 升级 schema 6；目标生产 broker、ACL、容量继续 `not_recorded`。

### 2.3 一致性边界

本轮只证明 consumer 与 adapter subject 的一对一精确绑定，不证明 stream subject 集、NATS ACL、跨账户映射、retention、replicas、有限 MaxDeliver 耗尽策略、跨 broker 原子 settlement、ordering、全局去重或 exactly-once。

## 5. 性能与资源边界

V58 只在启动阶段读取 adapter 已有 subject，并在一次新鲜 `ConsumerInfo.Config` 上执行有限次长度和字符串比较。成功路径 O(1)，不增加稳态网络往返、分配、锁、goroutine、buffer、retry 或 telemetry；publish/receive/body copy/handler/ack/DLQ/lease 热路径不变，因此不把本地 wall-clock 波动计为性能收益。

真实 p95/p99、吞吐、CPU、RSS、broker IOPS、积压恢复、容量和跨区延迟仍必须由目标环境测量；不得从 loopback 合同推导。
