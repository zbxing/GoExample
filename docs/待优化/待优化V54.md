## 2. 本轮复评发现

### 2.1 可执行缺口

`queueclient/natsjetstream.Adapter.Publish` 会过滤应用提供的 `Nats-Msg-Id` 等控制头，这是必要的隔离；但 adapter 没有受控的稳定消息 ID 发布入口，需要 JetStream duplicate-window 去重的调用方只能绕开 adapter 或放弃该能力。

`Publisher` 是窄接口，测试替身或错误实现可以返回 `nil`/零值 `PubAck` 且 `err == nil`。当前 adapter 只检查 error，会把没有可验证服务端确认的结果当成成功，与同步 publish ack 契约不一致。

### 2.2 必须共同修复的安全与确认边界

- 应用 `Message.Headers` 中的所有 JetStream 控制头继续被过滤。
- 稳定 ID 只能通过专用方法参数进入 `Nats-Msg-Id`，且 typed ID 最后写入，应用不能覆盖。
- ID 必须为 1..256 bytes 的无空白可打印 ASCII；非法输入在 broker 调用前拒绝。
- PubAck 必须非空、stream 非空且 sequence 非零；duplicate ack 是服务端确认成功。
- 消息 ID、PubAck、stream、sequence、消息和 backend error 不进入 telemetry 或错误文本。

### 2.3 一致性边界

调用方必须为同一逻辑事件选择并复用稳定 ID。目标 stream 必须配置合适的 duplicate window；只有该窗口内、同一 stream 的重复 publish 会被 broker 抑制。该能力不解决业务 handler 幂等、无限期去重、原子 outbox-to-broker、跨 broker 事务、ordering 或 exactly-once。

## 5. 性能与资源边界

普通 `Publish` 仅增加常数次 PubAck 字段检查，不增加消息 ID 扫描、header 或网络往返。`PublishDeduplicated` 扫描最多 256 bytes 并写入一个控制 header，不做 payload hash、不维护跨调用状态、不启动 goroutine 或 retry。

重复尝试在 configured duplicate window 内可减少重复持久化和下游消费，但不得由本地测试推导目标吞吐、p95/p99、磁盘节省或生产容量收益。
