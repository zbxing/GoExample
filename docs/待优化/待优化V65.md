## 2. 本轮复评发现

### 2.1 可执行缺口

`natsjetstream.Adapter.ReceiveDelivery` 固定调用 `Consumer.Next(FetchMaxWait(...))`，不会传入 `FetchPriorityGroup`、`FetchPrioritized`、`FetchMinPending` 或 `FetchMinAckPending`。当前 preflight 已从服务端新鲜 `ConsumerInfo` 证明 consumer 为 pull mode，却没有检查 `Config.PriorityPolicy` 与 `PriorityGroups`。

nats.go v1.53.1 支持 pinned、overflow 和 prioritized policy；这些模式要求或依赖请求级 group、pin、priority 或 threshold。满足持久性、DeliverAll、ReplayInstant、MaxDeliver、payload、subject、request expiration、pause 和 lease 条件的 priority consumer 仍会通过启动门禁，直到 worker 发出不带这些参数的 pull 请求才失败或进入 adapter 未声明的调度行为。

### 2.2 必须共同修复的边界

- 通用与 adapter-bound preflight 均以同一次新鲜 `ConsumerInfo.Config` 为准。
- 只接受 `PriorityPolicyNone` 且 `PriorityGroups` 为空；pinned、overflow、prioritized、unknown 或 group-only 返回固定 `ErrConsumerPriorityPolicy` 与正 required lease。
- 错误支持 `errors.Is`，不暴露 policy 数值、group 名、pin、threshold、identity、stream、URL、配置值或 backend 原文。
- 默认 policy 继续既有 pause、pull、持久性、DeliverAll、ReplayInstant、MaxDeliver、payload、subject、request expiration 与 AckWait/BackOff 校验。
- adapter 不自动选择 priority group、pin、优先级或阈值，不增加控制面写入、第二次 `Info`、公共配置、后台轮询、goroutine 或消息热路径工作。
- 单元测试锁定 policy 矩阵、group-only、required lease、单次 `Info`、错误优先级与隐私。
- 真实 file-backed JetStream 必须证明 pinned consumer 被拒绝；显式删除并重建默认 policy consumer 后通过并完成原 delivery 合同。
- delivery evidence 升级 schema 12；目标生产 priority 治理、broker 与容量继续 `not_recorded`。

### 2.3 性能与恢复边界

V65 把服务端已经明确的 request-policy 错配提前为启动失败，避免启动 worker 后才暴露 pull 不兼容。合法默认 consumer 只增加启动期一次 O(1) 枚举比较和切片长度检查；不新增网络往返、分配要求、锁、goroutine、timer、buffer、retry 或稳态 telemetry，不能据此宣称吞吐、p95/p99、CPU/RSS、priority 公平性或生产恢复时间改善。
