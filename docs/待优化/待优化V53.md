## 2. 本轮复评发现

### 2.1 可执行缺口

`Framework/queueclient` 对可靠投递使用确定性指数退避。相同配置的 workers/replicas 在相近失败时刻会在相同 backoff 边界重新进入依赖，形成同步重试风险。现有 HTTP retry 已加入有限正向 jitter，但 queue retry 尚未覆盖。

### 2.2 必须共同修复的租约证明

默认静态模式的 `Client.MinimumDeliveryLease` 当前累加每次确定性 `deliveryBackoff`。若 runtime 等待增加 jitter 而 preflight 仍按 base 计算，服务端 acknowledgement lease 可能短于 Framework 声明的完整处理上界。因此 runtime jitter 和静态 lease 最大预算必须在同一任务内完成，不能拆分计分。

动态 lease extension 模式不同：初始 lease 只覆盖 `LeaseExtensionInterval + max(SettlementTimeout, LeaseExtensionTimeout) + safetyMargin`，handler 与 retry 期间由续租循环覆盖，所以不得把全部 jitter backoff 重复加入动态公式。

### 2.3 V53-01 数学边界

```text
base = deliveryBackoff(config, attempt)
window = min(base / 2, MaxBackoff - base)
actual = base + random integer duration in [0, window]
static lease contribution = base + window
```

- 实际等待不短于既有 delivery backoff。
- 随机增量最多为 base 的 50%，最终等待不超过 `MaxBackoff`。
- `base == MaxBackoff` 或窗口不足 1ns 时不采样。
- context cancellation 继续立即中断 timer，并且不进入 ack/DLQ settlement。
- 不改变 attempt、永久错误、ack/DLQ、settlement、lease extension、observer、telemetry 或公共配置。
- 生产使用 `math/rand/v2` 顶层并发安全采样；确定性测试使用私有注入点。

| 动态 lease | 继续使用 interval、较长 callback 与 margin，结果不随 retry jitter 增长。 |

## 5. 性能与资源边界

成功消息、永久错误、最后 attempt 和 legacy `Receive` 不进入 jitter；新增成本只在原本会等待的 retry 失败路径，每次最多一次标准库整数采样和常数次 duration 运算。没有新增 goroutine、队列、timer 池或跨消息状态。

jitter 会有意增加部分失败重试的等待，单次上界为 `min(1.5*base, MaxBackoff)`；目标是分散同步重入，不宣称提高成功路径 CPU/分配、生产吞吐、p95/p99、broker 容量或恢复时间。生产比例和容量收益只能由真实依赖与目标负载测量。
