## 2. 本轮复评发现

### 2.1 可执行缺口

`natsjetstream.preflightConsumer` 已检查 explicit ack、durable/file-backed/no-expiry、完整起点、最低 redelivery、full payload、adapter exact subject 与 AckWait/BackOff，却未检查 `ConsumerConfig.ReplayPolicy`。nats.go v1.53.1 明确规定 `ReplayOriginalPolicy` 会按消息写入 stream 时的原始间隔回放；长空档会被复制到 backlog 恢复过程，但当前 worker 启动门禁不会报错。

### 2.2 必须共同修复的边界

- 复用已有新鲜 `ConsumerInfo`，只接受 `jetstream.ReplayInstantPolicy`，不增加第二次 `Info`。
- 失败返回固定 `ErrConsumerReplayPolicy` 与 required lease，支持 `errors.Is`，不暴露 identity、subject、policy 数值、历史间隔或 backend 原文。
- 单元测试覆盖 instant、original 和未知枚举；其他 preflight 错误优先级、预算和单次 Info 语义不回归。
- 真实 file-backed JetStream 覆盖 `DeliverAll + ReplayOriginal` 拒绝，再重建为 `ReplayInstant` 并完成既有 delivery 合同。
- delivery evidence 升级 schema 8；目标生产 broker、retention、replicas、ACL、容量与 backlog SLA 继续 `not_recorded`。

### 2.3 性能与恢复边界

V61 只消除 replay 配置施加的历史间隔下限，不证明生产 backlog 能在任何固定时间内清空。检查只在已有启动预检中增加一次 O(1) 枚举比较；不增加网络往返、分配要求、锁、goroutine、buffer、retry 或稳态 telemetry，消息热路径不变。

## 5. 性能与资源边界

V61 只读取已有 `ConsumerInfo.Config` 的一个枚举字段，不增加生产网络往返、分配要求、锁、goroutine、buffer、retry 或 telemetry。`ReplayInstant` 允许 broker 尽快交付，但实际速率仍受 broker、网络、worker、下游和容量限制；它不是无限吞吐或固定恢复时长的证据。

真实 p95/p99、吞吐、CPU、RSS、broker IOPS、积压清空速率、安全并发、replica 故障和跨区延迟仍必须由目标环境测量；不得以 loopback 单节点合同推导。
