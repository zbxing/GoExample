## 2. 全面复评发现

### 2.1 架构与边界

- `go.work`、Framework、Solutions/Services、SDK、consumer、证据工具和受控 manifest 已形成分层边界；Go 工具链、`GOROOT` 隔离、命令预算和独立 verifier 均有共享约束。
- 标准 `net/http` handler、Fiber 适配器、认证授权、SQL/Redis/queue/NATS 合同、SDK 生成与恢复证据已有行为测试和失败关闭语义。
- `MSFront` 目录、依赖树检查、前端 E2E 和前端生命周期明确排除，不在 V47 改动或评分。

### 2.2 性能基线与证据发布缺口

`.github/workflows/go-transport-benchmark.yml` 通过 `scripts/transport-benchmark-baseline.mjs` 选择上一轮可信 transport 报告。V47 复评时，`prepare` 在读取并完整校验候选之前就删除 `baseline.json`；JSON 损坏、矩阵不兼容或环境指纹不合法时，命令失败但本地原有基线已经丢失。该行为会降低后续回归比较的连续性，也使手工重试难以保留最后一份可信证据。候选确实缺失或 workflow 显式调用 `unavailable` 时仍应清理旧基线并记录不可用原因。

候选验证完成后，脚本还直接写入基线和来源 JSON。写入中途被终止或磁盘错误可能留下截断文件，下一阶段会把不完整文件当作输入并只能以失败结束。该问题属于仓库内性能基线/证据生命周期，可以通过“先验证、后发布”和现有 `writeFileAtomicallySync` helper 修复；不改变可信来源选择、GitHub run 约束、报告 schema 或 `not_available` 语义。

### 2.3 性能、资源与生命周期

- Framework 热路径、transport 基准矩阵、capacity knee、soak 资源门禁已有固定输入；真实 Linux、真实 payload、生产依赖和长稳容量仍需外部证据。
- V45/V46 已收敛根目录子进程和 Go 下载请求的等待边界；V47 只收敛跨运行基线文件的发布生命周期，不宣称提升网络吞吐或生产 SLO。
- 原子发布只保证单文件观察到完整旧版本或完整新版本；不宣称跨文件事务、跨主机共享存储或断电后的父目录 fsync。
