## 2. 本轮复评发现

### 2.1 可执行缺口

`Adapter.publish` 已拒绝 nil、空 stream 和零 sequence PubAck，但 `deadLetter` 与 `quarantineInvalidMessage` 仍只检查 publish error。若 publisher 返回畸形 ack 且 error 为 nil，这两条路径会继续 `DoubleAck` 源消息，造成 DLQ 写入未确认而源记录被删除。

### 2.2 必须共同修复的边界

- 普通、显式去重、永久错误 DLQ 和畸形消息 quarantine 使用同一确认有效性定义。
- DLQ PubAck 畸形必须返回固定 `ErrDeadLetter`，且源 `DoubleAck` 调用数为零。
- stream 与 sequence 有效的 `Duplicate=true` ack 仍成功，允许稳定 DLQ ID 的安全重试收敛。
- PubAck、stream、sequence、duplicate、消息 ID、消息、header、subject 与 backend error 不进入 telemetry 或错误文本。
- 不新增自动 retry、goroutine、网络往返、公开 API 或跨依赖状态。

### 2.3 一致性边界

DLQ publish 和 source ack 仍不是原子事务。稳定 ID 只在目标 DLQ stream 的 duplicate window 内抑制重复；V55 只保证“没有有效服务端 publish ack 时绝不确认源消息”，不保证无限期去重、ordering、broker 原子 settlement、业务副作用幂等或 exactly-once。

## 5. 性能与资源边界

本轮只增加/复用三个字段的常数判断，不增加分配、hash、锁、goroutine、buffer、自动 retry 或网络往返。成功路径仍是一轮 DLQ publish 和一轮 source confirmed ack；畸形 ack 会保留 source pending 供后续重投，这是防止数据丢失的预期代价。

不得由本地故障注入推导目标吞吐、p95/p99、磁盘节省、容量或恢复结论。
