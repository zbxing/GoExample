## 2. 复评发现

Redis authorization-request 的 create/consume 已用 Lua 同时维护 hash-only payload key 与全局 expiry zset，但 consume 仅凭 payload 存在就接受 state，没有要求 index member 存在，也没有核对 index score 与 payload `expiresAtMillis`。因此孤立 payload 或被篡改 expiry index 的请求仍能进入 token exchange。

create 同时在未检查绝对 cardinality 前执行 `ZREMRANGEBYSCORE`，污染或旧版本写入可突破 manager 的 10,000 上限并放大单次 Lua 工作量；未来 orphan member 还会被相同 state hash 的新 payload 静默接管。该缺口位于 `Framework/sharedstate`，不需要真实硬件、生产 Redis 或外部批准即可关闭。

## 4. V77-01 实施约束

1. state hash 必须为非零 SHA-256，index member 继续使用 64 字符小写 hex；payload 继续严格限制为 4 KiB，PKCE verifier/nonce 必须是 32-byte RawURL Base64。
2. create 必须先验证正整数毫秒 now/expires、`expires > now`、不超过 15 分钟 TTL、`maximum in 1..10000`，再执行任何 Redis mutation。
3. create 必须在 expiry cleanup 前用 `ZCARD` 拒绝超过 10,000 的全局 index；清理后，目标 payload key 或 active index member 任一已存在均返回固定 invalid，不得覆盖/接管。
4. consume 必须在一个 Lua 命令内读取 payload 和 index score 并一次性删除目标两边；Go 严格解码 payload，要求 score 为 `int64` 十进制整数且精确等于 `expiresAtMillis`。
5. missing payload 可清理目标 orphan member；missing member、score mismatch、malformed payload 或 expiry 异常均一次性失败，且不得触碰其他 pending request。
6. 正常 create/consume 各保持一个 `redis.evalsha`；create 常态 O(log N)，consume O(1)，不新增 goroutine、锁、后台状态、公开 API、配置键或 Redis key schema。
7. 本地测试只证明 adapter 的命令边界、双对象一致性、有界性和一次性失败，不证明生产 Redis latency、throughput、HA、TLS/ACL、capacity、eviction 或 recovery。
