## 2. 本轮复评发现

### 2.1 可执行缺口

`natsjetstream.Adapter` 以本地 `FetchMaxWait` 调用 `consumer.Next`；server-backed consumer 的非零 `MaxRequestExpires` 是单次 pull request expiration 的上限。nats.go v1.53.1 会把前者发给 broker，NATS 2.14.5 在期限超限时返回 409。当前 adapter-bound preflight 同时知道两个值却未比较，Worker 可通过启动门禁后才持续遇到被拒绝的 pull 请求。

### 2.2 必须共同修复的边界

- 只在 adapter-bound preflight 比较本地 wait；包级通用 `PreflightConsumer` 不臆测未知 adapter 配置。
- `MaxRequestExpires=0` 按 NATS 语义视为不设上限；等于或大于 `FetchMaxWait` 通过；更短非零值 fail closed。
- 失败返回固定 `ErrConsumerRequestExpires` 与正 required lease，支持 `errors.Is`，不暴露 identity、stream、subject、URL、期限值或 backend 原文。
- 复用同一次新鲜 `ConsumerInfo`，不新增第二次 `Info`、网络往返、公共配置或消息热路径工作。
- 单元测试覆盖 unlimited、exact、above 和 one-nanosecond-short，并锁定错误优先级、单次 Info、包级兼容和隐私。
- 真实 file-backed JetStream 同时证明超上限 pull 的 broker 拒绝、adapter preflight 先行拒绝及恢复兼容上限后的完整 delivery 合同。
- delivery evidence 升级 schema 9；目标生产 broker、retention、replicas、ACL、容量与 backlog SLA 继续 `not_recorded`。

### 2.3 性能与恢复边界

V62 把运行期确定性协议拒绝提前为启动失败，避免不兼容配置下的无效 pull 和重启抖动。合法配置只增加启动期一次 O(1) duration 比较；不增加网络往返、分配要求、锁、goroutine、buffer、retry 或稳态 telemetry，不能据此宣称合法路径吞吐、p95/p99、CPU/RSS 或生产恢复时间改善。
