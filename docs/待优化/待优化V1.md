## 2. 优化清单

### V1-01 统一时间预算并优化请求 deadline

- 优先级：P0
- 状态：`[x]`
- 问题：默认 request timeout 大于 write timeout；Fiber `timeout.New` 全局包裹 API，为每个快请求创建 goroutine/channel。
- 修改：
  - 默认 `HTTP_REQUEST_TIMEOUT` 调整为 8s，`HTTP_WRITE_TIMEOUT` 保持 10s，`SHUTDOWN_TIMEOUT` 调整为 20s。
  - 启动校验：`request < write` 且 `drain + request < shutdown`。
  - 全局 API 使用轻量 deadline context middleware，把 deadline 传播给 handler/DB/HTTP client。
  - handler 必须协作检查 `c.Context()`；超时映射为统一 408。
  - 不再给每个 API 请求创建硬超时 goroutine；确需强制中断的少数路由可显式使用 Fiber timeout。
- 验收：`TestRequestTimeout` 仍为 408；新增配置冲突测试；hello benchmark 分配/耗时不劣化。

### V1-02 优化指标并发热路径和延迟模型

- 优先级：P0
- 状态：`[x]`
- 问题：单锁 map 串行写；summary 无 quantile 且不可聚合。
- 修改：
  - 指标键保持 method + normalized route + status，控制基数。
  - 使用 `sync.Map` 只处理首次 series 创建，series 内使用 atomic counter/sum/buckets。
  - 延迟改为 Prometheus histogram，固定边界覆盖 5ms 至 10s。
  - 保留 in-flight、request total、uptime。
- 验收：race-safe；输出 `_bucket/_sum/_count`；原路由归一化测试保留；新增 histogram 测试；并发 benchmark 优于或不差于基线。

### V1-03 readiness 缓存与并发合并

- 优先级：P0
- 状态：`[x]`
- 问题：每个探针都调用全部依赖，多请求会放大后端压力。
- 修改：
  - 新增 `HEALTH_CACHE_TTL`，默认 1s。
  - 在 TTL 内复用不可变 report；并发过期请求只允许一轮检查。
  - Register/draining 状态变化使缓存失效；返回 report 时复制 map，防止调用方修改缓存。
  - 保留每项检查 timeout，并明确检查函数必须响应 context。
- 验收：连续/并发 readiness 只调用一次依赖；TTL 后重新调用；draining 立即覆盖缓存。

### V1-04 降低探针日志噪声

- 优先级：P1
- 状态：`[x]`
- 问题：kubelet 和 Prometheus 高频请求产生无业务价值的访问日志与编码开销。
- 修改：
  - 新增 `LOG_SKIP_PATHS` CSV 配置。
  - 默认跳过 `/livez,/readyz,/startupz,/metrics`。
  - 兼容路径 `/api/health*` 仍记录，便于前端联调；用户可覆盖默认值。
- 验收：默认探针不写日志；业务请求仍写；配置解析测试通过。

### V1-05 收紧生产诊断信息

- 优先级：P0
- 状态：`[x]`
- 问题：生产可无鉴权暴露 metrics；system info 暴露精确 runtime 指纹。
- 修改：
  - `APP_ENV=production` 时 `METRICS_TOKEN` 必填且至少 32 字符。
  - 新增 `SYSTEM_INFO_DETAILED`，默认仅非生产开启。
  - 生产默认只返回应用 version/commit/build/environment，不返回 Go/Fiber/OS/Arch。
  - pprof 保持默认关闭和独立 token。
- 验收：生产缺 metrics token 启动失败；生产 system info 不含 runtime 字段；开发保持原行为。

## 3. V1 不做项

以下项目需要明确基础设施或业务决策，避免为了“功能数量”引入无效依赖：

- `[-]` Redis limiter/idempotency：等待 Redis 与 key scope 方案。
- `[-]` OpenTelemetry exporter：等待 Collector、协议、采样和数据合规方案。
- `[-]` contrib Prometheus client：V1 先修正自研实现；需要 runtime collectors/exemplars 时迁移。
- `[-]` 正式用户系统/RBAC：等待领域模型、数据存储和安全策略。
- `[-]` OpenAPI 代码生成：等待契约源和版本治理方案。
- `[-]` CI、Kubernetes、镜像扫描：应进入 V2 交付工程，不与本轮服务器热路径修改混合。
- `[-]` Fiber `Prefork`、`ReduceMemoryUsage`、`Immutable`：没有目标 Linux 容器压测证据前不启用。

## 4. 验证记录

验证日期：2026-08-16。测试环境为 Windows/amd64、Intel Core i5-10400、Go 1.26.6（module language version 为 Go 1.25）。

- Go：`go test ./cmd/... ./internal/...`、`go vet ./cmd/... ./internal/...`、server build 全部通过。
- 根命令：`yarn cover:server`、`yarn bench:server` 均实际执行通过。
- 覆盖率：auth 82.1%、config 90.8%、health 88.9%、httpapi 84.7%、observability 79.8%、validation 68.4%。
- MSFront：`yarn lint`、`yarn typecheck`、`yarn build` 全部通过。
- 在线 smoke：`livez/readyz/startupz=200`、超时 `408`、超时指标状态 `408`、幂等重放和跨路由隔离通过、Early Data `425`、metrics `200` 且含 histogram、pprof 默认 `404`。
- Race detector：代码使用 `sync.Map`、atomic 和受锁保护的缓存状态；本机 `go test -race` 未完成，因为 Windows race detector 需要 CGO，而环境未安装 `gcc`。应在 V2 CI 的 Linux race job 补齐门禁。
