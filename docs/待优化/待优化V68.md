## 2. 本轮复评发现

OIDC Authorization Code 回调分别验证 ID token 与 access token，并比较 subject，但尚未验证 ID token 中可选的 `at_hash` 是否绑定本次 token response 的实际 access token。相同 subject 不能证明两个 token 属于同一次授权响应。

仓库固定 ID-token 算法为 RS256，因此声明存在时必须按 OIDC Core 使用 access token ASCII octets 的 SHA-256 摘要左半部分，并比较其 Base64URL 无填充编码。缺失 claim 保持兼容；空、null、错误类型、错误编码或 mismatch 必须失败。该验证属于 `Framework/auth`，transport-neutral callback 与浏览器 callback 都必须使用；浏览器仍须独立验证 access token 和双 token subject。

## 4. V68-01 实施要求

1. 保留 `VerifyIDToken` 签名与行为，新增 `VerifyIDTokenWithAccessToken`；内部解析 `at_hash`，不扩展公开 claims。
2. access token 非空且受 16 KiB 上限约束；RS256 只使用 SHA-256 左半摘要和 RawURL Base64，使用 constant-time 比较。
3. `at_hash` 缺失允许；声明后任何空值、null、类型错误、长度/编码错误或 mismatch 统一返回 `ErrInvalidToken`。
4. `CompleteOIDCCallback` 与 `OIDCBrowser` 都传入 exchange 返回的 access token；失败后 state 仍不可重放，浏览器不创建 session。
5. 浏览器路径继续调用 access-token verifier 和 subject 比较，不能把 `at_hash` 当作 access-token 真实性验证。
6. 错误、HTTP envelope、审计日志与 span 不暴露 token、nonce、hash 或 provider 原文。
7. OIDC browser evidence 升级 schema 2，新增 mismatch 测试、`accessTokenHashBound` 断言、JWKS verifier/test 源文件 checksum 与 downgrade/tamper 拒绝。
8. 更新 README、CHANGELOG、COMPATIBILITY、威胁模型、静态守卫、API snapshot 和 aggregate evidence 输入；OpenAPI/SDK 保持兼容。

## 6. 性能与非目标

`at_hash` 存在时只增加一次最多 16 KiB 输入的 SHA-256 和短字符串比较，O(n) 时间、O(1) 额外空间；缺失时不计算摘要。不增加网络、JWT parse、JWKS refresh、goroutine、timer、锁、共享状态或配置。本轮不提高已经 10.00 的运行时性能维度，也不以 httptest 证明生产 IdP/MFA/HSM/浏览器性能。

V68 不开放新 JWS 算法，不新增 duplicate-key 全局策略，不替代 access-token 验签、subject 比较或 HTTPS token endpoint 信任；不修改、构建、运行或计分 `MSFront`。
