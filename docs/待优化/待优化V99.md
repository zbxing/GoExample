## 1. 互斥判定与评分基线

V98-01（`If-Match` canonical header fast path）已完成；V98-02/V98-03 仍需要真实 edge、DNS、证书、HTTP/2/3、正式 IdP/MFA、生产 Redis/PostgreSQL/NATS、KMS/SIEM、跨主机恢复、目标容量、远端不可变制品和组织审批。全面复评发现幂等指纹仍可在固定 framing 不变的前提下，对常见短请求直接使用栈上编码缓冲，消除 hash 接口和字符串转字节带来的临时分配，因此本轮执行“复评并立即实施”分支。

评分继续采用 20 个非前端维度，权重直接合计 100%。V98 完成基线为 `9.927175/10`；V99-01 完成后为 `9.927925/10`，增量 `+0.000750`。

## 2. 全面复评发现

1. `idempotencyRequestFingerprint` 的摘要字段均为短字符串或受项目预算约束的 body，但原路径仍通过 `hash.Hash.Write` 接收 `[]byte(string)` 转换，并由 SHA-256 对象产生临时分配。
2. 生产幂等 command 仅使用 `If-Match`，短请求总 framing 可放入固定 4096-byte 栈缓冲；超出容量或 header 数量超过固定小数组时必须保留原通用路径。
3. `method`、URL、principal、媒体类型、header 名称/值、body 顺序、8-byte big-endian 长度前缀和 SHA-256 算法必须完全不变。不得改变 Storage/Locker、冲突比较、缓存、replay、ETag 或公开 API。
4. 真实目标环境与生产容量、HA、RPO/RTO、exactly-once 仍不能由本地 benchmark 替代。

## 4. V99-01 实施约束与非目标

1. 仅在 header 数量不超过 4 且完整 framing 不超过 4096 bytes 时使用栈缓冲；其它输入继续使用原通用 SHA-256 写入路径。
2. 使用与 legacy 完全一致的字段顺序、长度前缀、header 名称规范化、header 值读取和 body 字节。
3. 不新增公开 API、配置、schema、operation、错误 sentinel、SDK 或生成物；不改变认证授权、Storage/Locker、常量时间冲突比较、响应缓存和 replay 语义。
4. benchmark 只证明本机仓库内相对分配差异，不外推生产 RPS、p95/p99、RSS、GC、HA、容量或网络延迟。

## 6. 性能与架构评估

V99-01 不改变幂等中间件的 namespaced lock -> fingerprint -> Storage bind -> response cache -> unlock 顺序。常见短请求直接在 `[4096]byte` 中写入同样的 length framing 后调用 `sha256.Sum256`，实测完整指纹由 V98 的 `216 B/op、8 allocs/op` 降至 `0 B/op、0 allocs/op`；超容量 fallback 保留原行为。该结果仅为 Windows/amd64、Intel i5-10400、Go 1.27.1 本地仓库基准，不代表生产吞吐、延迟、容量、Redis 网络或 HA。
