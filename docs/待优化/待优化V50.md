## 2. 全面复评发现

### 2.1 架构、协议与交付

- Framework、Solutions/Services、两套 SDK、独立 consumer、OpenAPI、部署恢复和 evidence 工具仍保持既有所有权与依赖方向。

- V49 的 transport 稳定性合同已经使运行时性能与容量工程达到当前仓库证据上限，本轮不重复计分，也不修改 benchmark workload 或热路径。

### 2.2 数据一致性缺口

`sqlclient.Transaction` 与 `RetryTransaction` 已提供 rollback、取消、deadline、panic 和 PostgreSQL serialization/deadlock retry；`ExecVersioned` 已要求乐观更新恰好影响一行。但 `RetryTransaction` 的公开说明只要求调用方自行实现幂等或 outbox，Framework 没有一个只能在 `Tx` 内调用、并验证 outbox 写入恰好影响一行的原语。

调用方目前只能使用返回 `sql.Result` 的 `Tx.Exec`。漏查 `RowsAffected`、`ON CONFLICT DO NOTHING` 返回零行、错误 SQL 一次插入多行或 driver 无法提供受影响行数时，业务更新仍可能提交而没有唯一、可调度的 outbox 记录。仓库已有“事务内业务更新”和“消息投递”两侧能力，但缺少这一明确的 caller-owned SQL 衔接合同。

### 2.3 可执行优化边界

V50-01 增加 `Tx.EnqueueOutbox` 与固定 sentinel `ErrOutboxEnqueue`。该方法只存在于 `Tx`，使用调用方拥有的 SQL、schema、event ID 和 payload，在既有 operation timeout 内执行，并要求 `RowsAffected() == 1`。执行失败、结果缺失、行数不可用、零行或多行都返回错误，使 `Transaction`/`RetryTransaction` 按既有语义回滚。

Framework 无法从任意 SQL 文本证明目标表确实是 outbox，也不拥有 dispatcher、重试调度、清理、分区或 broker settlement。调用方必须使用稳定唯一 event ID，并使 retry callback 可重放。该能力只证明“同一 PostgreSQL 事务内业务状态和一条 caller-owned outbox 行共同提交或共同回滚”，不证明端到端 exactly-once。

## 5. 性能与资源边界

`EnqueueOutbox` 只在调用方显式使用时增加一次本来就必须发生的数据库 INSERT 和一次 `RowsAffected` 检查；不改变未采用 outbox 的请求热路径，不创建后台任务，也不扩大连接池或重试次数。端到端成本主要取决于调用方表结构、索引、payload、事务竞争和 dispatcher，仓库测试不能外推生产吞吐、延迟或积压容量。
