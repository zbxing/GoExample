## 2. 复评发现

V78 已把 Redis browser-session 认证读取定义为 payload、global zset、subject zset、token metadata 与 public-ID mapping 五对象共同成立的状态，但 inventory 与 device-name update 尚未遵守同一规则。

`listBrowserSessionsScript` 在绝对基数检查前清理 subject index，并只读取 member 对应 payload；缺失 global member、metadata、ID mapping、正 TTL 或一致 expiry 时仍可能返回 session。`UpdateBrowserSessionDeviceName` 使用 `GET ID mapping + GET payload + EVALSHA CAS`，最终只比较三个 string key，不验证两个 index 和 mapping TTL。以上缺口会让认证已拒绝的不完整状态继续被展示或修改，且可以在 `Framework/sharedstate` 内闭环，不依赖真实硬件、生产 Redis 或外部批准。

## 4. V79-01 实施约束

1. direct-store list/update 必须在 Redis I/O 前拒绝 nil context、零 subject/session-ID hash、越界 limit、非正 Unix millisecond 和非法 device name。
2. list Lua 必须在任何 `ZREMRANGEBYSCORE` 前验证全部参数并执行 `ZCARD <= 10000`；只选择最多 `limit` 个 token。
3. list 必须在一个 Lua 命令内读取有界 payload、正 TTL metadata/ID mapping、global score 和 subject score，验证 lowercase SHA-256 token 与闭合 mapping；Go 严格解码 payload、重算 public-ID hash并核对两个整数 score 等于 payload expiry。
4. update 第一条 Lua 必须从 subject-bound public ID 原子获取并验证 payload、双向 mapping、三个正 TTL 和两个 score；Go 严格解码后生成新 payload。
5. update 第二条 Lua 必须在写入前再次比较原 payload、双向 mapping、三个 TTL 与两个 score，任一对象变化均 fail closed；成功更新保留 payload 剩余 TTL。
6. 正常 list 预热后一个 `redis.evalsha`；正常 update 预热后两个 `redis.evalsha`，不得再出现独立 `redis.get`。不新增 goroutine、锁、后台状态、公开 API、配置键、payload 字段或 Redis key schema。
7. 本地 miniredis/telemetry 只证明 adapter 命令边界，不证明生产 Redis latency、throughput、HA、TLS/ACL、capacity、eviction 或 recovery。
