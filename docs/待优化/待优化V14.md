## 5. 本轮已实施优化

### V14-01：减少标准适配器请求深拷贝

`NewHTTPHandler` 原先每个请求调用 `http.Request.Clone`。该 API 除 Header 外还深拷贝 URL、Trailer、TransferEncoding、Form、PostForm 和 MultipartForm，而 Fiber v3.5.0 的标准适配器在此路径只读取 `*http.Request`。实现现复制请求结构体值并仅克隆需要注入私有桥接 token 的 Header，保留原请求 context、body、URL 和全部只读元数据，同时避免污染调用方 Header。

没有移除每请求 128-bit 随机 token、`sync.Map` 登记或 `LoadAndDelete`，因为它们承担标准入口与 Fiber middleware 之间不可猜测的一次性 context/write-deadline 桥接边界。只有 profile 证明这些机制成为主热点并有等价安全设计时才允许继续优化。

新增 `TestNewHTTPHandlerDoesNotMutateCallerRequest`：应用侧主动修改 Fiber 请求头后，调用方原始多值 Header 和攻击者提供的内部 header 仍逐值不变。既有取消、真实客户端断连、HTTP/1.1/HTTP/2 流式响应、SSE、write deadline 和 shutdown 测试继续作为行为门禁。

### V14-02：基准结果

环境：Windows/amd64，Intel i5-10400，Go 1.25.13，`-benchtime=2s -count=5`。未优化基线五轮固定为 37 allocs/op、5,605–5,965 B/op、18,513–23,744 ns/op；优化后两组共十轮固定为 36 allocs/op、5,491–5,855 B/op、17,219–26,632 ns/op。

结论仅限：每请求稳定减少 1 次分配，达到 V14-01 的仓库内 allocation 门槛。B/op 与 ns/op 区间均重叠，不声明字节、吞吐或延迟提升；该结果也不证明远端 Linux、目标 TLS edge、真实依赖、生产容量或 A级已经达成。

### V14-04：中间件成本矩阵、atomic 限流头与 parentless trace context

`BenchmarkHelloFiberHandler` 直接复用 `fasthttp.RequestCtx` 调用完整 Framework handler，把 `app.Test` 的 `net/http` 请求/响应编解码从中间件预算中剥离；当前本地默认组合五轮固定为 16 allocs/op、977 B/op。profile 将生产 external shared-state 路径的剩余可控成本定位到 atomic limiter 对 limit、remaining 与 reset 的逐请求整数转字符串。实现现以固定 20-byte 栈缓冲直接写入响应头，拒绝路径的 `Retry-After` 使用同一编码边界；没有移除 IP principal、原子 shared-state `Take`、fail-closed 错误或限流响应。

永久 `BenchmarkHelloFiberHandlerAtomicRateLimiter` 在相同 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 条件下，未优化基线五轮固定为 16 allocs/op、1,001 B/op，优化后两组十轮固定为 14 allocs/op、953 B/op，即稳定减少 2 allocs/op（12.5%）和 48 B/op。ns/op 区间受本机调度影响并重叠，不声明延迟或吞吐提升。行为测试锁定允许与拒绝状态、最大整数 limit/remaining、1.5 秒向上取整为 2 秒的 reset、拒绝 `Retry-After`，并以 `AllocsPerRun` 要求格式化帮助函数零分配。

随后新增永久 `BenchmarkHelloFiberHandlerMiddlewareMatrix`、`BenchmarkAuthenticationMiddlewareMatrix` 和 `BenchmarkIdempotencyMiddlewareMatrix`。激活矩阵使用 4,608-byte 响应、允许的 `Origin` 和 `Accept-Encoding: gzip`，直接调用相同 Fiber handler；相同本地工具链、`-benchtime=1s -count=5` 下，全开且成功日志被 level 过滤时固定为 17 allocs/op，实际输出 JSON request log 固定为 22 allocs/op，分别关闭 trace、CORS、compression 时固定为 14、15、15 allocs/op，关闭 request log、metrics 或 ETag 仍固定为 17 allocs/op。该结果只证明 filtered request log、metrics 和 ETag 在此场景不增加分配，激活的 CORS 与 compression 各有 2 allocs/op 边际成本；B/op 受压缩池和本机运行波动影响，仅 `without_compression` 五轮稳定为 924–926 B/op，不用其他重叠区间推导字节收益。

有效 HS256 Bearer 认证由关闭时的 13 allocs/op、728 B/op 增至固定 89 allocs/op、5,204 B/op。`alloc_objects` profile 显示约 82% 对象归属于受信 `golang-jwt` 的 JSON claims 解析、base64/HMAC 与校验链；这些是认证语义，不以自研解析器或跳过验证换取分数。idempotency 无 key 旁路在关闭/开启时均固定为 13 allocs/op、728 B/op；带 key 回放 profile 则定位到项目可控的 fingerprint 长度缓冲逃逸和 fingerprint Lock/Unlock 重复 namespace 拼接。实现现让同一摘要复用一个 `[8]byte` 长度缓冲，并让同一 fingerprint 锁 key 只构造一次，摘要格式、SHA-256、锁命名空间、冲突判定和外部存储边界不变；零分配帮助函数门禁及既有同请求回放、请求冲突、并发冲突行为测试继续保护语义。相同工具链两组 `-benchtime=2s -count=5` 下，回放路径由优化前五轮固定 39 allocs/op、2,167–2,182 B/op 降至十轮固定 34 allocs/op、2,039–2,052 B/op，即稳定减少 5 allocs/op 和至少 115 B/op；ns/op 存在调度离群，不作延迟结论。测试 double 的 defensive copy 与 Fiber msgpack replay 成本不冒充真实 Redis 数据。

矩阵复核同时发现，无远端 parent 的 server span 已由 OpenTelemetry context 保存当前 span，不需要再创建仅携带无效 parent 的 `traceRequestContext`。`newTraceRequestContext` 现仅在 parent 有效时保留惰性公开字符串缓存；无 parent 行为测试锁定当前 TraceID/SpanID、空 ParentSpanID、非远端标记、context 身份复用和零分配。相对上一阶段结果，默认 `BenchmarkHelloFiberHandler` 五轮由 16 allocs/op、977 B/op 降至固定 15 allocs/op、753 B/op，atomic 路径由 14 allocs/op、953 B/op 降至固定 13 allocs/op、729 B/op，两条路径均稳定减少 1 alloc/op 和 224 B/op。

V14-04 的仓库内工作已完成：直接 handler 的 filtered/emitted log、trace、metrics、激活 CORS/compression、ETag、有效 Bearer、idempotency 无 key 与带 key 回放均有永久入口，两个项目可控热点具备行为和 allocation 门禁。真实 Redis 网络路径、目标 IdP、不同生产 payload 与固定 Linux runner 的 CPU/GC/RSS 数据仍是目标环境证据，继续保持 `not_recorded`。上一阶段评分把标准生态与可替换性从 9.80 调至 9.81、运行时性能与容量工程从 9.87 经 atomic 限流优化后的 9.89、矩阵与 parentless trace 优化后的 9.91 再保守调至 9.92；未舍入加权和由 9.8197 经 9.8216、9.8230 升至 9.8237，三位精确综合评分为 9.824，综合等级仍为 A−。

本轮继续推进 V14-04 的消息处理热路径：`queueclient.Process` 在没有 `traceparent`/`tracestate` 时不再为 `propagation.MapCarrier` 创建空 map；只有发现追踪头时才按原有大小上限创建并复制 carrier。`Process` 的 body/header defensive copy、W3C parent 提取、baggage 隔离、超时/取消和低敏 span 语义保持不变。新增 `TestTraceCarrierLazilyAllocatesOnlyForTraceHeaders` 锁定无追踪头路径零分配并验证大小写归一化后的两个 W3C header，永久 `BenchmarkTraceCarrier` 在 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 下记录无追踪头固定 `0 B/op、0 allocs/op`，带追踪头固定 `336 B/op、2 allocs/op`。该增量仅证明仓库内普通消息热路径减少一次 map 分配，不代表 broker、远端 Linux、生产容量或长稳证据；V14-03、V14-05、V14-06 及 V14-07 至 V14-15 继续保持 `not_recorded`，不修改 `MSFront`。运行时性能与容量工程由 9.92 保守调至 9.93，未舍入加权和由 9.8237 升至 9.8244，三位展示值仍为 9.824，综合等级仍为 A−。

### V14-04 增量：queueclient header 校验

`validateHeaders` 现对空、单 header 以及恰好两个 header 路径均不创建重复检测 map；两 header 使用一次成对大小写比较，三个及以上 header 才创建归一化重复检测 set。名称、值、字节上限和大小写重复仍返回原有错误。新增 `TestValidateHeadersLazilyAllocatesDuplicateSet` 与永久 `BenchmarkValidateHeaders`，并将三 header 场景纳入分配基线。由于本机当前没有可执行的 Go 工具链，本轮未宣称新的 benchmark 数值或评分增量；既有已验证分数保持不变。本地 queueclient 优化不等价于 broker、远端 Linux、生产容量或长稳证据；V14-03、V14-05、V14-06 和 V14-07 至 V14-15 继续 `not_recorded`，不修改 `MSFront`。

### V14-04 增量：NATS JetStream 发布 header map 复用

`nats.NewMsg` 已经创建可写的 `Header` map；旧实现随后再创建并替换第二个 map。NATS JetStream 发布与 DLQ 路径现将经过控制 header 过滤的应用 header 直接写入 `NewMsg` 自带 map，保留控制 header 过滤、DLQ message ID 覆盖和调用方输入隔离。新增 `TestCopyApplicationHeadersReusesDestinationAndFiltersControlHeaders` 与永久 `BenchmarkCopyApplicationHeaders`，对照保留旧 helper 的分配基线。

## 15. 本轮增量：JetStream 无效消息隔离

`ReceiveDelivery` 过去遇到 queueclient 无法表示的多值应用 header 时直接返回 `ErrInvalidMessage`，源消息保持 pending，可能在 durable consumer 中持续重投并阻塞后续工作。适配器现在将这类消息先隔离到配置的 DLQ：保留 body 与合法单值应用 header，丢弃无法安全表示的多值 header 和 JetStream 控制 header，并使用来源 stream、consumer 与 sequence 派生的稳定去重 ID；只有 DLQ 发布成功后才 `DoubleAck` 源消息，然后继续接收下一条有效消息。

行为测试证明隔离严格遵守 publish-before-ack：DLQ 发布失败时源消息零确认，源确认失败时返回固定 `ErrDeadLetter`，缺失可信 metadata 时保持 `ErrInvalidMessage` 且不发布、不确认；错误文本不暴露后端细节。`go test ./Framework/... -count=1` 与 `go test -race ./Framework/queueclient/natsjetstream -count=1` 均通过。该仓库内能力不证明目标 broker、生产 DLQ 运维、跨主机故障、容量、长稳或 exactly-once；V14-03、V14-05、V14-06 和 V14-07 至 V14-15 继续为 `not_recorded`，不生成 V15，不修改 `MSFront`。韧性、故障与恢复由 9.2 保守调至 9.3，未舍入综合评分由 9.8279 升至 9.8309，三位展示值由 9.828 升至 9.831，综合等级仍为 A−。
