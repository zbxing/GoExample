## 2. 复评发现

Redis browser session 同时写入 payload、global zset、subject zset、token metadata 和 public-ID mapping，但认证读取当前只执行 `GET payload`。缺失或篡改任一索引/映射、两个 expiry score 相互矛盾时，payload 仍可进入 claims/CSRF 验证，导致集中 inventory/revoke 与实际认证状态分离。

创建脚本还会在绝对基数检查前清理 global/subject zset，并且只检查 string key，不拒绝目标 token 的孤立 zset member。direct-store 的零 hash、超过 10,000 maximum、非正毫秒和 sub-millisecond TTL 也没有全部在 Redis I/O 前拒绝。以上缺口位于 `Framework/sharedstate`，无需真实硬件、生产 Redis 或外部批准即可关闭。

## 4. V78-01 实施约束

1. direct-store create 必须在 Redis I/O 前拒绝 nil context、零 token hash、`maximum` 越界、非正 Unix millisecond、`expiresMillis <= nowMillis`、非法 subject/session ID/device/claims 和超限 payload。
2. create Lua 必须在任何 `ZREMRANGEBYSCORE` 前校验全部参数，并对 global/subject zset 分别执行 `ZCARD <= 10000`；cleanup 后 payload/metadata/ID/global member/subject member 任一冲突均拒绝。
3. read Lua 必须在一个命令内读取 payload、metadata、ID reverse mapping、global score 和 owner subject score，且 payload/metadata/ID key 的 TTL 均为正。
4. Go 必须严格解码 payload，拒绝 unknown field 和 trailing JSON，重新计算 payload subject 与 public-ID hash；两个 score 必须是 `int64` 十进制整数且严格等于 payload expiry。
5. missing/mismatched/malformed/fractional 状态 fail closed，不得修改其他 session；expired 的既有固定错误语义保持。
6. 正常 create/read 预热后各一个 `redis.evalsha`；create 常态 O(log N)，read 固定次数 O(log N)。不新增 goroutine、锁、后台状态、公开 API、配置键或 Redis key schema。
7. 本地 miniredis/telemetry 只证明 adapter 命令边界，不证明生产 Redis latency、throughput、HA、TLS/ACL、capacity、eviction 或 recovery。
