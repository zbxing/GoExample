## 1. 版本边界

V12 的仓库内实现、自动测试、失败门禁、文档与本地证据范围已经完成。V13 只承接 V12 尚未取得的目标环境、远端运行、外部系统、生产部署和审批证据，不回退 V12 已完成状态，也不把 workflow 定义、本地 loopback、未签名 manifest 或合成 workload 当作生产完成证明。

本文件记录 2026-08-26 至 2026-09-01 的 V13 实施历史。根据 2026-09-01 的版本收口决定，V13-01 至 V13-09 在未取得目标环境完整证据的情况下保持 `not_recorded`，并逐项迁移至 V14；V13 的“已完结”表示版本跟踪停止，不表示这些工作包已经完成。当前唯一最新待优化清单为 [待优化 V14](./待优化V14.md)。

本轮继续推进 V13-06 的仓库内默认 hello 响应编码热路径。刷新后的分配 profile 将剩余 Framework 可控成本定位到 `success -> Envelope -> c.JSON`；默认、空白或显式 `Fiber` 名称现直接写入与 `encoding/json` 完全一致的预编码成功 envelope 和 `application/json; charset=utf-8`，自定义名称仍走统一 `success` 编码，保留标准 JSON escaping。行为测试逐字节对照完整 body，并锁定 Content-Type、弱 ETag、条件请求和特殊字符转义。相同 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 下，本轮未修改基线五轮固定为 102 allocs/op、16,831–16,906 B/op；优化后两组共十轮固定为 99 allocs/op、16,682–16,765 B/op，即每请求稳定减少 3 次分配（约 2.9%），字节区间至少减少 66 B/op。顺序延迟区间重叠，不作吞吐或延迟提升结论。该增量只覆盖 Framework 示例 hello 的默认响应，不证明远端 Linux、目标 payload/IdP/依赖/TLS edge、生产容量或长稳，也不改变 `linuxRemoteBenchmark=not_recorded`；V13-01 至 V13-09 全部继续 `not_recorded`，不创建 V14，也不修改 `MSFront`。运行时性能与容量工程由 9.80 保守升至 9.81，未舍入加权和由 9.8148 升至 9.8155，三位精确综合评分升至 9.816。

本轮继续推进 V13-06 的仓库内 CORS/压缩 `Vary` 响应头热路径。allocation profile 将剩余 Framework 可控成本定位到受限来源 API 无 `Origin` 请求仍进入 Fiber CORS，以及压缩中间件对 `Origin` 动态拼接 `Accept-Encoding`；实现现为非 `OPTIONS` 的受限来源 `/api/v1` 请求预置静态 `Vary: Origin`，无 `Origin` 时跳过已无额外工作的 CORS，并在压缩中间件回收前把精确单值 `Origin` 替换为预计算的 `Origin, Accept-Encoding`。逐值行为测试锁定无/有允许 Origin、通配来源、preflight、handler error 和非 API 响应，保持既有 CORS、错误与压缩协商语义。相同 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 下，本轮未修改基线五轮固定为 99 allocs/op、16,662–16,745 B/op；优化后两组共十轮固定为 97 allocs/op、16,622–16,720 B/op，即每请求稳定减少 2 次分配（约 2.0%）。字节与顺序延迟区间重叠，不作字节、吞吐或延迟提升结论。该增量只覆盖 Framework 本地 API 响应头热路径，不证明远端 Linux、目标 payload/IdP/依赖/TLS edge、生产容量或长稳，也不改变 `linuxRemoteBenchmark=not_recorded`；V13-01 至 V13-09 全部继续 `not_recorded`，不创建 V14，也不修改 `MSFront`。运行时性能与容量工程由 9.81 保守升至 9.83，未舍入加权和由 9.8155 升至 9.8169，三位精确综合评分升至 9.817。

本轮继续推进 V13-06 的仓库内入站 W3C Trace Context 解析热路径。内存 profile 将带 `traceparent` 请求的剩余可控成本定位到 OpenTelemetry `propagation.MapCarrier` 的逐请求构造和对同一头值的通用传播解析；middleware 现直接把严格 `ParseTraceparent` 的结果构造成 remote `SpanContext`，保留现有 version 00、小写十六进制、非零 ID 与 reserved flags 拒绝策略，保留 sampled/random flags 和合法 `tracestate`，无效 `tracestate` 仍只被忽略而不否定合法 parent。flags 解码使用固定 `[1]byte` 栈缓冲，纯 header-to-SpanContext 路径由零分配门禁保护，recorder 测试锁定 remote parent 与 tracestate；新增永久 `BenchmarkHelloEndpointWithTraceparent`。相同 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 下，基线为 109–110 allocs/op、18,566–18,647 B/op，优化后两组共十轮为 5 轮 106 allocs/op、5 轮 107 allocs/op、18,217–18,366 B/op，即稳定至少减少 2 次分配（约 1.8%，通常减少 2–3 次）且字节区间至少减少 200 B/op；延迟区间重叠，不作吞吐或延迟提升结论。该轮通用 evidence 输入合同同步为 244 项，其中 243 项必需。该增量只覆盖 Framework 本地带 W3C parent 的请求路径，不证明远端 Linux、目标 payload/IdP/依赖/TLS edge、生产容量或长稳，也不改变 `linuxRemoteBenchmark=not_recorded`；V13-01 至 V13-09 全部继续 `not_recorded`，不创建 V14，也不修改 `MSFront`。运行时性能与容量工程由 9.83 保守升至 9.85，未舍入加权和由 9.8169 升至 9.8183，三位精确综合评分升至 9.818。

本轮继续推进 V13-06 的仓库内请求取消与采样 span 收尾热路径。profile 复核显示，每个普通请求都用 `context.AfterFunc` 单独监听同一个应用停机 context，而采样 span 又分两次提交 route/status 属性并触发第二次 SDK slice growth。应用现以一个有界、只持有活动请求的取消注册表统一处理停机，普通完成会移除登记，SSE 切换独立 stream timeout 时原位替换 cancel，停机后迟到请求立即取消；调用方取消、请求 deadline、SSE deadline、标准写期限和应用停机语义均由行为、并发与 race 测试保护。采样 span 则按九种标准方法、有限 Fiber 路由模板和 100–599 状态惰性复用二属性配置，一次提交 route/status；自定义方法和越界状态保持动态且不扩张缓存。相同 Windows/amd64、Intel i5-10400、Go 1.25.13、`-benchtime=2s -count=5` 下，默认路径基线五轮固定为 97 allocs/op、16,633–16,724 B/op，优化后两组共十轮固定为 95 allocs/op、16,486–16,586 B/op；带 sampled `traceparent` 路径从前轮 106–107 allocs/op、18,217–18,366 B/op 降至两组共十轮固定 104 allocs/op、17,990–18,075 B/op。两条路径均稳定至少减少 2 次分配，字节区间分别至少减少 47 B/op 和 142 B/op；延迟区间重叠，不作吞吐或延迟提升结论。通用 evidence 输入合同补入实际生产实现 `Framework/httpapi/routes.go` 与 `Framework/observability/tracing.go`，现为 246 项、其中 245 项必需。该增量不证明远端 Linux、目标 payload/IdP/依赖/TLS edge、生产容量或长稳，也不改变 `linuxRemoteBenchmark=not_recorded`；V13-01 至 V13-09 全部继续 `not_recorded`，不创建 V14，也不修改 `MSFront`。运行时性能与容量工程由 9.85 保守升至 9.87，未舍入加权和由 9.8183 升至 9.8197，三位精确综合评分升至 9.820。

## 3. 拆分顺序

1. 先完成 V13-01 至 V13-04 的外部信任边界：edge、Redis、身份和审计。
2. 再完成 V13-05 至 V13-07 的数据面、性能与交付实证；这些任务可以共享目标环境，但证据和完成判定必须独立。
3. 最后完成 V13-08 的真实消费者迁移和 V13-09 的综合长稳/恢复审批。

任何任务都不得仅凭配置、workflow、测试替身或本地 loopback 标记完成。无法提供某项强保证时，必须记录已批准的非目标、替代控制和残余风险，不能用文档声明代替运行证据。

## 4. 证据要求

- 每个工作包必须记录目标环境标识、不可变版本/digest、完整命令、开始/结束时间、退出状态、原始输出和制品 SHA-256。
- 远端运行必须记录可访问的 run URL、commit SHA、runner/image/toolchain 指纹和签名或平台 provenance；环境不兼容时不得执行固定性能回归阈值。
- 故障与恢复工作包必须记录注入点、观测到的失败、恢复步骤、数据一致性结果、RPO/RTO 实测值和责任人审批。
- `targetEdge`、`productionSharedStore`、`postgresRecovery`、`natsBroker`、`linuxRemoteBenchmark`、`signedRelease` 等边界只能由严格 verifier 根据完整制品更新，当前未取得的状态继续保持 `not_recorded`。
- `MSFront` 不在 V13 范围内，前端评分沿用现有基线且不因服务器侧工作上调。
