# Server Failure Matrix And Local Recovery Drill

Scope: Go `Framework`, `Proj/Example`, and server evidence. `MSFront` is out of scope.

## Purpose And Evidence Boundary

`yarn drill:server` turns selected existing behavior contracts into one bounded, repeatable local drill. It records raw output and a machine-readable result under `.temp/recovery/server-local`, then returns non-zero if any scenario fails.

This is local contract evidence. Loopback sockets, `httptest`, `miniredis`, and controlled exporters do not prove target Redis HA, a real collector, production edge behavior, alert delivery, operator response, RPO, or RTO. A workflow definition is not a successful remote run, and an unsigned artifact does not prove provenance.

The separate `yarn redis:sentinel:contract` Linux Docker entry point uses a pinned Redis 8.2.1 image, one master, one replica, three Sentinels, and separate data/Sentinel ACLs. It triggers `SENTINEL FAILOVER`, then checks replicated state, two-client reconnection, rate limiting, and locking. Its environment, raw test output, container logs, status, and SHA-256 are always written under `.temp/workflow-artifacts/redis-sentinel-contract`. This local contract intentionally has no TLS and remains distinct from target HA evidence.

The separate `yarn postgres:recovery:contract` Linux Docker entry point uses pinned PostgreSQL 16. It runs real serialization, two-transaction deadlock-victim retry, concurrent versioned-update conflict, HTTP versioned GET/strong If-Match/ETag/412/conditional 304 composition, and bounded lock-wait contracts, creates a deterministic 1,000-row checkpoint, takes a custom-format logical backup, adds one post-checkpoint row, and restores into an isolated database. An independent report rejects row or digest drift, inclusion of the post-checkpoint write, archive hash mismatch, and runs beyond two minutes. Raw output, the backup, container log, statuses, report, SHA-256, and an evidence manifest are always archived. This single-node logical contract remains distinct from target physical backup, WAL/PITR, failover, RPO, and RTO evidence.

The opt-in NATS contracts use one pinned NATS 2.14.5 server binary. The single-node delivery contract also proves dynamic lease extension: an 800-millisecond `AckWait` with 100-millisecond `InProgress` intervals carries one 1.5-second handler through confirmed acknowledgement without redelivery or pending work. Extension error, timeout, and panic fail closed before settlement in broker-neutral unit tests. The restart contract kills and restarts one process against the same file store; the three-node contract provisions three-replica source/DLQ streams and durable consumers, connects a dedicated business session to the actual source stream leader, discovers both peers, and kills that leader with one delivery outstanding. The same NATS connection, JetStream/stream/consumer handles, and adapter must observe disconnect/reconnect, move to a surviving server, and complete different-leader election, same-sequence redelivery, post-failover publish, confirmed acknowledgements, DLQ settlement, and drained pending state. The first failed node then restarts against its original file store, all four replicated resources return to three current replicas, and the first successor is killed with sequence 5 outstanding. That node remains offline while sequence 7 is fetched and the current leader is killed, creating an overlapping two-node outage. The connection must remain on the sole Core NATS survivor while JetStream rejects a publish within three seconds because quorum is unavailable. Restarting the sequence-7 node must restore quorum, same-sequence redelivery, fresh lease preflight, another publish and acknowledgement; restarting the final offline node must return all four resources to three current replicas and exactly eight source messages. After full recovery, sequence 9 is left unacknowledged before the current stream leader and another replica are released from one barrier into concurrent stop calls. Their start skew must stay within 250 milliseconds; the business connection must remain on the sole Core survivor while JetStream again rejects writes without quorum. Restoring the old leader must preserve same-session sequence-9 redelivery and lease preflight, sequence 10 must publish and acknowledge, and restoring the final peer must converge all resources with exactly ten source messages. Before WorkerGroup startup, recovery paths update the consumer to a 9-second acknowledgement lease and use fresh server `ConsumerInfo` to prove it covers the 8.51-second handler/retry/backoff/settlement/safety budget; reports bind both values and the preceding short-lease rejection. Before/after or append-only per-node logs and the strict schema-v6 JSON report are archived. These local contracts do not establish target-latency safety-margin tuning, target broker HA, cross-host network-partition tolerance, infrastructure-level simultaneous failure, disk-corruption recovery, production broker identity/authorization, atomic settlement, exactly-once, RPO, or RTO.

The schema-v6 continuation keeps all three processes alive and partitions only their cluster routes. Each actual cluster listener is reached through an advertised TCP proxy. With sequence 11 outstanding and all four replicated resources current, the source leader is kept off the original business connection server, all active proxy connections are closed from one barrier, and direct Core probes must still reach every process. JetStream publish must fail within three seconds; after routes reopen, the source must still contain exactly 11 messages before same-session redelivery, lease preflight, sequence-12 acknowledgement, drained pending state, and full replica convergence. The strict report records proxy connection counts, process/Core availability, leader and connection identities, the failure budget, no delayed commit, final 12 messages, and unchanged aggregate server starts. This loopback route injection does not establish target-broker, cross-host, cross-zone, network-device, authenticated production, disk-corruption, RPO, or RTO behavior.

The separate single-node snapshot contract uses the native JetStream chunked request/reply protocol with message checksum validation and consumer inclusion. It snapshots three messages while sequence 2 is unacknowledged and sequence 3 is pending, publishes sequence 4 after the checkpoint, deletes the source stream, and restores from the archived bytes. The restored stream must contain exactly sequences 1 through 3, preserve the durable consumer's one acknowledgement-pending and one message-pending state, redeliver sequence 2, dead-letter sequence 3, and converge to zero pending work. The raw snapshot, server log, exact byte count, SHA-256, deliberate tamper rejection, and a 15-second restore budget are independently verified. This logical file-stream snapshot does not establish disk-corruption recovery, cross-host backup, target capacity, production authorization, atomic settlement, PITR, RPO, or RTO.

Each Go test process has a 45-second test timeout and a 60-second parent-process timeout. All scenarios run even when an earlier scenario fails, so the final artifact contains the complete local matrix rather than only the first failure.

## Artifact Contract

`summary.json` records schema version, canonical timestamps, Git commit, Go version, overall status, per-scenario duration, exit code, signal/error category, selected test names, and stdout/stderr size plus SHA-256. Raw streams are separate files. `yarn evidence:manifest` independently archives their hashes, while `yarn evidence:verify` checks the resulting manifest against current files.

The CI job runs the server drill and, even after a failed scenario, generates and verifies a manifest before uploading `.temp/recovery/server-local`. The PostgreSQL contract independently uploads `.temp/workflow-artifacts/postgres-recovery-contract` with its own verified manifest. Remote status remains unverified until an actual run ID and artifact are retrieved and checked.

## Production Completion Criteria

1. Repeat shared-state cases against the target TLS/ACL and Sentinel/Cluster topology, including failover, eviction and network partition.
2. Repeat telemetry cases through the deployed collector, backend, Prometheus and Alertmanager, including alert delivery and recovery acknowledgement.
3. Repeat protocol and lifecycle cases through the target edge/load balancer with real drain and connection telemetry.
4. Execute PostgreSQL backup/restore, PITR, deadlock and failover drills against recorded RPO/RTO.
5. Repeat the overlapping, barrier-synchronized concurrent two-node, and route-partition NATS quorum-loss cases against the target authenticated cross-host/zone cluster, then add network-device policy, disk-corruption, capacity, infrastructure-level simultaneous failure, and approved RPO/RTO drills.
6. Sign remote artifacts with workload identity, retain them immutably, and verify provenance at deployment admission.
