# GoExample 优化执行提示词

你正在维护 `GoExample`。目标是在不夸大能力、不伪造证据、不扩大既定范围的前提下，通过真实代码、测试、运行制品和目标环境验证提高项目综合评分。

## 一、不可变规则

1. 每轮只能执行下述“分支 A”或“分支 B”之一，二者互斥；不存在第三个“长期优化”分支。
2. 本轮优化范围明确排除 `MSFront/**`：不得修改其源码、配置、依赖、测试或文档，不得以其既有能力为本轮提分。根目录的共享改动也不得只为 `MSFront` 服务。
3. 评分提升必须来自可定位的实现差异及相称的验证证据。只改文档、增加声明、增加 workflow 或增加未成功运行的配置，不得提分。
4. 不得把本地单元测试、`httptest`、loopback、`miniredis`、本地容器或测试替身描述为目标环境、生产部署或远端运行证据。
5. 不得为追求 `10/10` 虚构完成状态、运行 URL、签名、审批、RPO/RTO、容量结论或兼容性结论。
6. 尊重现有未提交改动，不回退、不覆盖与当前任务无关的用户修改；避免无必要的大规模重构和文件膨胀。

## 二、执行前事实核验

每次开始都必须重新读取仓库事实，不能把本提示词中的“当前状态”当作永久真值。

1. 按版本号数值排序 `docs/待优化/待优化V*.md`，确定最新文档，读取其状态、范围、工作包、完成标准、停止规则、非目标和实施记录。
2. 读取 `docs/评估/项目架构与性能评估.md` 的当前评分、权重、证据边界和剩余短板。
3. 读取相关源码、测试、配置、`README.md`、`Framework/README.md`、`go.work` 和 `package.json`；文档与代码冲突时，以可运行代码和测试事实为准，并修正文档。
4. 遵守仓库 `AGENTS.md`：当 `graphify-out/graph.json` 存在时，先用 `graphify query` 查询本轮问题；需要关系或概念细节时使用 `graphify path` / `graphify explain`。修改后执行 `graphify update .`。
5. 如果进入全面重评，可查阅最新官方文档、标准、上游框架资料和社区实践；外部资料只能作为比较依据，不能替代仓库证据。

事实来源优先级：可运行代码与测试/制品 > 最新待优化文档的明确状态 > 当前评估文档 > README 与设计说明 > 外部资料 > 推测。

## 三、两个互斥执行分支

### 分支 A：最新待优化文档尚未完成

满足任一条件即进入分支 A：文档状态为“实施中”或等价状态；存在未达到 acceptance criteria 的工作包；严格 verifier 仍为 `not_recorded` / `failed`；完成条件要求的目标运行、签名、审批或原始制品尚未取得。

执行要求：

1. 只继续最新待优化文档已经冻结的范围，不创建下一版待优化文档，不覆盖重写项目架构与性能评估文档。
2. 按优先级、依赖顺序和剩余风险选择仍可在当前条件下真实推进的事项；优先修复能够关闭明确缺口并建立失败门禁的代码，而不是继续追加开放式愿望清单。

5. 真实目标环境、外部 IdP、签名基础设施、生产审批等不可控条件暂不可用时，不要求伪造结果，也不能把对应工作包改成 `recorded` 或“已完成”。应记录 blocker、已完成的仓库内风险降低、残余风险和取得外部条件后的明确命令；若范围内已无可诚实推进的事项，本轮停止并报告阻塞，不创建下一版本。

2. 覆盖写入 `docs/评估/项目架构与性能评估.md`，不是在旧文末尾无限追加。保留必要历史结论，但正文必须反映当前实现和当前证据。

6. 新文档范围冻结后，立即选择最高优先级且可执行的工作包进行代码优化、测试和证据生成，并同步实施记录与评分。不得退回分支 A 之外再创建另一份新文档。

## 四、项目真实上下文

### 项目定位

`GoExample` 是一个以 Go 服务端工程能力为核心的多项目工作区，目标是提供可复用的生产级 Framework、可独立部署的业务/通用服务、版本化 OpenAPI 与生成式 Go SDK，以及可审计的测试、发布、部署和恢复证据链。不得用其它仓库的业务领域或技术栈替换这一定位。

### 工作区与模块边界

- 根目录：Node.js/Yarn 命令编排、契约检查、代码生成、证据生成与验证；不是业务运行时。
- `Framework/`：可复用 Go Framework，提供 HTTP、认证授权、共享状态、数据库、消息、可观测性和生命周期能力。
- `Solutions/Example/`：默认示例业务解决方案，持有 application use case、composition root、服务契约和标准 HTTP 入口。
- `Services/Billing/`：可被多个方案复用的独立 Billing 服务，不是 `Example` 内部包。
- `SDK/GoExample/`、`SDK/Billing/`：从各自 OpenAPI 契约生成并校验漂移的 Go SDK。
- `support/consumer/HealthProbe/`：独立 SDK 消费者与健康端点迁移演练模块，不能替代真实外部消费者。
- `support/api-contracts/`、`contracts/`：外部 API 子模块和契约引用/版本治理。
- `support/deploy/`、`scripts/`、`__test__/`：部署基线、任务编排、跨模块契约及证据门禁。
- `MSFront/`：独立 Next.js 管理端，本提示词的优化范围明确排除。

`go.work` 当前使用 Go `1.25.0`、工具链 `go1.25.13`，包含六个模块：`Framework`、`Solutions/Example`、`Services/Billing`、`SDK/GoExample`、`SDK/Billing` 和 `support/consumer/HealthProbe`。

### 当前技术栈

- Go 1.25；Framework 内部使用 Fiber v3，并通过适配器暴露标准 `net/http.Handler`。
- 默认服务入口使用标准 `net/http` server/lifecycle；生产 application/composition 层不得直接依赖 Fiber。
- OpenAPI 契约、兼容性比较器和生成式 Go SDK。
- Redis/Redis Sentinel、PostgreSQL、NATS JetStream 的适配、契约测试与恢复证据工具。
- OpenTelemetry、Prometheus、结构化日志、健康探针和有界指标标签。
- Nginx、Kubernetes、CI、SBOM、release provenance、签名/部署证据与严格 manifest verifier。
- 根任务运行环境为 Node.js `>=20.19.0` 和 Yarn `1.22.22`。

### 已有能力基线

评估和优化不得忽略下列已有能力，也不得把它们夸大为生产闭环：

- Framework 与业务服务边界已建立；`Example` 和 `Billing` 是独立服务，生产组合根通过架构测试隔离 Fiber。
- 标准 HTTP 入口具备有界连接、请求、读写、停机、TLS/HTTP2、流式响应与 SSE 生命周期契约；Fiber 兼容入口仍保留。
- typed query/command、统一 envelope、幂等、认证、角色及 tenant/resource 策略、OIDC/PKCE 和会话撤销等仓库内契约已建立。
- Redis 共享状态、Sentinel 客户端，`database/sql` 边界，broker-neutral queue 与 NATS JetStream adapter 已建立，并有本地/容器故障契约。
- 官方 OpenTelemetry、Prometheus 指标/规则、健康探针、审计 sink 边界及低敏日志/trace 契约已建立。
- OpenAPI 兼容门禁、双 SDK 生成/校验、消费者矩阵、Kubernetes/Nginx 渲染与校验、可复现 server release 和 evidence manifest/verifier 已建立。
- Fiber、原生 `net/http` 与 Framework 标准适配器已有固定本地 benchmark/capacity/soak 契约；这些结果不等于目标环境容量结论。

## 六、证据与评分纪律

所有结论必须标明证据层级：

| 层级 | 可证明内容 | 不可冒充内容 |
| --- | --- | --- |
| 静态/契约 | 结构、API、配置和失败门禁 | 运行性能、生产可用性 |
| 仓库内行为 | 单元、集成、真实 TCP、loopback 或本地容器行为 | 远端平台、生产拓扑和目标容量 |
| 远端 CI | 固定 runner 上的可追溯运行与制品 | 目标生产环境和业务审批 |
| 目标环境 | 指定版本、拓扑、身份和负载下的运行结果 | 未覆盖场景的普遍保证 |
| 审批闭环 | 具名角色批准的 RPO/RTO、例外和残余风险 | 技术实现本身 |

评分要求：

- 复用评估文档现有分项与权重，计算未舍入加权和，再生成展示值；禁止先决定目标分数再倒推分项。
- 每次加分必须指出“哪项缺口被关闭、对应代码/测试/制品是什么、为什么只增加该幅度、还剩什么限制”。
- 已为 `10.0` 的维度不得因同类增量重复加分；未取得目标证据的维度必须保守扣分。
- 性能结论必须标明“代码推断”“本地实测”“远端 CI 实测”或“目标环境实测”，并记录版本、机器/runner 指纹、参数、样本、误差/波动、原始输出和可比 baseline。
- `not_recorded` 只能表示未取得证据，不能夹带伪造的目标运行字段；`recorded` 必须通过对应严格 verifier。
