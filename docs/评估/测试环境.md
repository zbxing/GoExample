# GoExample 本地测试环境与证据边界

评估范围：排除 MSFront，覆盖 Framework、Solutions/Example、Services/Billing、脚本、部署基线和证据生成流程。

本文用于没有服务器时，在 Windows 上通过 WSL2、Linux 虚拟机和 Docker 尽可能完成本地测试。本文生成的结果应标记为 local_verified、linux_vm_verified 或 local_contract_only，不能直接标记为生产环境 recorded。

## 1. 推荐拓扑

优先采用以下顺序：

1. Windows 原生：Node、Go、API/SDK、静态检查和证据校验。
2. WSL2 Ubuntu：Linux 构建、Docker、性能 benchmark 和故障演练。
3. Docker：Redis、PostgreSQL、NATS、Nginx、OTel/Prometheus 等本地依赖。
4. 可选 kind、k3d 或 minikube：本地 Kubernetes 部署流程。
5. 真实服务器或云环境：只用于关闭真实 Edge、正式身份、生产容量、灾备和远端 provenance。

推荐目录结构：

~~~
Windows
  └─ WSL2 Ubuntu 或独立 Ubuntu VM
       ├─ ~/src/GoExample          # 仓库，放在 Linux 文件系统
       ├─ Docker Engine
       ├─ 本地依赖容器
       └─ .temp/                   # 测试输出和证据
~~~

不要把性能测试仓库放在 /mnt/c 下。Windows 挂载目录的文件系统转换会影响 Go 编译、容器卷和 I/O 测量。

## 2. Windows 与 WSL2 准备

### 2.1 安装 WSL2

在管理员 PowerShell 中执行：

~~~
wsl --install -d Ubuntu-24.04
wsl --update
~~~

重启后进入 Ubuntu，并安装基础工具：

~~~
sudo apt update
sudo apt install -y git build-essential ca-certificates curl
~~~

### 2.2 启用 Docker

可以选择以下任一方式：

- Windows Docker Desktop：启用 WSL2 backend 和 Ubuntu integration。
- 独立 Ubuntu VM：在 VM 内安装 Docker Engine。

确认 Docker 可用：

~~~
docker version
docker run --rm hello-world
~~~

### 2.3 准备项目工具链

在仓库根目录执行：

~~~
corepack enable
yarn --version
node --version
yarn env
go version
~~~

项目要求 Node >=20.19.0，包管理器为 Yarn 1.22.22。Go 脚本优先使用 yarn env 安装或解析的工具链；如需指定 Go，可设置 GO_BINARY。

将仓库放入 WSL2 文件系统：

~~~
mkdir -p ~/src
cd ~/src
git clone <repository-url> GoExample
cd GoExample
~~~

如果仓库已经位于 Windows 目录，可以先用于普通测试；性能测试应重新放到 ~/src/GoExample。

## 3. 第一轮：无外部依赖的仓库验收

先确认代码、API、SDK、Node 脚本和证据工具链没有问题：

~~~
yarn test:node
yarn api:compat
yarn test:server
yarn vet:server
yarn build:server
yarn release:server:build
yarn release:server:verify
yarn evidence:manifest
yarn evidence:verify
~~~

Windows 原生也可以运行：

~~~
yarn race:server
yarn vuln:server
~~~

Windows race detector 需要 GCC/MinGW。若只做 Linux 行为验证，应在 WSL2 或 Ubuntu VM 中重复执行。

如果 `yarn test:server` 因 Redis、Sentinel、PostgreSQL 或 NATS 未启动而失败，应记录具体外部依赖和错误输出；不能跳过失败、修改门禁或把结果写成通过。

## 4. 本地依赖层

仓库当前没有统一的本地 docker-compose.yml。建议在仓库外或 .temp/local-lab/ 中维护一个仅用于本地实验的 Compose 文件，不要把本地密码、证书和随机 Secret 提交到仓库。

至少准备以下服务，并固定镜像版本：

| 服务 | 本地用途 | 主要变量或入口 |
| --- | --- | --- |
| Redis | 限流、幂等锁、会话和共享状态 | REDIS_URL |
| Redis Sentinel | 主从发现和故障切换 | REDIS_TOPOLOGY=sentinel、Sentinel 地址和 master 名称 |
| PostgreSQL 16 | 事务、版本更新、迁移和恢复 | DATABASE_URL |
| NATS JetStream | ack、重投、lease、DLQ 和快照 | NATS_TEST_URL、NATS_SERVER_BINARY |
| Nginx | TLS、HTTP/2、header、超时和 drain | yarn edge:contract |
| OTel Collector | 本地 trace 导出链路 | OTEL_TRACES_EXPORTER=otlp |
| Prometheus | 指标抓取和告警规则 | support/deploy/prometheus/ |
| Keycloak 等 OIDC 服务（可选） | 本地 OIDC/MFA 协议集成 | OIDC_* |

Example 本地开发配置可从 Solutions/Example/.env.example 复制。验证真实 Redis 时使用：

~~~
SHARED_STATE_MODE=external
REDIS_URL=redis://...
~~~

不要把 memory 模式的结果当作跨实例 Redis 证据。

启动本地 Compose 后，先检查状态和日志：

~~~
docker compose ps
docker compose logs --tail=100
~~~

## 5. 本地真实协议和恢复合约

在 WSL2、Linux VM 或 Linux Docker host 中执行：

~~~
yarn redis:sentinel:contract
yarn postgres:recovery:contract
yarn nats:delivery:contract:evidence
yarn nats:restart:contract:evidence
yarn nats:cluster:contract:evidence
yarn nats:snapshot:contract:evidence
yarn drill:server
~~~

这些命令可以验证真实软件协议、重试、故障处理、快照和本地恢复。它们仍然属于本地或单机实验，不能证明跨主机 HA、磁盘损坏恢复、生产权限、生产延迟安全余量或 exactly-once。

NATS 重启和集群合约需要真实 NATS server binary。按项目脚本要求设置 NATS_SERVER_BINARY，并保留原始日志、报告和校验文件。

## 6. Edge 合约

先检查并渲染配置：

~~~
yarn edge:check
yarn edge:render --server-name api.example.com --upstream-host goexample-api --upstream-port 80
~~~

再执行 Linux Docker 合约：

~~~
yarn edge:contract
yarn edge:contract:verify
~~~

它会覆盖 TLS/HTTP/2、trace/request ID、431、502、503、504、上传中断和 SIGQUIT drain。输出位于：

~~~
.temp/workflow-artifacts/nginx-edge-contract/
~~~

该结果必须保留为 localContractOnly。它不能关闭真实 DNS、证书所有权、HTTP/3、生产容量或目标 Edge 的 not_recorded 状态。

## 7. 性能与长稳基线

在 WSL2 或独立 Ubuntu VM 中执行：

~~~
yarn bench:transports
yarn soak:transports
~~~

性能运行前记录环境指纹：

~~~
mkdir -p .temp/local-lab/environment
{
  date -u
  uname -a
  cat /etc/os-release
  lscpu
  free -h
  go version
  node --version
  docker version
  printf 'GOMAXPROCS=%s\n' "$GOMAXPROCS"
} > .temp/local-lab/environment/environment.txt
~~~

至少保留以下 workload：

- steady-c1、steady-c2、steady-c4、steady-c8、steady-c16、steady-c32、steady-c64、steady-c128；
- connection-churn-c16；
- response-32k-c16；
- auth-reject-c16；
- dependency-delay-5ms-c32。

记录吞吐、p50/p95/p99、CPU、RSS、GC、goroutine、FD、连接和网络快照。VM 结果只用于同一 VM 指纹下的相对比较和回归门禁，不外推生产 RPS、容量或真实硬件性能。

## 8. 可选本地 Kubernetes

安装 kind、k3d 或 minikube 后，先执行仓库检查：

~~~
yarn kubernetes:check
yarn kubernetes:render --image ghcr.io/example/goexample-api@sha256:<64-hex-digest> --allowed-origin https://console.example.com --oidc-issuer https://identity.example.com/tenant --oidc-audience goexample-api --oidc-jwks-url https://identity.example.com/tenant/.well-known/jwks.json
~~~

在本地集群中可以执行：

~~~
kubectl apply --server-side --dry-run=server -n <namespace> -f .temp/deployment/kubernetes/goexample-api.json
kubectl apply --server-side -n <namespace> -f .temp/deployment/kubernetes/goexample-api.json
kubectl rollout status -n <namespace> deployment/goexample-api --timeout=10m
kubectl get -n <namespace> deployment,pod,pdb,hpa
~~~

可继续验证扩缩容、探针、PDB、NetworkPolicy 和回滚：

~~~
kubectl rollout history -n <namespace> deployment/goexample-api
kubectl rollout undo -n <namespace> deployment/goexample-api --to-revision=<revision>
kubectl rollout status -n <namespace> deployment/goexample-api --timeout=10m
~~~

kind、k3d 和 minikube 只能证明本地 Kubernetes API 和部署流程。它们不能证明真实节点、跨可用区调度、生产 admission、真实 HPA/PDB 效果或生产回滚。

## 9. 合成数据和故障注入

没有生产数据时，使用可重复的合成数据：

1. 固定随机种子，并保存数据生成参数。
2. 覆盖正常、空值、边界长度、非法输入、重复请求和过期数据。
3. 覆盖 1 KiB、32 KiB 和 4 MiB 等 payload 大小。
4. 固定读写比例、并发数、依赖延迟和错误比例。
5. 将数据集摘要和 SHA-256 写入实验报告。

可以在 Linux VM 中使用 tc/netem 做延迟、丢包和断网测试；Windows 原生网络模拟不应被当作 Linux 或生产网络证据。虚拟机快照可以帮助恢复实验，但不能代替生产备份、PITR 或 RPO/RTO 演练。

## 10. 证据归档

每一轮完成后执行：

~~~
yarn evidence:manifest
yarn evidence:verify
~~~

同时保存：

- 环境指纹；
- 固定命令和退出码；
- 原始 stdout/stderr；
- 结构化报告；
- 输入和产物 SHA-256；
- Git commit、Go/Node/Docker 版本；
- 测试数据生成参数；
- 未运行项目的明确 not_recorded 原因。

不要提交真实密码、私钥、OIDC client secret、Redis 密码或生产日志。证据可以存放在受控的本地目录或 CI artifact 中。

## 11. 结果状态和评分边界

建议使用以下状态：

| 状态 | 含义 |
| --- | --- |
| local_verified | Windows 或本地容器内的仓库级行为通过 |
| linux_vm_verified | 固定 Linux VM 指纹下的 Linux 行为或 benchmark 通过 |
| local_contract_only | 本地 Docker/loopback 合约通过，不能外推生产 |
| not_checked | 没有运行或环境不一致，不能比较 |
| not_recorded | 需要真实目标环境、审批或远端 provenance |

本地结果可以提升测试覆盖率和回归信心，但不能手工关闭真实 Edge、正式 IdP/MFA、生产容量、跨主机 HA、生产 RPO/RTO、KMS/SIEM 或远端 provenance。当前 V126-02/V126-03 在没有这些原始证据、独立 verifier、不可变制品和批准记录前，应继续保持 not_recorded。
