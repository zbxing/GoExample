## 3. 架构与所有权评估

### 3.1 Workspace、模块与兼容边界

- `Framework` 提供 transport-neutral HTTP、认证授权、共享状态、SQL、消息、观测、健康检查和服务器生命周期；业务 SQL、driver、broker subject、生产地址与凭据留在组合根。
- `Solutions/Example` 与 `Services/Billing` 是独立交付根，共享 Framework 合同但不反向污染 Framework；两套 OpenAPI/SDK、consumer matrix 和 API snapshot 约束跨项目兼容。
- 标准 `net/http` 是默认服务边界，Fiber 保留在 Framework adapter 内；架构测试阻止生产 application/composition 直接导入 Fiber。
- 发布、部署、恢复和 evidence 生成器与独立 verifier 分离，远端及目标环境结论必须由不可变运行制品证明。
- V84 不新增公开类型、方法、字段、错误、配置、环境变量、schema 或跨模块依赖，公开 API 目标仍为 373 symbols。

### 3.2 并发、context 与资源所有权

- HTTP 入站、SSE、关闭与连接容量已有有限预算；Queue V80、SQL V81、Redis V82、通用出站 HTTP V83 已防止 callback/driver/hook/transport 在 context 完成后迟到返回 nil success。
- `OIDCClientConfig.HTTPClient` 与 `JWKSConfig.HTTPClient` 接受任意标准 `*http.Client`，身份模块不能假设调用方使用了 `httpclient.New` 的私有完成态 helper。
- OIDC discovery/token exchange 当前在 `Do`、body read、JSON parse 后未重新检查 caller cancellation 或已经到达的单调 deadline；忽略 context 的 transport/body 可使迟到成功被接受。
- JWKS cached-key 快路径不执行网络 I/O，也不检查 completed context；已取消的 token verification 仍可能成功。刷新路径用不可取消的 `sync.Mutex.Lock` 串行化，请求可在自身 deadline 后继续等待另一刷新。
- JWKS refresh 在发布新 key map 与 `refreshedAt` 前没有完成态检查；忽略 context 的 HTTP/body 路径可在预算后污染共享 cache。
- V84 应以 auth 私有 helper、可取消刷新 gate 和结果边界统一这些入口；显式 provider/解析错误继续映射到既有固定 public sentinel，避免泄露原始响应或底层错误。

## 4. 性能、内存与容量评估

- 入站 middleware、ETag、trace header、queue header、JetStream 转换、retry backoff 和响应体限制均有永久 benchmark 或确定性边界测试；当前没有证据支持新的吞吐数字或跨框架排名变化。
- OIDC discovery 通常发生于启动，token exchange 位于登录路径，JWKS cached verification 位于认证热路径；完成态 helper 必须保持 live-context 零分配且不得增加网络往返。
- 将 JWKS refresh 互斥等待改为 context-aware gate 仍维持最多一个远端 refresh，不新增后台 goroutine、轮询或跨请求 timer；只有发生刷新竞争时才进入 channel select。
- deadline/cancellation 的早拒绝减少无效 RSA parse、HTTP body parse 与锁后等待；不得把确定性单元测试外推为生产 p95/p99、吞吐或容量收益。
- Windows loopback、httptest 与自定义 RoundTripper 只证明仓库语义；Linux、真实 TLS/edge、HTTP/2/3、代理、跨区网络、正式 IdP 和目标 payload 容量继续 `not_recorded`。

## 5. 安全、可靠性与可观测性评估

- OIDC/JWKS 已有 HTTPS/loopback 限制、redirect 拒绝、64 KiB/1 MiB body 上限、duplicate-key 拒绝、PKCE/state/nonce、`at_hash`、ACR/AMR、RSA key 强度与缓存刷新限制。
- browser session、refresh family、角色/资源授权和加密审计链具有有界输入与失败关闭；正式 IdP/MFA/KMS/SIEM 运营仍属外部。
- V84 的安全目标不是撤销已发出的 token request，而是禁止 completed caller 接受迟到 token/metadata/key，禁止 canceled verification 使用 cached key 成功，并阻止过预算 refresh 发布共享 key state。
- OIDC/JWKS 仍只返回 `ErrOIDCProviderUnavailable`、`ErrOIDCTokenExchange`、`ErrJWKSUnavailable` 或 `ErrInvalidToken`；context、URL、query、header、body、credential、key material 与 backend error 原文不进入错误或 telemetry。
- Redis、PostgreSQL、NATS、Sentinel、Kubernetes、server recovery 和 evidence verifier 的仓库合同完整，但生产 PITR、RPO/RTO、容量、跨主机故障和组织响应继续由外部证据约束。

实施约束：

1. helper、gate 与错误映射保持 auth 包私有，不改变公开配置和调用方式。
2. completed context 包括 `ctx.Err()` 和已经到达但 Done 尚未调度的 deadline；live context 快路径应为零分配。
3. OIDC/JWKS 已取得的迟到 response body 必须 exactly-once close；close error 不覆盖固定主要错误。
4. JWKS 最多一个 refresh 访问远端；等待者可按自身 context 退出，取消者不得借用另一调用方刚发布的 cache 返回成功。
5. 显式 HTTP/status/body/JSON/key/JWT 错误继续折叠为既有 sentinel；不返回 context 原文，不记录敏感字段。
6. 不改变 refresh interval、unknown-key throttle、HTTP timeout、RSA/JWT/OIDC 校验、response limits、redirect 或 cache freshness 策略。
7. 不声称 context 能撤销 provider 已接受的请求，不声称本地替身等同真实 IdP、网络、容量或生产可用性。
