评估范围：根工作区、Go Framework、Solutions/Example、Services/Billing、协议、测试、CI、容器、供应链、观测与部署证据；本轮增量扫描与优化明确排除 MSFront，前端维度沿用 V10 已验证基线且不因本轮加分

## 1. 执行结论

GoExample 已经具备成熟工程模板的多数基础：工作区边界清楚，Go 服务有真实 TCP 生命周期契约、显式连接与请求容量限制、健康探针、优雅停机、结构化日志、低基数 Prometheus 指标、官方 OpenTelemetry server/use case span、OpenAPI 对照和严格配置门禁；MSFront 既有基线具备 Next.js App Router、服务端鉴权、角色策略、数据库/文件双存储、请求体上限、Origin 校验、浏览器 E2E 与可访问性测试；CI 还覆盖 Go race/vet/vulnerability、前端 lint/typecheck/test/build、CodeQL、SBOM 和依赖审查。本轮没有修改或重新给 MSFront 加分。

V12 的仓库内实现、自动门禁、文档和本地证据范围已于 2026-08-26 完成。尚缺的目标环境、远端制品、外部系统部署和生产审批事项已拆分到 `docs/待优化/待优化V13.md`；这一版本迁移不改变其 `not_recorded` 边界，也不因文档拆分增加评分。

项目当前最强的部分是本地工程治理、HTTP 生命周期测试和持续质量门禁。四组本地有界故障演练现已统一覆盖 Redis、OTel、HTTP 生命周期和出站取消，并产出逐组原始输出、摘要与可校验 manifest；固定 Redis Sentinel runner 还为 ACL failover/reconnection 建立了独立 Linux Docker 入口。固定 PostgreSQL 16 的新入口进一步执行真实 SQLSTATE/锁测试、逻辑备份、备份后写入与隔离恢复，并由独立报告器校验恢复点摘要、archive 哈希和总预算。仓库也固定了 Nginx edge 合约、可篡改检测的 Linux 服务 release 及默认分支 Sigstore/SLSA provenance 路径，以及 Fiber、原生 `net/http` 与 Framework 标准适配器三条路径的 9 × 3 容量矩阵、5 轮报告门禁、90% 观测峰值经验饱和点、30 秒/transport 有界 soak、系统快照、趋势输入和 profile 摘要。最弱的部分仍不是代码格式或单元测试，而是生产闭环：Redis 外部共享状态及 Sentinel 客户端已实现，但本机无 Docker、尚无成功远端 artifact 或目标 Redis HA 运行证据；真实 OTel collector/trace backend、目标 edge/真实证书与 DNS/HTTP3 生命周期制品、目标 PostgreSQL 物理备份/WAL/PITR/failover、目标 Kubernetes/等价平台 rollout 与恢复演练、成功远端签名制品/镜像 provenance/部署验签、远端 Linux benchmark/soak artifact 和持续运行记录仍缺失。Example 默认标准入口现已传播主动取消与真实 TCP 断连；原生 Fiber/fasthttp listener 的差异仍由主动 deadline 兜底，目标 edge 传播尚未验证。

V10 将 V9 的 16 个维度扩展为 18 个，并单独评价身份会话、恢复演练和生产证据，因此与 V9 的 9.063 不直接可比。按 V10 口径，扫描初始值为 8.753；第一批超时预算、logout CSRF 与移动端 WCAG 修复后为 8.793；第二批补齐 write/shutdown 预算、慢请求体 TCP 契约、认证响应禁缓存及严格 JWT claims 后升至 8.823；本轮先将所有受保护 management/system API 统一为 `privateJson` 禁缓存响应并升至 8.831，再补齐 Go JWT 必需 claims、最大年龄与角色边界升至 8.836，随后将 Go auth login/me、失败和限流响应统一禁缓存并升至 8.844，收敛所有 Go 错误 envelope、认证私有响应的 `no-store, no-transform`、`Pragma` 和 ETag 移除契约升至 8.852，将 MSFront 私有响应策略同步为 `no-store, no-transform` 并由单测/E2E 守卫升至 8.860，最后将会话状态页面重定向也纳入禁缓存策略并由 proxy 单测、Node 守卫和生产 E2E 升至 8.868。本轮在 Next `PHASE_PRODUCTION_SERVER` 配置加载阶段对生产 JWT 密钥和 `MSFRONT_TRUSTED_ORIGINS` 做 fail-fast 校验，instrumentation 保留同规则的运行时纵深校验；两项非法配置均经真实 `next start` 验证以退出码 1 终止，并由 60 个前端单测、路由契约、类型检查和生产构建验证，升至 8.876；随后按 RFC 6750 锁定 Bearer challenge 行为、CORS 可见性并拆分 OpenAPI 普通 401 与 Bearer 401 契约，升至 8.882；再为 Go 生产 JWT、metrics 和 pprof 建立 secret 域隔离启动门禁，升至 8.887；按 RFC 7519 为 Go JWT 增加可配置且强制验证的 audience，缺失和错误 `aud` 均由负向测试拒绝，升至 8.892；按 OWASP 日志治理基线限制客户端 Request ID，非法值在日志前换发并以无标签指标计数，升至 8.898；依据 Fiber 代理信任安全要求禁止 production 全网代理 CIDR，并以真实 TCP 验证 XFF 信任边界，升至 8.906；修复请求日志与 ETag 对流响应的物化，真实 TCP 证明慢读连接会安装并触发 socket 写超时、流生产提前终止，升至 8.912；V11 再将幂等 key 绑定 method/target/principal/media type/body SHA-256 指纹，不同请求复用 key 返回 409，并补齐 keep-alive 复用与 idle 回收、TCP 半关闭和 shutdown 连接归零契约，升至 8.924；随后增加结构化 OpenAPI breaking-change 比较器、PR base SHA 门禁和正反 fixture，升至 8.930；最后接入官方 OTel SDK、server/use case span 与有界 OTLP/HTTP exporter，以行为测试验证低敏属性、远端父上下文、protobuf wire contract、慢 collector 非阻塞和 shutdown flush，升至 8.942。提分均对应真实失败门禁与自动测试，不是文档加分。

在此基础上，三个 `/api/health*` 兼容 operation 增加运行时弃用头、精确 successor、CORS 可见性、OpenAPI response header 契约和 184 天迁移文档，成功与 503 路径均有行为测试，精确值升至 8.948。

随后 Framework 增加只接收标准 `context.Context` 的 `ApplicationQuery` adapter，Example 生产 project route 与 composition root 移除 Fiber import，并由 AST 架构测试、trace/deadline、错误脱敏和配置冲突测试锁定，精确值升至 8.960。

随后补齐 Framework 0.1.x SemVer/兼容策略/changelog 和 62 符号公共 API snapshot：本地门禁要求源码与 snapshot 精确一致，PR 使用 target branch base SHA 允许新增但拒绝既有符号删除/改签名；同时 application query 与默认 GET 路由冲突会在注册前失败，精确值升至 8.980。

本轮继续新增独立于 Fiber 的标准库 `httpclient`：总请求及各 transport 阶段均有有限 timeout，连接池和响应头有上限，启用 HTTP/2 与 TLS 1.2 下限，并支持克隆顶层配置的私有 CA/mTLS 设置和自定义代理；每次传输创建低敏 `CLIENT` span 并传播 W3C Trace Context，span 覆盖响应体读取/关闭生命周期，真实 `httptest` 锁定父子关系、503 状态、敏感字段不入 span、响应头上限、总超时与调用方取消。同时 `ApplicationQuery` 拒绝动态、转义和非规范路径及大小写冲突，公共 API snapshot 更新为 64 个符号，精确值升至 8.991。

随后为 OTLP exporter 增加与 HTTP 服务共用的固定低基数运行指标：enabled gauge、最终 batch/span 的 `success/failure` counter；真实假 collector 在 100ms export budget 下先持续返回 503、再恢复 200，测试锁定 `ForceFlush` 失败/恢复和计数变化，错误文本、endpoint 与凭据不进入标签。Prometheus 增加持续导出失败告警，精确值升至 8.997。之后以受控阻塞 exporter 模拟 burst outage：首个 span 导出停滞后，100 个新 span 的结束仍在 250ms 内完成；恢复后只导出正在处理的 1 个和容量为 4 的队列，其余按非阻塞策略丢弃，韧性分提升后精确值为 9.000。随后在官方 BatchSpanProcessor 前增加精确的非阻塞容量门，复用 exporter 完成回调回收容量并公开无标签 queue-drop counter；同一 burst 测试锁定 96 个超量 span 全部计数，Prometheus 增加持续丢弃告警，可观测性升至 9.7，精确值为 9.006。最后补充 processor pending/capacity/process-lifetime high-water gauge 和 80% 持续饱和告警；行为测试锁定停滞时 5/5/5、恢复后 pending 归零。该实现不改写 SDK 的 batch、timeout、ForceFlush、Shutdown 或重试逻辑，也不冒充真实 Prometheus/Alertmanager 演练，可观测性升至 9.8，精确值为 9.012。

最后新增明确排除 MSFront 的服务器威胁模型：按 OWASP 工作流记录 4 类数据、6 个信任边界和 15 项 STRIDE 威胁，并逐项关联现有代码/测试、残余风险、复审触发条件与所有权缺口；Node 守卫锁定结构、分类、STRIDE 覆盖和证据路径，evidence manifest 归档其 SHA-256。该文档只提升可执行文档治理，不代表正式身份、密钥平台、目标 edge、共享状态、审计留存或真实运行控制已经部署；开发体验与文档治理升至 9.8，精确值为 9.015。

随后实现服务器安全审计事件契约：登录成功/失败/限流、Bearer 缺失/无效及 metrics/pprof 授权成功/拒绝均写入可关联的 `security_audit` 结构化记录，并同步到固定 `event/outcome` 矩阵；未知指标输入折叠为 `_OTHER`，提交的用户名、密码、token、Authorization、body、raw URL、客户端 IP 和任意错误文本不进入审计记录。行为测试逐条解析 9 种路径并检查敏感值，持续登录限流有 Prometheus 规则和 runbook；Framework 公共 API snapshot 更新为 65 个符号。由于没有不可篡改 sink、留存/删除、SIEM/告警投递和具名责任人，只将身份、会话与授权治理升至 8.1，精确值为 9.020。

本轮完成 V11-02 仓库实现：引入 go-redis v9.22.0 和独立 `sharedstate` 包，提供带部署前缀的 Fiber Storage、启动/就绪探测、有限命令/连接池预算、`SET NX PX` owner token 锁、compare-and-delete Lua 解锁及 `INCR`/`PEXPIRE` 原子固定窗口限流。HTTP external 模式拒绝只有 Storage 而没有原子 limiter 的实现；锁键与响应缓存键分离，避免 owner token 污染幂等响应。两个独立 Redis client 和两个 Fiber app 连接 `miniredis` 的行为测试证明并发 quota=1 时严格一个 200/一个 429，同 key 同 body 只执行一次并回放，不同 body 一个 200/一个 409，同时覆盖有限 TTL、Redis 停止 fail closed、等待上界及旧 owner 不能删除新 lease。另有 `REDIS_TEST_URL` 真实 Redis opt-in 测试，但本机无 Redis 服务且该测试跳过，所以生产共享状态证据仍为 `not_recorded`。Framework 公共 API snapshot 现为 83 个符号；精确综合评分为 9.091。

本轮继续完成 V11-03 的 Redis database instrumentation：自定义 go-redis Hook 使用 composition root 的同一 OpenTelemetry provider，为连接、固定命令和 pipeline 创建 `CLIENT` span，并只记录 `db.system.name`、固定 `db.operation.name`、五种固定 result 及上限为 1000 的 batch size。它不记录 Redis URL/host、key/prefix、value、命令参数、owner token、caller 路径、事件或任意错误文本；`NOSCRIPT` 回退作为非错误缺失分类。行为测试覆盖 parent-child、Set/Get miss、Lua 限流、锁/解锁、pipeline、后端停止和全字段负向扫描，Example 已实际注入 provider。该工作仅证明本地 Redis instrumentation 契约，不证明真实 collector 或 Redis HA 已部署；可观测性与 SRE 升至 9.9，精确综合评分为 9.097。

随后修复 OTLP retry 预算失配：官方默认首次退避 5 秒，而项目默认总 export timeout 为 3 秒，旧配置通常会在第二次 HTTP 请求前被取消。现在每次 attempt timeout、初始/最大退避和最大 elapsed time 均从总预算派生，自有 HTTP transport 同时限制 connect、TLS、response header、连接池和 header bytes，并在 shutdown 关闭 idle connections。固定 `success/failure` attempt counter 与行为测试证明同一 batch 首次 503、第二次 200 时最终成功，同时持续 503 仍在总预算内最终失败；collector 响应体和 endpoint 不进入 metrics 或边界错误，最终失败只返回固定文本。Prometheus 对持续 attempt failure 单独告警。该修复使重试从名义配置变为可执行的有界恢复能力，韧性、故障与恢复升至 7.7，精确综合评分为 9.100。

最后完成 V11-11 的本地证据完整性闭环：新增只读 verifier，逐项校验 manifest schema、规范时间、Git 状态、安全路径、重复项、文件大小和 SHA-256；生成器把自身与验证器纳入输入哈希，Node 行为测试证明正常清单通过、制品篡改和 `../` 路径穿越失败，Linux benchmark workflow 在上传前始终执行独立校验。该能力只能发现相对 manifest 的变化，未签名清单仍不能证明作者、可信时间、远端运行来源或 provenance；因此证据完整性与生产就绪仅升至 6.9，精确综合评分为 9.103。

本轮继续推进 V11-07：Framework 增加泛型 `ApplicationCommand`/`NewJSONCommand`，把 JSON media type、typed bind/validation、幂等指纹/回放/409 冲突、统一 envelope 和错误脱敏留在 Fiber adapter 内；Example 新增真实 `POST /api/v1/project/describe` application use case，生产 projectapi 与 composition root 仍无 Fiber import，`project.describe` 是 HTTP server span 的真实 child。query/command 会在注册前统一拒绝非规范路径、同 method 大小写重复、默认 GET/POST 冲突及高级 registrar 混用；OpenAPI 路由对照和三个幂等写接口的 409 响应同步，公共 API snapshot 为 85 个符号。架构分层升至 9.6、标准生态与可替换性升至 8.1，精确综合评分为 9.115。

随后完成 V11-10 的本地恢复演练闭环：`yarn drill:server` 在独立 45 秒 Go 超时和 60 秒父进程超时内顺序执行 Redis 后端停止/锁安全、OTel 停滞与恢复、HTTP deadline/drain/shutdown、出站 timeout/cancellation 四组既有行为契约，即使单组失败也继续收集完整矩阵。逐组 stdout/stderr 和 `summary.json` 写入 `.temp/recovery/server-local`，摘要标记 `local_contract_only` 并记录 Git/Go、测试名、耗时、退出状态、字节数和 SHA-256；CI 始终生成、验证并上传 manifest，Node 守卫锁定场景、参数、runbook 与制品链。本地实跑四组均通过，但没有将 workflow、loopback、`miniredis`、受控 exporter 或未签名 artifact 冒充生产证据；韧性升至 7.8、证据完整性升至 7.0，精确综合评分为 9.121。

本轮继续推进 V11-07：Framework 新增泛型 `NewQuery`/`NewAuthenticatedQuery`，typed GET 的每个字段必须且只能来自 URI、query 或 header，三类来源隔离绑定后统一校验，URI tags 必须与动态路径参数一一对应；静态/动态重叠、默认路由覆盖、重复参数及非规范路径均在注册前失败。受保护 handler 只获得 subject/username/role IDs 最小 principal，Bearer 成功与拒绝响应统一 `no-store`。Example 新增真实 `GET /api/v1/project/preview/{audience}`，生产 `projectapi`/`projectapp` 仍无 Fiber import，OpenAPI 锁定 path/query/header 与 Bearer 401，`project.preview` 是 server span 的真实 child；公共 API snapshot 为 88 个符号。架构分层升至 9.7、标准生态与可替换性升至 8.2，精确综合评分为 9.133。

本轮再补齐 typed query 的角色授权边界：Framework 新增 `NewAuthorizedQuery`，以大小写敏感的精确 role ID 执行 any-of 匹配；required roles 在构造时复制，空、重复、非法或超过 32 项的声明均在启动期失败。角色不足在任何请求参数绑定和 application handler 前返回固定禁缓存 403，缺失/无效 Bearer 保持 401，正确角色才执行 handler。拒绝事件只记录固定 `authorization/failure/role_required/application_query` 与 request/trace/span 关联，不记录 subject、角色、claims、route 或凭据；指标固定矩阵同步扩展。Example preview 要求 `demo` role，OpenAPI 锁定 `x-required-roles` 与 403，公共 API snapshot 为 91 个符号。身份、会话与授权治理升至 8.3，精确综合评分为 9.143；正式身份、租户/资源级策略和生产审计 sink 未加分。

本轮进一步让 V12-07 的跨运行门禁可由 CI 自动执行：workflow 新增默认分支 push 入口，只从同仓库默认分支成功的 `push`/`workflow_dispatch` 运行发现未过期 benchmark artifact，排除 PR 来源；独立准入器限制候选路径和 2 MiB 大小，校验 schema v3、scope、9 × 2 matrix 及 median，并把 run ID、commit、branch、event、artifact name 和候选 SHA-256 写入 `baseline-source.json`。无可信运行、下载失败或旧制品无候选时会删除残留 baseline 并显式记录不可用，损坏或不兼容候选失败关闭；来源记录和当轮 candidate 同时成为远端 evidence 完整性条件。离线行为测试与静态 workflow 守卫已通过。该能力要到至少两次成功默认分支运行后才可能实际比较，本轮没有远端 artifact 或已选择 baseline，因此不宣称远端回归门禁已通过；运行时性能与容量工程仅保守升至 9.0，精确综合评分升至 9.479。

本轮进一步修正 V12-07 的跨运行环境可比性：schema v3 报告新增带规范字段 SHA-256 的 `environmentFingerprint`，固定记录 GitHub Actions runner OS/arch/image version、CPU model/logical CPUs、Go version 与 `GOMAXPROCS=2`。历史准入器复算摘要并要求 GitHub Actions/Linux 来源；缺字段、非规范字段、错误执行并发或摘要篡改均失败关闭。当前与历史指纹不同时，报告不执行固定阈值，而以 `environment_fingerprint_mismatch`、两侧摘要和逐字段差异标记 `not_checked`；同环境通过、环境合法变化和摘要篡改均有离线行为测试。该门禁减少 runner/toolchain 漂移导致的性能误报，但仍没有远端 artifact 或实际被选择且可比的历史 baseline；运行时性能与容量工程保守升至 9.1，精确综合评分升至 9.486。

本轮进一步提高 V12-07 的 workload 代表性：原 9 × 2 容量阶梯保持不变，新增完整 Framework middleware 下的 3 × 2 × 5 真实 TCP 合成场景，分别固定至少 32 KiB 响应、无效 Bearer 在 application handler 前返回 401，以及可取消的 5ms 依赖延迟。schema v4 报告器要求完整配置、零错误和稳定 payload，输出 throughput/p50/p95/p99 中位数及方向比；baseline 准入器同时验证三种场景的配置、payload 和双 transport median，同环境回归增加 6 项 10%/20%/25% 比较，环境不一致仍优先 `not_checked`。缺场景、配置漂移、错误、payload 漂移和场景回归均有离线负向测试。该证据只提高固定 loopback workload 覆盖，不代表目标 payload、目标 IdP、目标依赖、TLS edge、远端 Linux 或生产容量；运行时性能与容量工程保守升至 9.2，精确综合评分升至 9.493。

- 标准 `net/http` HTTP/2 对照不等于 Fiber listener 已支持 HTTP/2/3。
- workflow 文件存在不等于 Linux 性能、镜像扫描、远端浏览器或供应链任务已经成功。
- 本地 OTel SDK、span 和 OTLP exporter 行为测试不等于真实 collector/trace backend 已部署，也不等于告警与故障恢复链路已闭环。

## 4. 官方与社区基线

资料于 2026-08-20 通过网络重新访问。版本和社区能力只用于定义比较基线，不作为 GoExample 已实现能力的证据。

| 来源 | 核心结论 | 对本项目的含义 |
| --- | --- | --- |
| [Fiber Config](https://docs.gofiber.io/api/fiber#config) | Fiber 提供 body、read/write/idle timeout、read buffer 和 concurrency 等 transport 配置 | 当前项目已显式接入主要容量与超时项，但仍要通过目标 edge 校准 |
| [Fiber ProxyHeader / TrustProxy](https://docs.gofiber.io/api/fiber#proxyheader) | 转发头容易伪造，必须用 `TrustProxyConfig` 校验代理来源，否则可能绕过基于 IP 的访问控制 | production 不得信任 IPv4/IPv6 全网；未命中代理 allowlist 的连接必须忽略 XFF |
| [Fiber Ctx](https://docs.gofiber.io/api/ctx) | `Ctx`/底层缓冲存在生命周期与复用约束 | handler 外不能保留请求值，业务层应继续脱离 Fiber 类型 |
| [fasthttp README](https://github.com/valyala/fasthttp/blob/master/README.md) | 官方明确多数场景 `net/http` 更易用且覆盖更多场景，fasthttp 面向特定高性能需求 | 必须用同业务 Linux 数据证明 Fiber 收益足以覆盖生态成本 |
| [`net/http.Server`](https://pkg.go.dev/net/http#Server) | 标准 server、request context、TLS/HTTP2 和 middleware 生态成熟 | 是迁移对照和长期兼容基线 |
| [`net/http.Client` / `Transport`](https://pkg.go.dev/net/http#Client) | Client timeout 覆盖连接、重定向和响应体读取；Transport 应复用并可限制连接池、阶段 timeout 和响应头 | Framework 出站 client 必须有限、可复用且尊重调用方 context，不能使用无 timeout 的默认 client |
| [Redis distributed locks](https://redis.io/docs/latest/develop/use/patterns/distributed-locks/) | 单实例正确释放必须比较随机 owner 值后删除，锁有效期和获取时间共同决定安全窗口 | 幂等锁使用 `SET NX PX`、随机 owner 和 Lua compare-and-delete，lease 大于请求预算；目标 HA 仍需另行验证 |
| [Redis `INCR` rate limiter](https://redis.io/docs/latest/commands/incr/) | 计数与首次过期设置必须放入脚本或事务，避免并发和故障造成无 TTL key | 跨实例 limiter 通过一个 Lua 脚本执行 `INCR`、`PTTL` 与首次 `PEXPIRE`，普通 Fiber Storage 读改写不计为原子实现 |
| [OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) | 资源消耗、认证、授权、错误配置和资产清单是核心风险 | body/header/连接/admission、RBAC、OpenAPI 和 Origin 门禁都应持续测试 |
| [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) | 威胁建模应持续维护范围、资产、信任边界、威胁、缓解措施和验证证据，而不是一次性清单 | 服务器模型必须逐项映射 STRIDE 风险、代码/测试、残余边界、复审触发条件和所有者；文档本身不证明生产控制 |

优点：根 Node 层只做编排；Go workspace 清楚分开 Framework、Example、Billing、两个版本化 SDK 与独立 HealthProbe consumer；`internal` 保持项目私有；环境准备、test/race/vet/vuln 和 CI 从 `go.work` 动态发现全部 module；Framework 有独立 0.1.x 版本、332 符号公共 API snapshot 和 target-branch 兼容门禁。

缺点：Example 与 Billing 仍只有仓库内消费者，SDK 与 HealthProbe 尚无已发布 module-scoped tag、外部跨版本消费者或部署迁移记录；根与 MSFront 各有 Yarn lock，升级与审计需要双重维护；需持续防止公共层吸收单项目逻辑。

### 6.2 架构分层与 Framework：9.9

优点：配置、auth、health、httpclient、observability、queueclient、server、sharedstate、sqlclient、validation 分包合理；composition root 清楚；`projectapp` 只接收 `context.Context` 与 typed input；Framework context-only/typed/authenticated/authorized query 和泛型 command 将 Fiber 注册、URI/query/header 来源隔离、最小 principal、角色门禁、JSON bind/validation、幂等、统一 envelope 和错误映射留在 adapter 内，Example 生产 `projectapi` 不导入 Fiber；query/command 定义先完整校验，静态/动态重叠、参数映射、非规范路径、同 method 大小写重复和默认 GET/POST 冲突不会因 Fiber 注册顺序静默遮蔽；authorized query 还会复制并校验 required roles，在输入绑定和 handler 前执行 403；真实 `project.get`/`project.preview`/`project.describe` child span、AST 架构、OpenAPI 路由对照与公共 API snapshot 测试阻止依赖/契约回流；Redis、SQL 与 queue 实现集中在 adapter 包，composition root 负责 driver/SDK、配置、探活、注入和关闭。

缺点：application adapter 目前覆盖静态/动态 GET/HEAD 和 JSON POST/PUT/PATCH/DELETE，尚不表达定制 middleware；高级 `RouteRegistrar`、Storage、`fiber.StructValidator`、默认 handler 和 `*fiber.App` 仍构成公共锁定；Billing 已证明第二项目可消费核心 adapter，但尚无外部项目证明发布兼容性。

### 6.3 标准生态与可替换性：9.7

补充：RunHTTP 现可直接接收并克隆调用方 tls.Config，默认最低 TLS 1.2，通过标准 ServeTLS 协商 HTTP/2；不安全版本、版本区间冲突或缺失证书来源会在监听前失败，调用方配置不会被运行期 HTTP/2 设置回写。NewHTTPHandler 还会在外层 writer 没有直接暴露 Flusher 时通过标准 ResponseController unwrap 链补充刷新能力，避免符合标准包装约定的 middleware 将流式响应缓冲到处理结束。

优点：无输入/typed/authenticated/authorized GET/HEAD 与 typed JSON command 都由 Fiber 内部 adapter 调用标准 context/结构化 application use case；typed command 支持 POST/PUT/PATCH/DELETE 且同一 adapter 边界一致；URI/query/header 通过 tags 映射，认证只暴露最小 transport-neutral principal，角色策略由 transport-neutral role IDs 声明；生产 project handler 不依赖 HTTP 框架；`NewHTTPHandler` 将组装后的应用暴露为标准 `net/http.Handler`，可直接叠加标准库 middleware/edge，并以一次性进程内桥保留 caller deadline、取消和 context value；`server.RunHTTP` 再提供标准 listener、accepted connection/read-header/read/write/idle/header 上限、draining、共享 shutdown budget 与超时强制关闭，Example 已默认接入并显式注入 application shutdown；最小连接 observer 将容量和固定状态映射为无动态标签指标，panic 不影响生命周期，90% 持续饱和有告警/runbook；TLS/HTTP2 对照能复用相同 envelope；独立 `httpclient` 直接复用标准 `net/http.Client`/`Transport` 与 OTel API，且不依赖 Fiber；`queueclient/natsjetstream` 同样把真实 NATS SDK 隔离在 broker-neutral 核心之外，以窄 publisher/consumer 接口接到既有 delivery callback；Fiber/NATS 依赖均未渗入 Example application package。

缺点：定制 application middleware 的项目路由仍需 Fiber 注册器，大量依赖 fasthttp 原生对象的 middleware 仍不能直接替换；原生 Fiber listener 不经过标准 context bridge，仍由主动 request deadline 与 shutdown hook 兜底；标准 server 只有本地指标/规则，没有目标 TLS/HTTP2/3、Prometheus/APM 或 paging 运行证据；JetStream adapter 不管理 stream/consumer，也没有第二 broker adapter 或目标 broker 业务接入；adapter 有转换与维护成本；Gin/Echo/Hertz 尚无同业务对照；新出站 client 尚无真实业务消费者。

### 6.4 API、Schema 与兼容契约：10.0

优点：OpenAPI 3.1 是 inventory 的事实源；runtime route 与文档 operation 有自动对照；结构化兼容比较器解析本地 `$ref`，PR 使用 base SHA 阻断 operation/response/parameter/property 移除、认证收紧和 schema 不兼容变化，并进一步覆盖方向敏感的 type/nullability、参数序列化/content、请求 encoding、discriminator、响应 header schema/content 和新增响应 media type；9 个 Node fixture 锁定破坏性变更失败及请求放宽、响应收窄、header 大小写变化的兼容路径。Billing 生成 SDK 的全部公开方法均实际穿过独立服务的 Framework handler，并映射回发布 operation 的 method/path，带参数方法还验证 query、JSON body 和业务响应，阻止清单、调用实现和服务 adapter 独立漂移；三个兼容健康 operation 已标记 `deprecated: true`，200/503 均返回并声明 RFC 9745 `Deprecation`、RFC 8594 `Sunset` 和 successor `Link`，CORS 可见且标准探针无误标，迁移窗口为 184 天；JSON media type、body limit、validation、统一 envelope 和 RBAC path policy 都有测试；普通密码登录 401 与受保护资源 Bearer 401 已拆分，OpenAPI 明确 `WWW-Authenticate`，Go 契约测试要求所有声明 security 的操作引用 Bearer 401；Example preview 还声明并测试 `x-required-roles: [demo]` 与统一 403；Go 幂等 key 绑定 method、原始 target、认证 subject、规范化 media type 和原始 body 的 SHA-256 指纹，同 key 不同请求返回禁缓存 409，同指纹才回放；MSFront 请求体使用 Zod 且限制最大字节与错误条目数。

### 6.5 协议与网络：8.9

补充：标准 listener 的直接 TLS 路径已用临时 CA/证书完成真实 TLS 1.2+ 与 HTTP/2 协商测试；TLS 包装后的 hijacked HTTP/1.1 upgrade 连接也会在停机时被底层连接跟踪器关闭。刷新桥只在最多 32 层 `Unwrap()` 链可到达 `http.Flusher` 或 `FlushError() error` 时暴露能力，不透明与循环 writer 保持原样。`SendServerSentEvents` 进一步固定 EventSource wire format、UTF-8/字段/大小边界、心跳和无内部队列的逐事件刷新；真实 HTTP/1.1 与 TLS/HTTP2 测试证明首事件和心跳可在流保持活动时送达。恢复 source 在响应头写出前接收最多 1024 bytes 的安全 `Last-Event-ID` 和同一有界 context，两种协议都证明游标传递与流完成后的 producer 取消。

缺点：固定 Nginx Docker runner 已定义但本机无 Docker 实跑且没有远端成功 artifact，更没有目标 Nginx/Ingress/cloud LB、真实证书/DNS 或 HTTP/3 证据；Fiber listener 无 HTTP2/3；标准入口 SSE 仍没有目标 edge buffering/断连/容量、浏览器实际重连、持久化 replay store 的缺口恢复/去重/跨副本一致性或长稳内存上限测试，WebSocket 也没有应用协议契约；标准 listener 连接饱和已有本地固定指标，但目标 edge 的拒绝/排队语义和遥测仍未验证。

### 6.6 中间件与应用安全：10.0

优点：request ID、trace、日志、metrics、recover、Helmet、HSTS、CORS、rate limit、deadline、idempotency 顺序明确；客户端 Request ID 在日志链路前执行 128 字节与安全字符集校验，非法值换发且原值不进入日志；代理 IP allowlist 控制 XFF 是否可影响限流主体，production 拒绝明显的 IPv4/IPv6 全网信任，可信/不可信行为有真实 TCP 契约；diagnostics token 常量时间比较；production 禁止默认 JWT secret，并由 Next production-server 配置门禁校验 JWT 密钥长度/默认值和可信 Origin 格式，instrumentation 复用同一规则做纵深校验；错误配置已通过真实 `next start` 负向实验验证以非零状态退出；Go auth login/me、所有统一错误 envelope、失败和限流响应及 MSFront cookie/API 均返回 `no-store, no-transform` 与 `Pragma: no-cache`；`/api/v1` 的流安全缓存验证器只为缓冲响应生成弱 ETag，对禁存储响应移除 ETag，并且不会读取流 body；MSFront 私有 JSON 响应和会话状态重定向也统一禁止缓存转换，并有 Vitest、proxy 行为测试、Route Handler、Node 守卫与生产 E2E 断言；MSFront cookie 使用 HttpOnly/SameSite/Secure；所有受保护 route 执行会话、Origin 与角色路径策略；所有 auth、system、management API 通过统一 helper 返回禁缓存响应。服务器侧另有受 Node 守卫和证据清单保护的威胁模型，记录数据分类、信任边界、15 项 STRIDE 风险、现有控制与生产残余边界；认证、typed query 角色拒绝和诊断授权决策使用固定事件/结果/原因并关联 request/trace/span，行为测试拒绝用户名、密码、token、Authorization、body、raw URL、IP、subject、role、claims 和任意错误文本进入审计事件。

### 6.7 身份、会话与授权：9.91

优点：Go demo JWT 限制算法/issuer/audience、必需 claims、最大年龄和角色边界；通用 `TokenVerifier` 与 RS256 JWKS verifier 固定 issuer/audience、RSA/token/JWKS/刷新预算，`VerifyIDToken` 固定 sub/nonce/azp/auth_time/iat，并以默认关闭的策略要求精确 ACR、全部 AMR 和 fresh auth_time；authorization request 发送同一有界 `acr_values` 提示，但 callback 独立验证签名 claims，缺失、过期、重复、malformed 或 mismatch 均失败关闭。`AuthorizationRequestManager`、`OIDCClient`、`CompleteOIDCCallback` 和 `SessionManager` 覆盖 PKCE/state/nonce、discovery/exchange、一次性 callback 与 hash-only refresh rotation/reuse/revoke。可注入 `AuthorizationRequestStore` 让 state 只以 SHA-256 索引，Redis Lua 在全局数量门禁下跨 client 原子消费 verifier/nonce payload；HTTP 使用 context-aware start/complete，双 callback 并发仅一个成功，tamper/expiry/outage 均失败关闭。`BrowserSessionManager` 再提供受 access-token `exp` 截断、全局及单用户限量、credential 仅存 hash 的 opaque session，以公开随机 ID 和 subject SHA-256 提供低敏稳定排序清单、subject 绑定单 session/整用户撤销；可选 inventory store 不破坏旧 store 接口，Redis Lua 跨 client 原子执行限量/撤销且故障 fail closed。非安全 cookie 请求必须通过 Strict CSRF cookie/header 双提交和服务端 hash 绑定，logout 立即撤销，显式 Bearer 始终优先。demo 与 OIDC 配置互斥，production browser OIDC 强制 external shared state，外部 token/session 可进入真实 project route。transport-neutral `authorization.Authorizer` 以 deny-by-default decision 和有界 principal/tenant/type/ID/action/attributes 固定策略输入；四种 typed query/command adapter 保证 Bearer -> role -> bind -> resource policy -> handler，command 的 deny 还先于 precondition/幂等状态。策略 error、非法 decision、timeout、panic 固定脱敏为 403，资源格式错误固定 400。Example preview/describe 已接入 subject-owned tenant 与 environment attribute policy；缺省 tenant 保持旧客户端兼容，显式跨租户由 no-span/privacy/idempotency 无污染测试、OpenAPI 扩展和 SDK 锁定。Go 登录、session、Bearer/角色/资源拒绝与 diagnostics 决策有低敏审计和有界 sink；MSFront 既有 JWT/RBAC/Origin/cookie 边界保持不变。

缺点：仓库仍没有目标 IdP 的实际 MFA enrollment/challenge/recovery 与 claim mapping；现有 session inventory 没有设备管理 UI/指纹。Redis-backed authorization/session stores 和本地 HTTP 契约不能替代生产 Redis HA、KMS/Vault、目标 IdP/DNS/TLS/密钥轮换、生产集中撤销和身份故障制品；Go 与 MSFront 仍维护两套 demo/本地身份逻辑；Example ownership policy 是本地静态示例，不是生产 policy engine、关系/属性数据源或策略版本/分发/缓存失效/管理审计证明；本地审计无已部署不可篡改存储、留存/删除、SIEM/paging 和具名责任人。

### 6.8 并发、超时与生命周期：9.98

优点：`HTTP_MAX_CONNECTIONS` 与 `HTTP_MAX_IN_FLIGHT` 分别约束 transport 和业务容量；admission 非阻塞且探针不占 slot；draining 拒绝新业务并保留已有请求；deadline 与 shutdown 能取消协作式 handler；默认 `NewHTTPHandler` 路径额外传播 caller 取消、较短 deadline 和真实标准 TCP 断连。SSE 在 handler 返回后将请求 context 的取消所有权移交给 stream producer，并以 `sync.Once` 统一回收 application cancellation hook 与 deadline；HTTP/1.1、HTTP/2 断连和 `RunHTTP + app.ShutdownWithContext` 行为测试证明活动 producer 有界退出。真实慢读 TCP 契约证明 `WriteTimeout` 能终止受背压响应，计数 listener 证明 shutdown 后 idle keep-alive 连接归零；标准 listener 还包装受限连接，在 `StateHijacked` 时登记升级连接、应用自行关闭时移除，并在共享停机流程后关闭其余连接，真实 101 upgrade 测试证明 `RunHTTP` 返回后客户端不再保持开放；标准出站 client 对总请求、连接、TLS、响应头、idle 和每主机连接均设置有限预算，真实测试覆盖总超时与调用方取消；queue worker 的 `ReceiveDelivery` 模式以最多 10 次 attempt、有限指数退避和独立结算 timeout 约束 handler/ack/DLQ，并让父 context 取消在 handler、退避和结算阶段正常收敛；health cache 有请求合并；read/write 不超过 idle，read/write/request 加 drain 必须分别小于 shutdown。

缺点：原生 Fiber listener 下客户端断开仍不会及时取消 application context；queue worker 的仓库内 retry/ack/DLQ 依赖 callback 尊重 context，Go 无法终止无视取消的 adapter，且目标 broker redelivery、持久化与恢复仍未闭环；标准 listener 已有容量/open/state 指标，但 Fiber direct-listener 503 和目标 edge 饱和仍无统一 counter；hijacked 连接仅验证有界强制关闭，WebSocket 尚无应用协议 graceful close，SSE 也缺目标 edge drain、浏览器重连和目标规模长稳内存曲线证据；本轮定向 Windows race 二进制因本机 GCC side-by-side 配置错误未能启动。

### 6.9 运行时性能与容量：9.3

优点：存在真实 TCP 三路径 transport benchmark。固定 9 个 workload 以 keep-alive 并发 1/2/4/8/16/32/64/128 和连接 churn 形成 9 × 3 矩阵，明确区分 Fiber、手写原生 `net/http` 迁移基线，以及经过 `projectapi.Queries -> httpapi.New -> httpapi.NewHTTPHandler` 的真实 Framework 标准入口；三条路径先通过相同 project envelope 等价性门禁，再以 5 轮结构化数据记录 payload、throughput、p50/p95/p99、错误率、连接获取/拨号/在途峰值、alloc/malloc、GC、goroutine 与 Linux FD。完整 Framework app 的大响应、认证拒绝和依赖延迟场景继续以 Fiber 与 `framework-net-http` 形成 3 × 2 × 5 矩阵。schema v5 Node 报告器拒绝不完整、篡改、错误和 payload 漂移，输出原生方向比、Framework adapter 相对 Fiber/原生基线的比值，以及三条路径首次达到观测峰值吞吐 90% 的经验饱和并发；同环境历史比较覆盖 27 项容量和 6 项场景的吞吐/p95/p99 阈值。带 SHA-256 的 `environmentFingerprint` 固定 runner OS/arch/image、CPU model/logical CPUs、Go version 和 `GOMAXPROCS=2`，准入器复算摘要，只有指纹一致才执行阈值；合法环境差异会输出逐字段 mismatch，历史 schema v4 则以 `report_schema_migration` 清除旧 baseline 并明确降级。CI 只从同仓库默认分支成功的 push/manual run 选择未过期 candidate，拒绝 PR 来源；另有并发 32、5 秒分窗的 opt-in 双路径 soak，CI 固定 30 秒/transport。Linux workflow 保存进程 CPU/RSS、前后 socket/网络/内存/FD limit、Go benchmark 趋势输入及 CPU/heap profile/文本摘要，manifest 要求 benchmark、baseline 来源/candidate 与 soak 制品完整。

## 7. 性能瓶颈判断

当前没有证据证明 Fiber 是瓶颈，也没有证据证明它带来足够业务收益。实际生产瓶颈更可能依次出现在 PostgreSQL 查询与连接池、外部探测、序列化与前端 BFF、日志/观测出口、共享状态，以及最后才是路由器。继续做 hello-world QPS 优化价值有限。

下一步应先让当前固定 Linux 阶梯矩阵、baseline candidate 与短时 soak 在默认分支连续成功至少两次，核验受信历史报告确实被自动选择、环境指纹一致并通过阈值；若 hosted runner 指纹持续变化，应建立明确的同规格自托管 runner 池，而不是放宽比较字段。随后再扩展目标 payload、认证失败、数据库/RPC 延迟和 TLS/edge，并在目标负载下复用同一预设规则确认容量拐点，补队列等待、小时/天级目标依赖长稳与取消后残留任务。只有 profile 显示 HTTP/JSON 热路径占主导，且方向比在目标负载中稳定达到 ADR 门槛，才值得继续做 Fiber 微优化。

## 8. 到 10 分的必要条件

1. 用目标 Linux/edge/数据库 workload 完成 Fiber 与至少一个 `net/http` 方案的可追溯决策。
2. 所有业务 use case 脱离 Fiber pooled context，Framework 有版本与兼容策略，并被第二个真实项目消费。
3. 目标 edge HTTP/2/3、header、timeout、buffering、disconnect、streaming 和 drain 契约自动化。
4. 在目标 Redis TLS/ACL 与 Sentinel/Cluster 拓扑运行现有共享 limiter/idempotency 契约，并补齐 failover、eviction、网络分区、容量、延迟、告警及 session/revocation。
5. 目标 IdP/MFA、设备管理 UI/指纹、生产集中撤销、secret manager，以及具备完整性、访问控制、留存/删除、SIEM/paging 与具名责任人的审计闭环。
6. 将现有 Redis/SQL/queue instrumentation 和 exporter retry 在目标环境贯通，并完成生产业务出站/SQL/queue 调用链、真实 broker/collector/trace backend、dashboard、SLO 告警与受控故障演练。
7. PostgreSQL deadlock/failover/容量/备份恢复/PITR 达到记录的 RPO/RTO。
8. Kubernetes/等价平台完成多副本、PDB/HPA、rolling update、节点驱逐和 rollback 演练。
9. 镜像签名、SLSA provenance、部署验签和远端 CI artifact 持续可追溯。
10. MSFront bundle/Lighthouse/Web Vitals、多浏览器与生产多实例缓存/会话语义闭环。
