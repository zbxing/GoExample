# GoExample 项目架构与性能评估（V11）

评估日期：2026-08-20
评估范围：根工作区、Go Framework、Proj/Example、协议、测试、CI、容器、供应链、观测与部署证据；本轮增量扫描与优化明确排除 MSFront，前端维度沿用 V10 已验证基线且不因本轮加分
比较基线：Go `net/http`、Chi、Gin、Echo、Fiber/fasthttp、CloudWeGo Hertz、Next.js、PostgreSQL、Prometheus/OpenTelemetry 与 Kubernetes 生产实践
综合评分：**9.0/10**（精确加权值 **8.960/10**，满分 10）
目标评分：**10.0/10**，但只有目标环境运行、故障演练和可追溯证据完成后才能达到

## 1. 执行结论

GoExample 已经具备成熟工程模板的多数基础：工作区边界清楚，Go 服务有真实 TCP 生命周期契约、显式连接与请求容量限制、健康探针、优雅停机、结构化日志、低基数 Prometheus 指标、官方 OpenTelemetry server/use case span、OpenAPI 对照和严格配置门禁；MSFront 既有基线具备 Next.js App Router、服务端鉴权、角色策略、数据库/文件双存储、请求体上限、Origin 校验、浏览器 E2E 与可访问性测试；CI 还覆盖 Go race/vet/vulnerability、前端 lint/typecheck/test/build、CodeQL、SBOM 和依赖审查。本轮没有修改或重新给 MSFront 加分。

项目当前最强的部分是本地工程治理、HTTP 生命周期测试和持续质量门禁。最弱的部分不是代码格式或单元测试，而是生产闭环：没有真实外部共享状态实现、真实 OTel collector/trace backend、目标 edge HTTP/2/3 契约、PostgreSQL 故障与恢复演练、Kubernetes/等价编排、签名发布、远端 Linux benchmark artifact 和持续运行记录。Fiber/fasthttp 的客户端断连取消差异也已被真实 TCP 实验证明，仍只能依赖主动 deadline 兜底。

V10 将 V9 的 16 个维度扩展为 18 个，并单独评价身份会话、恢复演练和生产证据，因此与 V9 的 9.063 不直接可比。按 V10 口径，扫描初始值为 8.753；第一批超时预算、logout CSRF 与移动端 WCAG 修复后为 8.793；第二批补齐 write/shutdown 预算、慢请求体 TCP 契约、认证响应禁缓存及严格 JWT claims 后升至 8.823；本轮先将所有受保护 management/system API 统一为 `privateJson` 禁缓存响应并升至 8.831，再补齐 Go JWT 必需 claims、最大年龄与角色边界升至 8.836，随后将 Go auth login/me、失败和限流响应统一禁缓存并升至 8.844，收敛所有 Go 错误 envelope、认证私有响应的 `no-store, no-transform`、`Pragma` 和 ETag 移除契约升至 8.852，将 MSFront 私有响应策略同步为 `no-store, no-transform` 并由单测/E2E 守卫升至 8.860，最后将会话状态页面重定向也纳入禁缓存策略并由 proxy 单测、Node 守卫和生产 E2E 升至 8.868。本轮在 Next `PHASE_PRODUCTION_SERVER` 配置加载阶段对生产 JWT 密钥和 `MSFRONT_TRUSTED_ORIGINS` 做 fail-fast 校验，instrumentation 保留同规则的运行时纵深校验；两项非法配置均经真实 `next start` 验证以退出码 1 终止，并由 60 个前端单测、路由契约、类型检查和生产构建验证，升至 8.876；随后按 RFC 6750 锁定 Bearer challenge 行为、CORS 可见性并拆分 OpenAPI 普通 401 与 Bearer 401 契约，升至 8.882；再为 Go 生产 JWT、metrics 和 pprof 建立 secret 域隔离启动门禁，升至 8.887；按 RFC 7519 为 Go JWT 增加可配置且强制验证的 audience，缺失和错误 `aud` 均由负向测试拒绝，升至 8.892；按 OWASP 日志治理基线限制客户端 Request ID，非法值在日志前换发并以无标签指标计数，升至 8.898；依据 Fiber 代理信任安全要求禁止 production 全网代理 CIDR，并以真实 TCP 验证 XFF 信任边界，升至 8.906；修复请求日志与 ETag 对流响应的物化，真实 TCP 证明慢读连接会安装并触发 socket 写超时、流生产提前终止，升至 8.912；V11 再将幂等 key 绑定 method/target/principal/media type/body SHA-256 指纹，不同请求复用 key 返回 409，并补齐 keep-alive 复用与 idle 回收、TCP 半关闭和 shutdown 连接归零契约，升至 8.924；随后增加结构化 OpenAPI breaking-change 比较器、PR base SHA 门禁和正反 fixture，升至 8.930；最后接入官方 OTel SDK、server/use case span 与有界 OTLP/HTTP exporter，以行为测试验证低敏属性、远端父上下文、protobuf wire contract、慢 collector 非阻塞和 shutdown flush，升至 8.942。提分均对应真实失败门禁与自动测试，不是文档加分。

在此基础上，三个 `/api/health*` 兼容 operation 增加运行时弃用头、精确 successor、CORS 可见性、OpenAPI response header 契约和 184 天迁移文档，成功与 503 路径均有行为测试，精确值升至 8.948。

随后 Framework 增加只接收标准 `context.Context` 的 `ApplicationQuery` adapter，Example 生产 project route 与 composition root 移除 Fiber import，并由 AST 架构测试、trace/deadline、错误脱敏和配置冲突测试锁定，精确值升至 8.960。

## 2. 证据边界

### 2.1 已实测

- `yarn test` 覆盖根 Node 守卫、Go modules、MSFront 单元测试与路由授权契约。
- `yarn race:server`、`yarn vet:server`、`yarn build:server` 可在本地重复执行。
- 真实 TCP 覆盖 TLS/HTTP/1.1、标准 `net/http` TLS/HTTP/2 对照、loopback HTTP/2 edge、请求 deadline、server shutdown、客户端断连限制、请求头 431、慢请求头/请求体 408、连接容量 503、应用 admission、draining、未知长度流式响应、慢读客户端 write timeout、keep-alive/idle 回收、TCP 半关闭和停机连接归零。
- OpenTelemetry 行为测试覆盖 server span kind/name/远端 parent/低敏属性、application child span、OTLP/HTTP protobuf 路径、慢 collector 非阻塞和 provider shutdown flush。
- API 生命周期行为测试覆盖三个兼容健康路由的 200/503 弃用头、successor 映射、CORS 可见性、标准探针无误标和 OpenAPI response header 声明。
- Framework application query 行为测试覆盖 context/trace/deadline、统一 envelope、错误脱敏、默认路由共存、非法定义和注册模式冲突；AST 门禁覆盖 Example 生产 projectapi 与 composition root 无 Fiber import。
- MSFront 单元测试覆盖 Origin 策略、启动配置 fail-fast、服务端授权、请求体限制、数据库配置、probe allowlist、登出 CSRF、JWT claims/最大年龄和认证响应禁缓存。
- evidence manifest 会记录输入、artifact SHA-256、Git/toolchain 和未验证边界。

### 2.2 仅有代码或静态配置

- GitHub workflows、Docker build、CodeQL、SBOM、dependency review 和 Linux transport benchmark 已定义，但当前工作区没有可核验的远端成功 run 链接或 artifact。
- Prometheus recording/alert rules 已定义，但本机没有 `promtool`、运行中的 Prometheus/Alertmanager 或告警演练。
- OTel SDK 与 exporter 已实现，但当前只有本地假 collector wire 测试，没有真实 collector、trace backend、outbound/database instrumentation 或 exporter drop/retry 运行指标。
- MSFront 有 PostgreSQL migration、pool timeout 和集成脚本，但当前没有数据库运行、故障切换、恢复或目标数据量证据。
- production external shared-state 模式会 fail-fast，但仓库没有 Redis/等价 `Storage` 与分布式 `Locker` 实现。

### 2.3 不得据此宣称完成

- loopback reverse proxy 不等于 Nginx、Envoy、Ingress 或云负载均衡生产 edge。
- 标准 `net/http` HTTP/2 对照不等于 Fiber listener 已支持 HTTP/2/3。
- workflow 文件存在不等于 Linux 性能、镜像扫描、远端浏览器或供应链任务已经成功。
- 本地 OTel SDK、span 和 OTLP exporter 行为测试不等于真实 collector/trace backend 已部署，也不等于告警与故障恢复链路已闭环。
- 数据库 schema 和 repository 不等于备份、PITR、RPO/RTO 或故障恢复已验证。

## 3. 项目结构扫描

```text
GoExample
├── package.json / scripts/              根级跨工具链编排
├── Framework/                           Go 公共 module
│   ├── auth / config / health
│   ├── httpapi                          Fiber adapter、中间件与真实 TCP 契约
│   ├── observability                    日志、指标、W3C trace context
│   ├── server                           listener、draining、shutdown
│   └── validation
├── Proj/Example/                        唯一真实 Go 项目
│   ├── cmd/server                       composition root
│   ├── internal/projectapp              transport-neutral use case
│   └── internal/projectapi              Fiber 与 net/http 对照 adapter
├── MSFront/                             Next.js 16 管理控制台与 BFF
│   ├── app/api                          服务端访问守卫
│   ├── lib/server                       auth、RBAC、数据库、probe、repository
│   ├── database/migrations              PostgreSQL schema/migration
│   └── __tests__                        单元、契约与浏览器测试
├── deploy/prometheus/                   SLO recording/alert rules
├── docs/openapi / adr / observability   契约、决策与运行手册
├── .github/workflows                    质量、安全、浏览器、供应链、benchmark
└── __test__                             跨模块守卫与 E2E
```

当前 Go 请求路径：

```text
TCP/TLS -> fasthttp/Fiber
        -> request-id -> trace -> log -> metrics -> recover -> security/CORS
        -> /api deadline -> rate limit
        -> /api/v1 draining -> admission
        -> Fiber adapter -> typed projectapp use case
```

当前管理控制台路径：

```text
Browser -> Next.js proxy cookie validation
        -> route requireApiAccess
        -> Origin check + current user lookup + role/path policy
        -> file repository or PostgreSQL pool
        -> optional allowlisted Go health probes
```

## 4. 官方与社区基线

资料于 2026-08-20 通过网络重新访问。版本和社区能力只用于定义比较基线，不作为 GoExample 已实现能力的证据。

| 来源 | 核心结论 | 对本项目的含义 |
| --- | --- | --- |
| [Fiber Config](https://docs.gofiber.io/api/fiber#config) | Fiber 提供 body、read/write/idle timeout、read buffer 和 concurrency 等 transport 配置 | 当前项目已显式接入主要容量与超时项，但仍要通过目标 edge 校准 |

| [fasthttp README](https://github.com/valyala/fasthttp/blob/master/README.md) | 官方明确多数场景 `net/http` 更易用且覆盖更多场景，fasthttp 面向特定高性能需求 | 必须用同业务 Linux 数据证明 Fiber 收益足以覆盖生态成本 |

| [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#event-collection) | 跨信任区日志事件数据应校验格式并清理 CR/LF 与分隔字符，字段长度和类型应一致且有文档 | 客户端 Request ID 必须在日志链路前限制长度和字符集；拒绝事件计数不得携带原值标签 |

| [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) | secret 应遵循最小权限、受控访问和轮换，避免一个凭据扩大到无关信任域 | JWT 签名、metrics 和 pprof 凭据必须使用独立随机材料；本地隔离门禁仍不能替代 KMS/Vault 与轮换平台 |
| [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/instrumentation/) | 完整可观测性需要 SDK、instrumentation、context propagation 和 exporter | SDK、server/use case span 与可选 OTLP exporter 已接入；真实 collector、outbound/database instrumentation 和运行告警仍未闭环 |

| [PostgreSQL connections](https://www.postgresql.org/docs/current/runtime-config-connection.html) | `max_connections` 会直接影响资源，应用池必须受限 | MSFront pool 有上限与 timeout，但需目标数据库容量验证 |
| [Kubernetes Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) | readiness、SIGTERM、grace period 和 lifecycle hook 决定滚动停机行为 | 当前应用 draining 逻辑较好，但无真实编排演练 |
| [Next.js deployment](https://nextjs.org/docs/app/getting-started/deploying) | 自托管需要明确 build/runtime、缓存、代理和多实例边界 | 当前前端 build 有门禁，但没有生产容器、缓存一致性和多实例会话验证 |

## 6. 全量优缺点

### 6.1 Workspace 与模块治理：9.4

优点：根 Node 层只做编排；Go workspace 清楚分开 Framework 与项目；`internal` 保持项目私有；前后端、部署、文档和跨模块测试目录职责明确；脚本支持未来按 `GO_PROJECT` 选择项目。

缺点：只有 Example 一个 Go 消费者；Framework 没有独立版本、changelog、弃用窗口和兼容矩阵；根与 MSFront 各有 Yarn lock，升级与审计需要双重维护；需持续防止公共层吸收单项目逻辑。

### 6.2 架构分层与 Framework：9.3

优点：配置、auth、health、observability、server、validation 分包合理；composition root 清楚；`projectapp` 只接收 `context.Context` 与 typed input；Framework `ApplicationQuery` 将 Fiber 注册、统一 envelope 和错误映射留在 adapter 内，Example 生产 `projectapi` 与 `cmd/server` 不再导入 Fiber；AST 架构测试阻止依赖回流；共享状态通过接口注入并在 production fail-fast。

缺点：`ApplicationQuery` 目前只覆盖无请求体 GET；高级 `RouteRegistrar`、Storage、`fiber.StructValidator`、默认 handler 和 `*fiber.App` 仍构成公共锁定；没有后台 worker 生命周期抽象；没有第二项目证明 Framework API 是真实公共需求。

### 6.3 标准生态与可替换性：7.9

优点：同一 project use case 已有 Fiber 内部 adapter 与 `net/http` 对照；生产 project handler 只依赖标准 context 和结构化数据；TLS/HTTP2 对照能复用相同 envelope；Fiber 依赖未渗入 Example 生产 projectapi、composition root 或 application package。

缺点：带 path/query/body/header 输入的项目路由仍需 Fiber 注册器；大量标准 `http.Handler`、`RoundTripper` 和 APM middleware 不能直接复用；断连 context 语义不同；adapter 有转换与维护成本；Gin/Echo/Hertz 尚无同业务对照。

### 6.4 API、Schema 与兼容契约：9.9

优点：OpenAPI 3.1 是 inventory 的事实源；runtime route 与文档 operation 有自动对照；结构化兼容比较器解析本地 `$ref`，PR 使用 base SHA 阻断 operation/response/parameter/property 移除、认证收紧和 schema 不兼容变化，允许的可选增量与失败路径均有 Node fixture；三个兼容健康 operation 已标记 `deprecated: true`，200/503 均返回并声明 RFC 9745 `Deprecation`、RFC 8594 `Sunset` 和 successor `Link`，CORS 可见且标准探针无误标，迁移窗口为 184 天；JSON media type、body limit、validation、统一 envelope 和 RBAC path policy 都有测试；普通密码登录 401 与受保护资源 Bearer 401 已拆分，OpenAPI 明确 `WWW-Authenticate`，Go 契约测试要求所有声明 security 的操作引用 Bearer 401；Go 幂等 key 绑定 method、原始 target、认证 subject、规范化 media type 和原始 body 的 SHA-256 指纹，同 key 不同请求返回禁缓存 409，同指纹才回放；MSFront 请求体使用 Zod 且限制最大字节与错误条目数。

缺点：部分 response schema 仍较泛化；没有自动生成 SDK；缺消费者版本矩阵和真实版本迁移演练；组合 schema 变化采取保守阻断而非语义证明；Go 与 Next 错误 envelope 仍有两种格式。

### 6.5 协议与网络：8.3

优点：Fiber TLS/HTTP1.1、标准 TLS/HTTP2、loopback edge、431、慢 header/body 408、连接容量 503、未知长度 streaming 和超时均走真实 socket；慢读客户端契约使用受控 TCP 缓冲区制造背压，观测服务端安装写截止时间、底层 socket 返回 timeout 且流生产未完整结束；同一 TCP 连接连续 HTTP/1.1 请求、idle timeout 回收、客户端 `CloseWrite` 后完整响应及 shutdown 后 active connection 归零均有契约；header/body/connection/admission 均有显式上限；可信代理 CIDR 经过解析，production 拒绝 IPv4/IPv6 `/0`，真实 TCP 证明未受信连接不能用 XFF 改写客户端 IP；read/write/idle/drain/shutdown 组合预算均有启动门禁。

缺点：无目标 Nginx/Envoy/Ingress/cloud LB 契约；Fiber listener 无 HTTP2/3；没有目标 edge 下的慢 reader/writer、上传中断、SSE/WebSocket、流式断连与内存上限测试；transport 连接拒绝发生在 middleware 前，标准客户端可能只看到连接错误且无应用指标。

### 6.6 中间件与应用安全：9.9

优点：request ID、trace、日志、metrics、recover、Helmet、HSTS、CORS、rate limit、deadline、idempotency 顺序明确；客户端 Request ID 在日志链路前执行 128 字节与安全字符集校验，非法值换发且原值不进入日志；代理 IP allowlist 控制 XFF 是否可影响限流主体，production 拒绝明显的 IPv4/IPv6 全网信任，可信/不可信行为有真实 TCP 契约；diagnostics token 常量时间比较；production 禁止默认 JWT secret，并由 Next production-server 配置门禁校验 JWT 密钥长度/默认值和可信 Origin 格式，instrumentation 复用同一规则做纵深校验；错误配置已通过真实 `next start` 负向实验验证以非零状态退出；Go auth login/me、所有统一错误 envelope、失败和限流响应及 MSFront cookie/API 均返回 `no-store, no-transform` 与 `Pragma: no-cache`；`/api/v1` 的流安全缓存验证器只为缓冲响应生成弱 ETag，对禁存储响应移除 ETag，并且不会读取流 body；MSFront 私有 JSON 响应和会话状态重定向也统一禁止缓存转换，并有 Vitest、proxy 行为测试、Route Handler、Node 守卫与生产 E2E 断言；MSFront cookie 使用 HttpOnly/SameSite/Secure；所有受保护 route 执行会话、Origin 与角色路径策略；所有 auth、system、management API 通过统一 helper 返回禁缓存响应。

缺点：启动校验只覆盖格式和明显不安全默认值，不能替代 KMS/Vault、密钥轮换或集中撤销；Go demo auth 仍是单用户 HS256 示例；MSFront 登录未提供多实例共享防爆破机制；无 OIDC/JWKS/MFA、secret manager、rotation、break-glass 和集中撤销；外部 limiter/locker 尚未实现；没有完整 threat model、审计保留和敏感数据分类；metrics 等非业务基础设施响应仍需按各自协议决定是否允许压缩。

### 6.7 身份、会话与授权：8.0

优点：Go JWT 限制算法与 issuer，签发并强制验证配置的 audience，强制 `sub`/`iat`/`nbf`/`exp`/`jti`、最大年龄及有界且一一对应的角色 claims，缺失/错误 `aud` 均有负向测试；Go production 配置强制 JWT、metrics 与启用的 pprof 使用不同 secret，三种跨域复用均有负向测试；MSFront JWT 限制算法、issuer、audience，强制 `sub`/`iat`/`exp` 并限制 12 小时最大年龄，畸形角色 claims 整体拒绝；MSFront 每次请求重新读取当前用户状态与角色；RBAC policy 与 route inventory 有自动守卫；cookie 安全属性合理；状态变更要求可信 Origin。

缺点：无 Authorization Code + PKCE、nonce/state、JWKS rotation；无 refresh token family、重用检测、设备会话、集中 revoke 和 MFA；Go 与 MSFront 维护两套 demo/本地身份逻辑；权限模型缺租户与资源级授权证明。

### 6.8 并发、超时与生命周期：9.9

优点：`HTTP_MAX_CONNECTIONS` 与 `HTTP_MAX_IN_FLIGHT` 分别约束 transport 和业务容量；admission 非阻塞且探针不占 slot；draining 拒绝新业务并保留已有请求；deadline 与 shutdown 能取消协作式 handler；真实慢读 TCP 契约证明 `WriteTimeout` 能终止受背压响应，计数 listener 证明 shutdown 后 idle keep-alive 连接归零；health cache 有请求合并；read/write 不超过 idle，read/write/request 加 drain 必须分别小于 shutdown。

缺点：客户端断开不会及时取消 Fiber application context；无 worker、scheduler、queue consumer 停止顺序；transport 503 无应用层 counter；尚无长连接 drain 与 shutdown 内存/连接收敛测试。

### 6.9 运行时性能与容量：8.6

优点：存在真实 TCP 双 transport benchmark、5 轮 Linux workflow、p50/p95/p99、错误率、CPU/heap profile 和进程 CPU/RSS 采集入口；Go 热路径限制 metrics label；MSFront probe 有 timeout、TTL cache 与请求合并；PostgreSQL pool、statement/query/connect/idle timeout 均有上限。

缺点：没有可核验 Linux artifact；workload 仍偏小，缺认证失败、数据库/RPC 延迟、TLS edge、不同 payload/并发和连接 churn；无 benchstat 趋势、容量拐点、GC/FD/网络/队列指标；MSFront 无 bundle budget、Lighthouse 和生产 Web Vitals。

### 6.10 可观测性与 SRE：9.4

优点：结构化日志关联 request/trace/span；请求日志不会为计算响应字节而物化 body，未知长度流明确记录 `response_bytes=-1`；官方 OTel server span 严格传播 W3C parent/tracestate，只记录 route template、method 和 status，Example `project.get` use case 是其真实 child；可选 OTLP/HTTP exporter 使用 ParentBased ratio sampling 与有界非阻塞 batch queue，慢 collector 不阻塞请求且 shutdown 会 flush；客户端 Request ID 只接受不超过 128 字节的安全 token，非法值在日志前换发，原值不写日志且由无标签 counter 观测；Prometheus 指标含请求、直方图、in-flight、admission/draining、runtime/GC；SLO rules 定义 availability、latency 和 burn rate；runbook 明确未验证边界。

缺点：没有真实 OTel collector/trace backend；无 outbound/database instrumentation 和 exporter drop/retry 指标；无 dashboard、远端 Prometheus、Alertmanager 和告警演练；transport 连接拒绝不可从当前应用 metrics 直接观察。

### 6.11 数据一致性与持久化：8.1

优点：MSFront 支持 file/database driver，database 模式缺 URL 时失败；SQL 使用参数绑定；pool 与查询超时有边界；migration/integration 脚本存在；项目更新使用数据库版本字段；probe 与 inventory 读路径有缓存；Go 幂等响应与请求指纹使用隔离命名空间和不短于响应的 TTL，指纹仅保存定长摘要并由同一路由锁保护。

缺点：文件存储不适合多实例；数据库更新未形成完整 optimistic concurrency/ETag 冲突契约；无 deadlock/serialization retry、连接耗尽、锁等待与 failover 测试；无备份/PITR/RPO/RTO；无目标数据量 `EXPLAIN ANALYZE BUFFERS`。

### 6.12 前端架构、性能与可访问性：9.2

优点：Next.js App Router、server-only repository、typed routes、Zod、BFF access guard 和 SSR 边界清楚；axe 双视口与 production build E2E 已通过桌面/移动 8 个场景；组件与 controller 拆分较细；安全 header、strict mode 和源站/probe allowlist 完整。

### 6.13 测试与质量工程：9.8

优点：Go unit/race/vet/TCP、Node 静态守卫、Vitest、route authorization、Playwright/axe、migration integration 和 benchmark 分层清楚；失败消息可操作；关键安全和配置边界有负向测试；新增幂等指纹顺序/并发/共享命名空间、keep-alive/idle、TCP 半关闭、shutdown 连接归零、慢请求体 TCP 408、write/shutdown 预算、JWT claims/年龄、Bearer challenge/OpenAPI 引用和 production auth cache 响应头回归测试。

优点：actions 与 service images 固定 digest；Go module 动态发现；race/vet/govulncheck、CodeQL、dependency review、CycloneDX SBOM 与高危扫描齐全；Docker 使用固定 digest、multi-stage、distroless nonroot；manifest 记录 hash 与边界。

## 7. 性能瓶颈判断

当前没有证据证明 Fiber 是瓶颈，也没有证据证明它带来足够业务收益。实际生产瓶颈更可能依次出现在 PostgreSQL 查询与连接池、外部探测、序列化与前端 BFF、日志/观测出口、共享状态，以及最后才是路由器。继续做 hello-world QPS 优化价值有限。

应先取得以下数据：固定 Linux runner 的同业务 benchmark；目标 payload 和并发；数据库/RPC 延迟；TLS/edge；CPU、RSS、GC、FD、连接数、队列、错误率和 p99；取消后残留任务。只有 profile 显示 HTTP/JSON 热路径占主导，才值得继续做 Fiber 微优化。

## 8. 到 10 分的必要条件

1. 用目标 Linux/edge/数据库 workload 完成 Fiber 与至少一个 `net/http` 方案的可追溯决策。
2. 所有业务 use case 脱离 Fiber pooled context，Framework 有版本与兼容策略，并被第二个真实项目消费。
3. 目标 edge HTTP/2/3、header、timeout、buffering、disconnect、streaming 和 drain 契约自动化。
4. Redis/等价共享 limiter、idempotency、session/revocation 完成跨实例原子与故障测试。
5. OIDC/MFA、refresh rotation、集中撤销、secret manager 和审计闭环。
6. OTel outbound/database instrumentation、真实 collector/trace backend、exporter drop/retry 指标、dashboard、SLO 告警与受控故障演练完成。
7. PostgreSQL deadlock/failover/容量/备份恢复/PITR 达到记录的 RPO/RTO。
8. Kubernetes/等价平台完成多副本、PDB/HPA、rolling update、节点驱逐和 rollback 演练。
9. 镜像签名、SLSA provenance、部署验签和远端 CI artifact 持续可追溯。
10. MSFront bundle/Lighthouse/Web Vitals、多浏览器与生产多实例缓存/会话语义闭环。

## 9. 本轮已实施优化

- 配置新增 `HTTP_READ_TIMEOUT <= HTTP_IDLE_TIMEOUT` 与 `HTTP_WRITE_TIMEOUT <= HTTP_IDLE_TIMEOUT` 门禁。
- 配置新增 drain delay 加 read/write/request timeout 必须分别小于 shutdown timeout 的总预算门禁。
- 真实 TCP 新增不完整请求体 read timeout 契约：返回 408 且不进入业务 handler。
- MSFront `POST /api/auth/logout` 现在要求可信 Origin，拒绝跨站登出，并返回 `Cache-Control: no-store`。
- MSFront login/me/logout、system/management API 与 Proxy 401 统一禁止缓存，并由 production E2E 检查登录、me 和菜单响应的 `no-store`/`no-cache`。
- MSFront JWT 强制关键标准 claims、12 小时最大年龄和完整的有界角色数组，畸形令牌整体拒绝。
- Go demo JWT 强制 `sub`/`iat`/`nbf`/`exp`/`jti`、配置 TTL 最大年龄、有界角色 claims 及目标 `aud`，缺失、错配、错误 audience 及超龄令牌均被拒绝。
- Go 统一错误出口和私有响应设置 `Cache-Control: no-store, no-transform` 与 `Pragma: no-cache`；`/api/v1` ETag 包装器移除禁存储响应的 ETag，覆盖 404、413、校验、超时、panic、认证和限流，并由服务器测试验证禁缓存与不压缩。
- MSFront `disableResponseCaching` 同步设置 `no-store, no-transform`，由 Vitest、登出行为测试和生产 Chromium E2E 验证认证、菜单与跨站拒绝响应。
- MSFront proxy 对匿名保护页和已登录登录页重定向统一禁缓存，由 proxy 单测、Node 守卫和生产 Chromium E2E 验证 Location、307 和响应头。
- Go 受保护 API、metrics 与 pprof 的 RFC 6750 Bearer challenge 现由行为测试锁定，`WWW-Authenticate` 对 CORS 客户端可见；OpenAPI 将密码登录普通 401 与 Bearer 401 分离，并由 Go 契约测试防止受保护操作引用漂移。
- Go production 配置禁止 JWT secret、metrics token 和已启用 pprof token 跨信任域复用；三种错误组合在 `config.Load()` 阶段失败，环境示例和 Example 文档明确独立随机材料与 KMS/Vault 的边界。
- Go demo JWT 新增 `JWT_AUDIENCE`，签发和验证均绑定目标 API；同一签名密钥和 issuer 下缺失或错误 `aud` 的令牌由单元测试拒绝，并由根级评分守卫锁定。
- Go Request ID 入口新增 128 字节和安全字符集门禁；超长/分隔字符输入在 request logger 前被换发，原值不进入日志，替换事件以无标签 Prometheus counter 暴露，并有行为测试与根级守卫。
- Go production 配置拒绝 `TRUSTED_PROXIES=0.0.0.0/0` 与 `::/0`；真实 TCP 测试证明未受信连接的伪造 XFF 被忽略，明确可信代理才可提供基于 IP 限流使用的客户端地址。
- Go 请求日志不再通过 `Response.Body()` 计算流响应字节，未知长度记录为 `-1`；`/api/v1` 缓存验证器跳过流 body，同时保留普通弱 ETag/304 和 `no-store` ETag 移除语义。
- 新增慢读客户端真实 TCP 写超时契约：受控 socket 缓冲制造背压，断言服务端安装 `WriteTimeout` 截止时间、底层写入返回 timeout 且流生产提前终止；普通与 race 测试均通过。
- Go 幂等中间件新增 SHA-256 请求指纹注册：method、原始 target、principal、规范化 Content-Type 和 body 与 key 绑定；相同请求继续回放，不同请求复用 key 返回 409，顺序、并发和共享命名空间测试通过。
