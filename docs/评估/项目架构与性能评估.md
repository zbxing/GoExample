# GoExample 项目架构与性能评估

评估日期：2026-08-17  
评估范围：根 Node/Yarn 编排、Framework、Proj/Example、MSFront、PostgreSQL 数据层、测试、CI、供应链、Docker 与文档  
评分规则：每项最高 10 分，综合评分最高 10 分；综合分按权重计算，不使用分享评分  
目标：10 分；没有真实运行记录的能力不按生产闭环计分

## 1. 执行结论

V6 实施后的综合评分为 **9.0/10**，精确加权值为 **8.993/10**。相比 V5 的 8.793，提高 0.200 分。

项目已经具备清晰的多项目边界、成熟的 Fiber HTTP 基础设施、较完整的本地质量门禁、可执行 PostgreSQL migration、OpenAPI 3.1 路由契约和供应链扫描入口。Go 核心质量仍高于项目整体平均；当前主要短板已从“基础工程能力缺失”转为“生产环境闭环证据不足”。

本轮确认并完成：

1. PostgreSQL 初始 schema 覆盖 6 张业务表，含约束、外键、大小写不敏感唯一索引和查询索引。
2. migration runner 使用 SHA-256、session advisory lock、单文件事务和 migration history；支持 `--dry-run` 与 `--status`。
3. PostgreSQL pool size、连接、空闲、statement 和 query timeout 均可配置且有严格边界。
4. 会话/API Key 撤销与审计写入改为同一事务；审计失败不再静默忽略。
5. 标准 OpenAPI 3.1 文档成为 Fiber API 和 MSFront inventory 的单一事实源。
6. Go 契约测试直接比较 OpenAPI 与 `app.GetRoutes(true)`，覆盖 17 条实际操作、operationId 唯一性和响应声明。
7. CI 新增固定 commit SHA 的 CycloneDX SBOM 生成和 Grype High 阈值扫描。
8. 根测试、Go race/vet/coverage/vulnerability、MSFront lint/typecheck/test/build 和生产依赖 audit 均完成本地验证。

尚不能计为完成：真实 PostgreSQL migration/并发/恢复验证、OIDC/MFA、跨实例 limiter/idempotency、OpenTelemetry、浏览器 E2E、Linux/TLS 容量与长稳、远端 Actions 成功记录、镜像签名和部署恢复演练。

## 3. 当前架构

```text
package.json / yarn xxx
├─ scripts/                         环境、Go、MSFront 和 migration 编排
├─ tools/                           共享工具
├─ __test__/                        根 Node、contract、integration、E2E 资产
├─ docs/openapi/openapi.json        Fiber API 单一事实源
├─ go.work
│  ├─ Framework/                    公共 Fiber module
│  │  ├─ auth                       演示 JWT
│  │  ├─ config                     严格环境配置
│  │  ├─ health                     并发检查、缓存、draining
│  │  ├─ httpapi                    Fiber、中间件、平台路由
│  │  ├─ observability              slog、HTTP/runtime metrics
│  │  ├─ server                     listener 和优雅停机
│  │  └─ validation                 struct validator
│  └─ Proj/Example/                 示例服务工程
│     ├─ cmd/server                 composition root
│     └─ internal/projectapi        项目私有路由和 OpenAPI 漂移测试
└─ MSFront/                         Next.js 管理台与 BFF
   ├─ app                           页面和 21 个 Route Handler
   ├─ lib/server                    文件/PostgreSQL DAL、认证、RBAC、schema
   ├─ database/migrations           PostgreSQL schema 单一迁移源
   ├─ scripts/migrate.mjs           migration runner
   └─ __tests__/unit                11 个 Vitest 文件
```

主要请求链：

```text
Fiber: requestid -> logging -> metrics -> recover -> helmet -> earlydata
       -> CORS -> diagnostics -> ETag/compress -> routes -> limiter -> deadline

MSFront: proxy 乐观会话检查 -> Route Handler -> Origin check -> requireSession
         -> requireApiAccess -> Casbin policy -> Zod -> repository -> file/PostgreSQL

Database migration: discover -> SHA-256 -> advisory lock -> history check
                    -> BEGIN -> SQL -> history row -> COMMIT -> unlock
```

## 5. 各维度优缺点

### 5.1 Workspace 与模块边界：9.5/10

优点：

- 根目录只负责 Node/Yarn 编排，Framework、Proj、MSFront 和工具目录职责清晰。
- `go.work` 管理公共 module 与项目 module，项目私有实现位于 `internal`。
- CI 从 workspace 动态发现 module/project，新项目可沿用根命令和矩阵。
- 测试布局遵循 Go 与 Next 生态，不强行把 `*_test.go` 搬离 package。

缺点：

- 只有 Example 一个真实项目，Framework 抽象尚未被第二个业务工程反证。
- Framework 没有 tag、兼容窗口、弃用周期或变更日志策略。
- `httpapi.Options` 字段较多，未来可能变成跨项目耦合入口。

### 5.2 Go/Fiber 框架设计：9.3/10

优点：

- Fiber v3.5.0、composition root、配置、健康、指标、验证、认证示例和 listener 生命周期边界明确。
- Prefork、Immutable、ReduceMemoryUsage 等性能选项没有在缺证据时盲目启用。
- auth 明确标记为 demo，生产环境默认关闭并拒绝默认 secret。
- package 可独立测试，Example 项目路由不污染 Framework。

缺点：

- demo auth 仍位于公共 Framework，正式身份适配器接口尚未落地。
- 公共扩展点主要依赖 `Options` 和 callback，没有版本兼容测试。
- 没有第二种存储、队列或后台任务实现验证 composition 边界。

### 5.3 HTTP 与 API 契约：9.8/10

优点：

- request ID、日志、metrics、recover、安全头、CORS、deadline、limiter、idempotency、JSON 媒体类型和 body limit 较完整。
- 代理信任默认关闭；credentialed CORS 禁止通配符；metrics/pprof 可独立保护。
- MSFront 20 个 JSON 写入口继续使用严格 Zod schema 和稳定 400/413/415/422 错误。
- OpenAPI 3.1 已取代简化 inventory，MSFront 直接读取同一文档。
- Go 测试使用 Fiber 实际路由表验证 17 个操作，能阻止路径/方法/operationId 漂移。

缺点：

- OpenAPI response data 仍使用通用 envelope，业务数据 schema 不够细。
- 尚无 SDK 生成、breaking-change diff、版本弃用和消费者兼容矩阵。
- auth 路由按配置启用，文档只通过描述表达这一部署条件。

### 5.4 并发与生命周期：9.1/10

优点：

- request deadline 写入下游 context，耗时示例响应取消。
- readiness 共享单次刷新，取消调用方不会污染公共缓存。
- 注册、revision 和 draining 会使缓存失效，报告返回深拷贝。
- 停机先 draining，再等待传播并在总预算内关闭 listener。

缺点：

- 忽略 context 的依赖检查仍可能留下长生命周期 goroutine。
- 没有队列 consumer、定时任务和后台 worker 的 stop ordering。
- 缺目标编排平台 termination grace 和 load balancer 传播实测。

### 5.5 运行时性能：8.7/10

优点：

- Fiber/fasthttp 热路径轻量，metrics 使用 route template 避免动态 path 标签爆炸。
- health/probe cache 与 in-flight merge 降低重复 I/O。
- PostgreSQL pool 现在有明确 max、connect、idle、statement 和 query timeout。
- Docker 使用静态、non-root runtime 和裁剪构建参数。

缺点：

- 当前 benchmark 基于 Windows `app.Test`，不代表真实 socket/TLS/代理/数据库吞吐。
- 没有 benchstat 基线和自动退化阈值。
- 未采集 CPU/heap/block/mutex profile，也没有代表性 PGO profile。
- 数据库索引是基于查询形状设计，尚无真实 `EXPLAIN (ANALYZE, BUFFERS)`。

### 5.6 可观测性：8.2/10

优点：

- slog 记录 request ID、route、status、duration、response size 和 client IP。
- Prometheus exposition 覆盖请求、in-flight、直方图、uptime、goroutine、heap 和 GC。
- metrics 标签基数受控，诊断端点默认关闭或受 token 保护。

缺点：

- 没有 OpenTelemetry trace、OTLP exporter、baggage、span status 或日志/指标关联。
- 没有 SLI/SLO、recording rule、dashboard 和 alert 模板。
- 日志缺统一敏感字段过滤、采样和留存策略。

### 5.7 安全与身份：8.5/10

优点：

- Go JWT 固定算法、issuer、时间和 jti；MSFront JWT 固定 issuer/audience/算法。
- Cookie 为 HttpOnly、生产 Secure、SameSite=Lax；写请求校验 Origin。
- Route Handler 重新读取用户/角色，37 个方法有授权契约。
- 输入 schema、错误脱敏、CSP/HSTS/COOP/CORP 和关闭 `X-Powered-By` 已完成。
- 会话/API Key 撤销和审计现在原子提交，审计错误不会再静默吞掉。

缺点：

- 文件身份与自包含 JWT 不是多实例生产身份系统。
- 没有 OIDC/OAuth2、MFA、token family、刷新轮换、设备管理或集中撤销。
- 没有 KMS/Vault、密钥轮换、泄漏响应和登录风险控制。
- SSRF 仍需 DNS/IP/CIDR 解析与网络出口策略共同控制。

### 5.8 数据一致性与持久化：8.5/10

优点：

- 初始 migration 覆盖 projects、users、roles、sessions、API keys 和 audit events。
- schema 含 PK/FK/CHECK、时间、version、JSON 类型约束、活动凭据索引和大小写不敏感唯一索引。
- migration runner 有命名规则、SHA-256、防并发 advisory lock、history 和单文件事务。
- 访问管理更新、角色同步、撤销和审计均使用事务；数据库 timeout 不再依赖驱动无限等待。
- 文件存储继续使用严格读取、原子替换和数据目录边界。

缺点：

- 本机没有 PostgreSQL/Docker，migration 仅完成解析和 dry-run，未执行真实 DDL。
- 没有 seed 生命周期、向下/向前兼容窗口、在线大表迁移策略或 rollback 决策矩阵。
- 没有并发冲突、死锁、连接耗尽、故障切换和事务隔离 integration test。
- 没有 PITR、备份校验、恢复时间/恢复点目标和恢复演练。

### 5.9 MSFront 架构与性能：8.8/10

优点：

- app/components/providers/lib/data 边界清晰，server-only DAL 和 DTO 方向正确。
- 探针有超时、缓存、请求合并、生产 origin allowlist。
- 自定义 error/loading/not-found、安全头、Zod 输入和错误脱敏完整。
- API inventory 不再维护重复 JSON，而是读取标准 OpenAPI。
- lint、typecheck、41 个单测和 production build 均通过。

缺点：

- 259 个 Client Module 偏多，大型 controller/repository/dictionary 增加 bundle 和维护成本。
- 没有 bundle budget、Core Web Vitals、interaction profile 或浏览器 trace。
- 没有 Playwright、axe、视觉回归和真实权限端到端测试。
- PostgreSQL 页面目前没有真实数据库运行证据。

### 5.10 测试与静态质量：9.4/10

优点：

- Go 组合覆盖率 85.6%，覆盖 CORS、deadline、limiter、idempotency、panic、JWT、metrics、health concurrency 和 shutdown。
- test/race/vet/vulnerability/build 均有根命令和 CI 入口。
- MSFront 41 个单测覆盖认证、RBAC、文件存储、密码、Origin、probe、请求体、数据库配置、migration 和 OpenAPI parser。
- Go OpenAPI 契约直接读取 Fiber runtime route registry，不依赖脆弱的源码正则。

缺点：

- validation 68.4%、Example main 65.0%、server 75.6%，错误分支仍可提升。
- 没有真实 PostgreSQL Route Handler integration test。
- 没有浏览器 E2E、a11y、视觉或前端性能测试。
- coverage 与 benchmark 仍无 CI 退化阈值。

### 5.11 配置与开发体验：9.8/10

优点：

- `yarn env`、`yarn dev`、`yarn test`、`yarn migrate:front` 和 Go 子命令统一。
- Go 下载有官方 metadata、SHA-256 和失败清理，module 执行 `go mod verify`。
- Go project path 有字符和目录穿越保护，构建注入版本、commit 和 UTC build time。
- `yarn vuln:server` 优先使用本地固定 scanner，断网时不再强制请求 Go proxy。

缺点：

- 本地 scanner 数据库可能过期，离线成功必须同时记录 DB 时间。
- 工具下载中断、代理异常、磁盘满和权限错误的自动测试仍不完整。

### 5.12 CI 与供应链：9.2/10

优点：

- 所有 action 固定完整 commit SHA，权限最小化，旧任务可取消。
- Go CI 动态矩阵执行 test/race/vet/vulnerability/build 和 Docker health smoke。
- MSFront CI 执行 frozen install、audit、lint、test、typecheck 和 build。
- 新 workflow 使用 Syft 生成 CycloneDX JSON，并以 High 为失败阈值扫描 SBOM。
- OpenAPI 变更会同时触发 Go 和 MSFront 契约检查。

缺点：

- 本轮没有远端 Actions 成功记录，SBOM/Grype 仅证明配置和 actionlint 正确。
- 没有 CodeQL、secret scanning 策略、license policy 或 dependency review。
- 没有镜像级 SBOM/扫描、cosign 签名、SLSA provenance 和发布 attestation。

### 5.13 扩展与部署能力：7.4/10

优点：

- 多 module/multi-project、动态 CI、项目 Dockerfile、readiness/draining 适合继续扩展。
- PostgreSQL schema、migration 和连接池为多实例数据层提供了迁移基础。
- file/database adapter 保留本地演示与生产存储的切换点。

缺点：

- limiter、idempotency 和部分本地文件状态仍是进程内状态，不能直接水平扩容。
- 没有 Kubernetes/Compose/Helm、NetworkPolicy、PDB 和 autoscaling 参考实现。
- 没有 cache/message 实际依赖、multi-region、一致性或灾难恢复策略。
- 没有资源 request/limit、容量模型和负载驱动的扩缩容证据。

### 5.14 文档与可维护性：9.6/10

优点：

- 根、Framework、Example、MSFront、database、tools 和测试目录均有职责说明。
- OpenAPI 是机器可验证文档；V1-V6 保留优化历史和验收证据。
- 文档明确 demo auth、进程内状态、目标环境证据和 PGO/Prefork 边界。

缺点：

- 缺 ADR、threat model、data flow、runbook、incident 和 rollback 文档。
- 扫描规模与评分仍需人工更新，尚未生成带 commit 的审计 artifact。

## 7. 性能基线与解释

环境：Windows/amd64、Intel Core i5-10400、Go 1.26.6 执行器、module language version 1.25。V6 未修改 Fiber 热路径，因此沿用最近一次固定 `-benchtime=50000x -count=5` 基线。

| Benchmark | 5 轮中位数 | 内存/分配 | 正确解释 |
| --- | ---: | ---: | --- |
| Hello endpoint 串行 | 41.9 µs/op | 约 16.5 KB、109-110 allocs | 包含 `app.Test` 和完整 middleware，不是网络吞吐 |
| Hello endpoint parallel | 15.4 µs/op | 约 17.1 KB、112 allocs | 仅用于本地版本间相对回归 |
| Metrics middleware parallel | 5.0 µs/op | 约 10.9 KB、71 allocs | 不包含 Prometheus 拉取全链路 |
| Cached readiness | 203.7 ns/op | 336 B、2 allocs | 不包含真实依赖检查 |

禁止由上述数字推导生产 QPS、TLS p99、数据库容量、内存上限、Prefork/PGO 收益或多实例一致性。PostgreSQL 新索引同样需要目标数据量上的 `EXPLAIN ANALYZE`，不能由 schema 静态审查得出性能结论。

## 9. 为什么仍不是 10 分

当前差距不是继续增加中间件数量可以解决的，而是需要外部系统和目标环境证据：

1. **身份**：OIDC/OAuth2、MFA、集中撤销、密钥轮换和风险控制尚未实现。
2. **数据**：migration 尚未在真实 PostgreSQL 上执行，缺并发、故障切换、PITR 和恢复演练。
3. **分布式状态**：limiter、idempotency 和锁尚未使用共享 store。
4. **可观测性**：没有 OpenTelemetry、SLO、告警和跨信号关联。
5. **前端证据**：没有 Playwright、axe、Core Web Vitals、bundle budget 和视觉回归。
6. **容量**：没有 Linux/TLS/代理/数据库真实 I/O 压测、长稳和故障注入。
7. **交付**：没有远端 workflow 记录、镜像扫描/签名、provenance 和部署恢复证明。

只修改评分数字不会提高工程质量。后续应按 [待优化 V6](../待优化/待优化V6.md) 的剩余项逐项获取可重复证据；达到 10 分需要代码、运行环境、运维流程和恢复能力同时闭环。
