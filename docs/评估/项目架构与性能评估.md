## 1. 互斥分支决策与复评结论

V24-01 已通过专项测试、完整 Go workspace、164 项 Node 测试、276 个 evidence 输入、53 个制品、总 manifest/verify、差异检查与图谱更新。V24-02 至 V24-10 都只能由不可替代的真实 Linux、硬件、业务负载、edge、依赖、IdP/KMS、远端制品、Kubernetes、正式发布、权限或组织审批关闭。因此 V24 的仓库内可执行项已经清零，本轮严格执行互斥流程的第二分支：覆盖本评估、生成 V25，再只按 V25 实施；不继续改写 V24。

V25 图谱与源码复评确认，V24 的 `runBoundedCommand()` 已为 evidence manifest 与独立 verifier 的顶层 Git/Yarn/Go 探测提供 64 MiB 输出上限、默认及最大 30 秒时限、`SIGTERM` 和严格 Windows fallback 分类。但聚合器随后调用的 7 个领域 evidence verifier 仍各自直接使用无界 `spawnSync()` 读取当前 Go 版本或 Git commit：

- audit chain、authorization、OIDC browser、SDK release 与 SDK consumer 各有 Go/Git 两类探针，共 10 条身份路径；
- SDK consumer matrix 与 server recovery 各有一条 Git 探针，共 2 条身份路径；
- 12 条路径在报告生成或独立验证时执行，均没有 `timeout`、`killSignal` 或显式 `maxBuffer`，还重复维护 trim、退出码和严格格式校验。

因此 V24 解决的是顶层边界，不代表整条证据链已经有界。异常阻塞或被 `GO_BINARY`/PATH 劫持的工具可以越过顶层探测，在任一领域 verifier 中无限等待；总 manifest 和 verify 都会被连带阻塞，CI 只能依赖 5 至 20 分钟的 job 总超时，后续证据上传可能无法执行。这是仓库内可复现、可测试且收益最高的 V25 缺口。

### 2.1 Workspace、模块与工具链

- `go.work` 固定 `toolchain go1.25.13`，统一 Framework、服务、解决方案、SDK 与独立消费者等 Go module；工具脚本由根 `package.json` 和固定 Yarn 入口编排。
- `selectRepositoryToolCommand()` 统一显式命令、仓库托管候选与 PATH fallback 的优先级，并保留严格入口所需的版本和 `GOROOT` 隔离语义。
- `runBoundedCommand()` 已建立通用同步短命令的输出、时间与失败分类边界；V25 不改变长时间测试、构建、发布或恢复 drill 的任务专属 timeout。
- 当前 7 个领域 evidence 模块绕过该共享边界并复制身份解析。V25 应在现有 helper 内导出严格 Go/Git 身份读取器，由领域模块保留各自错误前缀，避免新 schema、异常类型或公开返回契约扩散。

### 2.2 HTTP、应用层与公共 API

- `server.RunHTTP` 持有监听、TLS、连接状态、shutdown 与 drain；标准 `http.Handler` 是服务入口，Fiber 位于兼容适配层。
- `HTTPApplication` 将 query、command、route 与 event stream 描述符解释为传输行为，业务应用不直接依赖具体 HTTP 框架。
- 公共 API snapshot、兼容策略、changelog、OpenAPI、生成 SDK、release manifest 与 consumer matrix 共同约束外部变更；正式 tag、升级窗口和第二个真实外部消费者仍属发布治理边界。
- deadline、连接上限、request admission、限流、body 上限、慢客户端、SSE、keep-alive、HTTP/2、取消与 shutdown 均有本地 TCP/TLS 或行为测试；目标 DNS、真实证书、edge/ingress 与 HTTP/3 未实测。

### 2.3 数据、消息与出站依赖

- SQL 客户端约束查询与事务 timeout、序列化/死锁重试、乐观并发，并在 `BeginTx` 后和 `Commit` 前检查取消。
- queue 层分离 broker-neutral 契约和 NATS JetStream adapter，覆盖确认、重投、DLQ、lease 延长、重启、快照及三节点本地集群合约。
- HTTP 客户端限制响应体和重试范围，并提供 deadline、backoff、circuit breaker 与低基数观测。
- 真实 PostgreSQL/Redis/NATS 跨主机故障、磁盘损坏、PITR、exactly-once 与批准 RPO/RTO 仍未记录，本轮不改变这些结论。

### 2.4 身份、安全、可观测性与证据链

- 仓库内覆盖 JWT/OIDC/JWKS、浏览器授权回调、会话与设备清单、资源授权、CSRF、输入限制、安全头、限流、幂等及加密哈希审计链。
- OTEL span、metrics、SLO/Prometheus 规则与审计事件使用固定或低基数维度，并对队列饱和、导出器阻塞/失败和 shutdown flush 建立测试。
- evidence generator 与 verifier 对 schema、artifact inventory、SHA-256、Git commit、工作区状态和必需输入进行双向约束；总 manifest 不能替代领域 verifier 的执行边界。
- V25 只把短身份探针收敛到既有 30 秒/64 MiB helper，并把 helper 纳入 7 组领域报告的 source 哈希范围；不放宽校验、不删除制品、不把失败降级为 `not_recorded`。
- 正式 IdP/MFA、KMS/Vault、生产 policy engine、SIEM、collector、告警投递和值班演练需要外部系统及权限，继续保持 `not_recorded`。

## 3. 性能与容量评估

### 3.1 已证明的仓库内结论

- Framework 与 Example 具有 HTTP/Fiber/标准入口微基准、TCP transport 基准和容量采样器；关键热路径使用 `ReportAllocs` 或 `AllocsPerRun` 门禁。
- 已优化路径包括标准 HTTP adapter、出站 tracing、队列/JetStream header、ETag、限流 header、响应体上限、重试与 circuit breaker。
- admission、连接池、request/transaction deadline、body 上限、backoff、breaker 与 drain 为容量失控提供结构性保护。
- V25 的 30 秒约束作用于同步身份工具和 CI 尾延迟，不是服务请求热路径；不调整服务 RPS、p99、内存、GC、网络协议或容量分项。

### 3.2 不能外推的结论

- 微基准的 `ns/op`、`B/op` 和 `allocs/op` 只证明相同机器、工具链和输入下的局部变化，不能证明生产吞吐或容量。
- 当前没有同一不可变 Linux runner、CPU、Go、`GOMAXPROCS`、连接模型、payload 和观测口径下的 Fiber、`net/http`、Framework 标准入口及选定外部框架完整对照。
- 真实认证、PostgreSQL、Redis、NATS、TLS edge、SSE 慢客户端及至少 30 分钟饱和/长稳趋势仍缺 CPU、GC pause/alloc rate、RSS、FD、goroutine、连接池和队列积压数据。

### 3.3 性能判定

运行时性能工程接近成熟，局部回归门禁可信；生产容量与跨框架选型仍为 `not_recorded`。V25 降低的是证据任务的无限等待风险，不将工具进程上限换算成业务性能收益，也不改写目标环境容量判断。
