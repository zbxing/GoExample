# Framework compatibility policy

`Framework` is currently on the `0.1.x` development line. A release tag must use the module-scoped form `Framework/v0.1.0`; the repository currently does not claim that such a release has been published.

## Supported baseline

- Go language: `1.25.x`; CI and local orchestration currently pin `go1.25.13`.
- Fiber: `3.5.x` for the transport-specific APIs that remain public.
- API snapshot: `Framework/api-snapshot.json`, generated from importable production packages only.

Run `yarn api:compat` to require the working snapshot and current exported API to match. Run `yarn api:snapshot` only when intentionally adding API or after an approved compatibility-line change. Once the first snapshot exists on the target branch, the PR workflow additionally compares the current API with that target snapshot: additions are compatible, while removal or signature changes fail. The one-time bootstrap path is explicit in CI and still requires the current source and checked-in snapshot to match exactly.

Before `v1.0.0`, a breaking change requires a minor version increment in `Framework/VERSION`, an updated snapshot, an `Unreleased` changelog entry, and migration guidance. At or after `v1.0.0`, it requires a major version increment. Patch releases never permit source-incompatible API changes.

The optional `httpapi.Options.OIDCBrowser` field and `httpapi.NewOIDCBrowser` constructor are additive. Existing resource-server and demo compositions retain their routes and behavior when the field is nil; the original constructor retains callback-only behavior. `httpapi.NewOIDCBrowserWithSessions`, `auth.BrowserSessionManager`, and `auth.BrowserSessionStore` are additive opt-in APIs. Session-enabled compositions add a conditional logout operation and allow protected routes to use the opaque cookie; unsafe cookie-authenticated requests must supply the bound CSRF cookie/header pair. Bearer behavior is unchanged and an explicit Authorization header always takes precedence over cookies.

`auth.(*JWKSVerifier).VerifyIDTokenWithAccessToken` is additive. Existing `VerifyIDToken` callers remain source compatible and preserve the previous missing-`at_hash` behavior; callback compositions in this repository use the new method so a present ID-token `at_hash` is bound to the exchanged access token. The current verifier accepts only RS256, so the binding uses the corresponding SHA-256 left-half Base64URL digest. Providers that omit `at_hash` remain compatible; malformed or mismatched values fail closed. OpenAPI and SDK contracts are unchanged.

`auth.NewOIDCClient` retains its public config, metadata, constructor, and exchange signatures, but token endpoint client authentication is now validated against discovery. A configured secret selects `client_secret_basic`; an omitted `token_endpoint_auth_methods_supported` remains compatible because OIDC defines that method as the default. A client without a secret now requires an explicit `none` declaration, so deployments that previously relied on missing metadata for a public client must correct the provider metadata or configure a supported confidential client. Providers that only advertise `client_secret_post`, JWT, or mTLS methods remain unsupported and fail at construction rather than downgrading. Confidential requests no longer duplicate `client_id` in the form, and RFC 6749 form encoding is applied before Basic authentication. The API snapshot, OpenAPI, and generated SDKs are unchanged.

OIDC discovery and token responses also reject duplicate JSON object keys before decoding, including escaped spellings and case-folded spellings that could otherwise target the same Go field. Malformed documents and multiple top-level values fail through the existing fixed sentinels. This is an intentional fail-closed behavior change for ambiguous provider responses; normal single-key JSON, unknown fields, public signatures, API snapshot 373, OpenAPI, SDKs, and browser evidence schema 3 remain compatible.

Session-enabled compositions now also add conditional list, bounded device-name update, subject-bound single-session revoke, and revoke-all routes. This is an additive OpenAPI `1.4.0` change: existing operations are unchanged, while clients that use the new PATCH or DELETE operations must send the CSRF cookie/header pair when authenticating by browser cookie. Bearer-authenticated calls do not require CSRF. Malformed, unknown, and cross-subject public session IDs intentionally share the same 404 response; legacy stores without inventory or metadata support fail closed with 503. Device names are explicit caller metadata only; the Framework does not infer a device fingerprint or parse User-Agent values.

`auth.BrowserSessionConfig.MaxSessionsPerSubject`, the public session inventory types/methods, and `BrowserSessionInventoryStore` are additive. A zero per-subject limit defaults to the existing global limit. The original `BrowserSessionStore` method set is unchanged, so existing stores continue to support start/verify/end; inventory operations against a legacy external store return `ErrBrowserSessionInventoryUnavailable`. Store implementations that opt into the extension must preserve subject scoping, bounded results, atomic limits/revocation and fail-closed backend errors.

The Redis browser-session payload and indexes now include the public session ID, hashed subject ownership and creation time. A rolling deployment must treat pre-inventory browser sessions as invalid and require reauthentication, or drain/reset only the application's browser-session namespace before enabling the new binary; mixed old/new writers are not supported. Authorization-request and refresh-session namespaces are unaffected.

Inventory reads are implementation-only compatible: Redis performs expiry cleanup, bounded token selection and payload reads in one Lua command, while the existing Go validation and HTTP/OpenAPI/SDK contracts remain unchanged. The one-command guarantee is covered by local telemetry/command-count tests; it does not assert production Redis latency, HA, TLS/ACL, capacity or recovery behavior.

Refresh-session persistence is implementation-only compatible: Redis rotation and family revoke now derive the family from the hash-only token mapping and perform validation plus mutation in one Lua command each. `auth.SessionStore`, manager behavior, fixed error sentinels, API snapshot 373, OpenAPI, SDKs and serialized contracts remain unchanged. The one-command guarantee is covered by warmed local telemetry tests; it does not assert production Redis latency, HA, TLS/ACL, capacity, eviction or cross-host recovery.

`auth.AuthorizationRequestStore`, `AuthorizationRequestRecord`, and the `StartContext`/`CompleteContext` methods are additive. Existing `Start`/`Complete` callers retain bounded in-process behavior. Injecting a store changes ownership of pending state to that backend; implementations must preserve hash-only state keys, atomic one-time consumption, finite expiry and fail-closed errors.

The optional `auth.JWKSConfig.RequiredACR`, `RequiredAMR`, and `MaxAuthAge` fields and `auth.AuthorizationRequestConfig.ACRValues` are additive. Their zero values preserve existing ID-token and authorization-request behavior. When enabled, assurance requirements intentionally reject callbacks without a matching `acr`, every required `amr` value, and a fresh `auth_time`; callers must deploy the matching IdP policy before enabling them.

The snapshot gate covers exported declarations and signatures. It does not prove behavioral compatibility, serialized schema compatibility, performance stability, or a successful release. Those require contract tests, benchmarks, deprecation windows, and release artifacts appropriate to the change.

`httpapi.HTTPApplication` and `NewHTTPApplication` are additive standard-library ownership APIs. The returned value implements `http.Handler` and exposes a matching `Shutdown(context.Context)` method while keeping the internal Fiber app private. Existing `httpapi.New`, `NewHTTPHandler`, `RouteRegistrar`, response/SSE helpers, observability middleware, and `server.Run` signatures remain supported on the current compatibility line. Standard services may migrate without changing `Options`, routes, wire behavior or timeout semantics; removal of the Fiber-native compatibility channel requires a future versioned decision and external migration evidence described by ADR 0003.

`httpapi.ApplicationEventStream`, `NewEventStream`, `NewAuthenticatedEventStream`, and `NewAuthorizedEventStream` are additive transport-neutral SSE registration APIs. They use fixed GET static paths under `/api/v1`, pass only `context.Context` and a bounded `Last-Event-ID` to application sources, and reuse the existing bounded SSE lifecycle. Existing `RegisterRoutes`, `RouteRegistrar`, Fiber SSE helpers, `ApplicationQuery`, and `ApplicationCommand` APIs remain unchanged; event streams cannot be mixed with `RegisterRoutes` or overlapping GET/HEAD application routes. Stream source state is in-process/application-owned and does not claim durable replay or target-edge buffering.

`httpapi.ApplicationRoute`, `ApplicationRouteRequest`, `ApplicationRouteResponse`, and `ApplicationRouteHandler` are additive transport-neutral custom route APIs. Routes use canonical static paths under `/api/v1`, default to GET, and may declare another standard HTTP method. Handlers receive defensive copies of context, method/path, multi-value query, headers, and body; response status, headers, and body are bounded and validated before writing. Handler routes and event streams cannot overlap application descriptors or be mixed with `RegisterRoutes`; existing Fiber APIs remain unchanged. This boundary does not claim dynamic routing, arbitrary middleware composition, durable stream replay, target-edge buffering, or HTTP/3.

`httpclient.LimitResponseBody` and `httpclient.ErrResponseBodyTooLarge` are additive opt-in APIs. Existing clients retain unbounded streaming response bodies unless a caller explicitly applies a positive per-response limit. A known oversized `Content-Length` is rejected before reading; unknown-length and chunked bodies stream up to the limit and use one bounded probe to distinguish exact EOF from excess data. Successful complete reads preserve ordinary keep-alive reuse, while oversized bodies are closed without an unbounded drain and might therefore forfeit that connection.

`httpclient.RetryConfig` and `Config.Retry` are additive and disabled when `MaxAttempts` is zero. Enabling retries affects only GET, HEAD, OPTIONS, and TRACE requests whose bodies are absent or reproducible through `Request.GetBody`; write methods are never inferred as replay-safe. The total attempt count is capped at five, exponential backoff is capped at five seconds and remains inside the original request context/deadline. Only an intermediate response already selected for retry and reporting a non-negative `Content-Length` of at most 32 KiB is read toward EOF before close, with a strict declared-length-plus-one ceiling; unknown, larger, or non-conforming bodies remain bounded, and a final response is never consumed by the retry layer. Existing clients therefore retain single-attempt behavior unless they opt in, and the V59 behavior change requires no public API migration.

`httpclient.CircuitBreakerConfig`, `Config.CircuitBreaker`, and `ErrCircuitOpen` are additive. A zero failure threshold preserves the prior behavior. When enabled, the breaker treats one client as one downstream failure domain and observes the final logical result outside any configured retry policy; callers using unrelated downstreams must create separate clients. Open state, one half-open probe, generation isolation, thresholds, and timeout are bounded. The optional additive `CircuitBreakerObserver` receives only a `CircuitBreakerObservation` with fixed `State` and `Event` strings, runs synchronously outside the breaker state lock, and has panic isolation. Configuring it while the breaker is disabled fails during `New`; callers must keep the callback non-blocking. The state is in-process only and is intentionally not shared across replicas.

`httpapi.ServerSentEventOptions.StreamTimeout` is additive. Zero preserves the existing behavior in which `Options.RequestTimeout` and the standard server write timeout continue to bound the stream. A positive value opts into a distinct SSE lifetime after the handler claims the body stream; it must exceed the heartbeat interval and cannot exceed 24 hours. Any shorter standard caller deadline, client cancellation and application shutdown continue to win. `NewHTTPHandler` also bridges standard `http.ResponseController` write-deadline control: the transport deadline is the effective stream deadline plus a fixed one-second protocol-cleanup allowance, and an early completion shortens the remaining allowance to one second. An unsupported controller preserves compatibility; another controller error fails before the response is streamed. Enabling the field therefore does not create an unbounded stream or require increasing the timeout of unrelated API requests.

The unreleased `queueclient.Client.MinimumDeliveryLease`, optional delivery lease-extension fields/callback/observer, package-level `natsjetstream.PreflightConsumer`, and adapter-bound `(*natsjetstream.Adapter).PreflightConsumer` APIs are additive on the `0.1.x` line; zero values keep the prior static-budget behavior and existing adapter construction remains source-compatible. Package-level preflight retains its existing signature and generic consumer checks. Both preflight entrypoints now require the fresh server response to describe a pull consumer (`DeliverSubject == ""`); the additive fixed `ErrConsumerNotPull` classifies a push consumer that cannot satisfy the adapter's bounded `Next()` receive contract without exposing delivery configuration or identity. Neither entrypoint subscribes to a push subject or changes the consumer. Both preflight entrypoints also fail closed when the fresh server response reports an active pause; the additive fixed `ErrConsumerPaused` classifies that unavailable startup state without exposing pause timing or identity, and neither entrypoint performs an automatic control-plane resume. They also fail closed unless the server reports `DeliverAllPolicy`; the additive fixed `ErrConsumerDeliveryPolicy` classifies previously accepted `DeliverLast`, `DeliverNew`, start-sequence, start-time, and last-per-subject consumers that can skip retained backlog. Both entrypoints require `ReplayInstantPolicy`; the additive fixed `ErrConsumerReplayPolicy` classifies original or unknown replay modes that can impose historical message intervals on backlog recovery. These are intentional unreleased reliability tightenings and do not recover messages already removed by stream retention or guarantee a target backlog-clearance time. The adapter method additionally requires its actual consumer to report exactly one filter equal to the adapter's validated literal subject; callers that need subject isolation should migrate to the method. It fails closed for empty, wildcard, mismatched, multiple, or conflicting filters through `ErrConsumerSubjectMismatch`. Adapter-bound preflight also requires a nonzero `MaxRequestExpires` to be at least the adapter's `FetchMaxWait`; zero retains the NATS unlimited value, while a shorter limit returns the additive fixed `ErrConsumerRequestExpires`. Package-level preflight cannot make this comparison because it intentionally has no adapter configuration, so callers needing pull-expiration compatibility must use the adapter method. Preflight also fails closed for a server-reported `HeadersOnly=true` consumer because that mode omits every payload required by `queueclient.Message.Body`; this does not reject a legitimate empty application payload. Deployments that enable JetStream lease extension must run preflight with the exact worker configuration and treat either a failed server-backed lease check or runtime extension failure as fail-closed. These checks do not replace stream retention, replica, subject or account ACL validation, consumer-mode or pause governance, target-environment backlog and latency calibration, or exactly-once settlement.

JetStream preflight also requires `PriorityPolicyNone` with no priority groups because the adapter's bounded `Next()` path supplies no request-level priority group, pin, priority, or overflow threshold. The additive fixed `ErrConsumerPriorityPolicy` classifies priority-enabled or inconsistent group configuration without exposing policy values, group names, identity, or backend text; callers needing priority scheduling require a separately designed adapter surface and migration. This tightening is source compatible on the unreleased `0.1.x` line and does not establish production priority governance, fairness, starvation resistance, target capacity, atomic settlement, or exactly-once delivery.

JetStream preflight now classifies every readable non-`AckExplicitPolicy` server configuration through the additive fixed `ErrConsumerAckPolicy` while retaining `ErrConsumerPreflight` for a missing or unreadable `ConsumerInfo`. AckAll is incompatible with concurrent per-message settlement because confirming a higher sequence can implicitly confirm lower sequences still being processed; AckNone, FlowControl, and unknown values likewise cannot implement the adapter's `Ack`/`Nak`/`Term` contract. The error returns the already computed required lease and exposes no policy value, identity, subject, URL, configuration, or backend text. Existing explicit-ack deployments remain source and runtime compatible; this tightening does not provide automatic consumer migration, atomic settlement, production acknowledgement governance, or exactly-once delivery.

JetStream `Adapter.ReceiveDelivery` keeps its public signature and configured maximum-wait range, but each internal pull now uses a caller-derived child deadline through nats.go `FetchContext` instead of an independent `FetchMaxWait` option. This is an intentional unreleased lifecycle correction: an in-flight empty pull observes caller cancellation immediately, while the adapter's configured duration still caps one pull and internal deadline/no-message results continue polling. Parent context errors remain visible and all unrelated SDK/backend failures remain the fixed `ErrReceive`; message conversion, acknowledgement, lease extension, DLQ behavior, preflight, telemetry, and control-plane ownership are unchanged. The added child context/timer has a measurable local fast-path cost and the local cancellation contract does not establish a production shutdown SLO, immediate broker waiting-request cleanup, capacity, or exactly-once delivery.
